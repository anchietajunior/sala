Aula 03 — APIs REST e URIs

Duração: ~2h  ·  Branch: aula-03-apis-rest-e-uris

Temas teóricos: o conceito de API, REST, verbos HTTP e a estrutura de uma URI [T-3]

Objetivos — ao final, o aluno consegue:

  • Definir o que é uma API e distinguir a interface publicada da implementação que ela oculta;
  • Nomear as partes de uma URI (esquema, host, porta, caminho, query, fragmento) em qualquer endereço real;
  • Explicar o que são recursos e representações e mapear os verbos HTTP nas operações CRUD;
  • Modelar um recurso como classe Python e manter a coleção como uma lista de objetos, não de dicionários;
  • Completar um CRUD em memória com DELETE e PUT, escolhendo verbo e status code adequados, e justificar a regra de geração de ids;
  • Validar a entrada de uma rota FastAPI com um schema Pydantic, explicando por que o 422 substitui o 500.

Estrutura da aula: o código vem antes da teoria. Primeiro o recurso Books amadurece — vira classe, ganha DELETE e uma regra de id defensável. Só então a teoria dá nome ao que foi escrito, e um segundo bloco de código fecha o CRUD com validação.

Passo 1 — o modelo Book: dando nome ao conceito

Por quê: a forma como guardamos os dados hoje decide o quanto vai doer trocá-los pelo banco na aula 04. Um dicionário aceita qualquer chave, não garante campo nenhum e espalha por todo o arquivo o conhecimento sobre "o que é um livro". Uma classe concentra num lugar só a resposta a essa pergunta. É a orientação a objetos da aula 01.2 entrando no projeto — e é o mesmo desenho que o ORM vai adotar daqui a duas aulas.

Logo depois de app = FastAPI(), crie o modelo:

class Book:
    def __init__(self, id: int, name: str):
        self.id = id
        self.name = name

    def __repr__(self):
        return f"Book(id={self.id}, name={self.name!r})"
  • __init__ é o único portão de entrada: não existe Book sem id e sem name;
  • __repr__ é como o objeto se apresenta no terminal — o dunder method da aula 01.2, agora com utilidade prática: ao depurar, o print mostra um livro legível em vez de <__main__.Book object at 0x104...>;
  • Chame a atenção para o que não está aqui: nada de FastAPI. É Python puro. O framework não exigiu classe nenhuma — a escolha é nossa, de modelagem.
Para a turma: "Se eu digitar {"id": 4, "nmae": "O Hobbit"}, com a chave escrita errada, o dicionário reclama? E Book(id=4, nmae="O Hobbit")?" (o dicionário aceita calado e o erro só aparece muito depois; a classe recusa na hora, com TypeError apontando o argumento inesperado)

Passo 2 — a coleção vira uma lista de objetos

Por quê: com o molde pronto, a "tabela" de livros deixa de ser uma lista de dicionários.

Troque a lista books por objetos:

books = [
    Book(id=1, name="Dom Casmurro"),
    Book(id=2, name="O Hobbit"),
    Book(id=3, name="Clean Code"),
]

Diga em voz alta o que isso vai virar: a classe vira tabela, cada objeto vira uma linha, a lista vira o resultado de um SELECT. É literalmente o mapeamento que a aula 04 automatiza com o ORM.

As duas rotas de leitura precisam acompanhar: onde havia chave de dicionário, agora há atributo de objeto.

@app.get("/api/books")
def list_books(name: str = ""):
    if name == "":
        return books
    return [book for book in books if name.lower() in book.name.lower()]


@app.get("/api/books/{book_id}")
def read_book(book_id: int):
    for book in books:
        if book.id == book_id:
            return book
    raise HTTPException(status_code=404, detail="Book not found")

Recarregue /api/books no navegador. Pare nesse ponto e cobre a estranheza: não devolvemos dicionários, devolvemos objetos Book — e mesmo assim saiu JSON, sem escrevermos uma linha de conversão. O FastAPI, ao não reconhecer o tipo, inspeciona os atributos da instância e monta o JSON a partir deles. Funciona — mas é o framework inferindo o formato, não um contrato que declaramos. Enquanto todo atributo do objeto puder ser publicado, a inferência acerta; é quando o objeto passa a guardar algo que não deve sair que ela deixa de servir.

Passo 3 — o POST passa a criar um objeto

Por quê: se a coleção guarda objetos, a rota que cria precisa produzir um objeto. E é aqui que se vê a fronteira do sistema: o dicionário cru do cliente entra, mas não circula lá dentro.

@app.post("/api/books", status_code=201)
def create_book(book: dict):
    new_book = Book(id=len(books) + 1, name=book["name"])
    books.append(new_book)
    return new_book
  • Insista na assimetria: entra dicionário, sai Book. O dado do cliente só vira objeto nosso ao passar pelo Book(...); dentro do sistema, circulam apenas Books;
  • O parâmetro continua book: dict — cru, sem validação. Envie de novo um POST com corpo {} pelo Swagger: 500, o mesmo KeyError da aula 02. Deixe explícito o limite do que acabamos de fazer: a classe protege o que já está dentro do sistema, mas não vigia a porta de entrada. Validar é trabalho da borda, e a borda ainda está aberta.

Passo 4 — a rota que faltava: DELETE /api/books/{book_id}

Por quê: o recurso sabe nascer e ser lido, mas não sabe morrer. E a remoção traz um status code que a turma ainda não viu.

@app.delete("/api/books/{book_id}", status_code=204)
def delete_book(book_id: int):
    for book in books:
        if book.id == book_id:
            books.remove(book)
            return
    raise HTTPException(status_code=404, detail="Book not found")
  • 204 No Content: a operação teve sucesso e não há o que devolver — apagamos o livro, não faria sentido mandá-lo de volta;
  • O return sem valor não é descuido: o 204 proíbe corpo na resposta;
  • Não achou? O mesmo 404 do GET por id. A resposta para "esse recurso não existe" não muda com o verbo.

Compare as duas respostas cruas no terminal, lado a lado:

Mac e Windows (iguais) 
curl -i http://127.0.0.1:8000/api/books/2
curl -i -X DELETE http://127.0.0.1:8000/api/books/1
GET /api/books/2           DELETE /api/books/1
HTTP/1.1 200 OK            HTTP/1.1 204 No Content
server: uvicorn            server: uvicorn
content-length: 26         (não existe)

{"id":2,...}               (nada)

O 200 informa content-length; o 204 não traz esse header — não há corpo para medir, e a resposta acaba na linha em branco. Se algum aluno reparar que o 204 ainda vem com content-type: application/json, anunciando um corpo que não existe: é uma sobra do FastAPI, inofensiva e fora do nosso controle — bom lembrete de que framework também tem canto mal varrido.

Repita o mesmo DELETE: o segundo devolve 404. Registre a observação sem batizá-la ainda — o efeito no servidor é o mesmo das duas vezes, só o status muda. A teoria de daqui a pouco dá nome a isso.

Passo 5 — a dívida da aula 02 vence: de onde vem o próximo id

Por quê: com o DELETE no ar, a pergunta que ficou no quadro deixa de ser hipótese. Provoque a falha em sala, anunciando antes que vai quebrar.

Salve o main.py (o --reload reinicia e a lista volta aos três livros — memória morre com o processo, lição da aula 02). Depois, pelo Swagger:

  1. DELETE /api/books/2 → 204. Restam os ids 1 e 3, e len(books) agora é 2;
  2. POST /api/books com {"name": "Refactoring"} → o id novo é len(books) + 1 = 3… que já existe;
  3. GET /api/books → dois livros com id 3.

Mostre então o estrago, que é pior do que o id repetido:

  • GET /api/books/3 devolve "Clean Code" — o laço para no primeiro que casa. O livro recém-criado é inalcançável;
  • DELETE /api/books/3 apagaria "Clean Code", não o livro novo. O cliente pede para remover um e a API remove outro.
Para a turma: "O id serve para identificar. Se dois livros têm o mesmo id, o que exatamente a nossa API perdeu?" (a resposta que interessa: a capacidade de se referir a um recurso — sem identidade única não há GET, PUT nem DELETE confiáveis)

A correção: o próximo id não pode depender do tamanho da lista, e sim do último id existente nela. Logo abaixo da lista books, crie a função:

def next_book_id():
    if not books:
        return 1
    return books[-1].id + 1

E use-a no POST:

@app.post("/api/books", status_code=201)
def create_book(book: dict):
    new_book = Book(id=next_book_id(), name=book["name"])
    books.append(new_book)
    return new_book
  • books[-1] é o último elemento da lista — como cada livro novo entra no fim, o último é sempre o de maior id;
  • O caso da lista vazia é tratado primeiro e de propósito: sem ele, books[-1] levantaria IndexError ao criar o primeiro livro depois de apagar todos. Numeração recomeça em 1;
  • Repita a sequência que quebrou: apague o id 2, crie outro livro — nasce com id 4. Sem colisão.
Honestidade sobre o limite desta regra. Faça também o caso contrário, ao vivo: apague o último livro (DELETE /api/books/3) e crie um novo. Ele nasce com id 3 — o id do livro que acabou de sair. Não há colisão, porque o antigo não existe mais, mas há reaproveitamento: um cliente que tivesse guardado o endereço /api/books/3 passaria a receber um livro diferente do que pediu, sem nenhum erro. É a diferença entre um id que só cresce e um id calculado a partir do estado atual. Anote no quadro como dívida: na aula 04 quem escolhe o id é o banco, com AUTO_INCREMENT, um contador que nunca reaproveita — e é por isso que ele existe.

10 min Teoria [T-3] — o conceito de API

Pontos a explicar:

  • Origem do termo: a primeira ocorrência registrada de application program interface na literatura técnica está em "Data structures and techniques for remote computer graphics", de Ira W. Cotton e Frank S. Greatorex Jr., apresentado na AFIPS Fall Joint Computer Conference de 1968. O problema deles é o mesmo que temos aqui: um programa em uma máquina precisava usar recursos de outra, e era necessário descrever o que podia ser pedido sem descrever como era feito;
  • Fundamento conceitual: David L. Parnas, em "On the Criteria To Be Used in Decomposing Systems into Modules" (Communications of the ACM, v. 15, n. 12, 1972), estabelece o princípio da ocultação de informação: cada módulo esconde uma decisão de projeto e expõe apenas a interface pela qual os outros o utilizam. É o mesmo encapsulamento da aula 01.2 — a API é essa interface, publicada e assumida como compromisso;
  • Definição de trabalho: uma API é o contrato que um software oferece para ser usado por outro software — quais operações existem, o que cada uma exige e o que devolve —, deliberadamente silencioso sobre a implementação;
  • Nem toda API é web. A turma já usou várias hoje: books.append(...) é a API da list; open(...) é a API de arquivos da biblioteca padrão; @app.get(...) é a API do próprio FastAPI. A web API é o caso particular em que o contrato é exposto pela rede, sobre HTTP — o consumidor pode estar em outra máquina, escrito em outra linguagem, mantido por outra equipe;
  • Por que isso decide o projeto: na aula 07 o React entra em cena. Ele será outro programa, em outro processo, e tudo o que saberá do backend é a API. Se o contrato mudar sem aviso, a tela quebra. Essa é a razão de, no fim de hoje, o formato da resposta deixar de ser promessa e virar declaração;
  • O contrato legível por máquina: a página /docs da aula 02 não é enfeite. O FastAPI publica em /openapi.json uma descrição formal do contrato no padrão OpenAPI — criado como Swagger por Tony Tam em 2011 e doado em 2015 à Linux Foundation, onde foi renomeado. O Swagger UI é apenas um leitor desse arquivo. Abra /openapi.json no navegador e mostre o JSON bruto por trás da página bonita.

Analogia sugerida: a tomada elétrica. O contrato são a forma dos pinos e a tensão nominal; quem fabrica o aparelho não sabe nada sobre a usina, a linha de transmissão ou a subestação — e não precisa. Trocar a usina não quebra o aparelho; trocar o formato da tomada quebra todos eles de uma vez.

Para a turma: "Que APIs vocês já usaram hoje sem chamar de API?"
Para a turma: "Se eu renomear o campo name para title na resposta, o que acontece com quem consome a API?" (quebram todos os clientes ao mesmo tempo — mudança de contrato é evento grave, e é por isso que ele precisa estar declarado em algum lugar)

15 min Teoria [T-3] — anatomia de uma URI

Pontos a explicar: na aula 02 prometemos a anatomia completa. Comece pela definição da RFC 3986: "uma URI (Uniform Resource Identifier) é uma sequência compacta de caracteres que identifica um recurso abstrato ou físico". O conceito foi proposto por Tim Berners-Lee no projeto original da web; a sintaxe genérica em vigor foi formalizada na RFC 3986 (Berners-Lee, Fielding e Masinter, 2005). O propósito é dar à rede uma forma uniforme de identificar qualquer recurso, independente de protocolo ou formato. Disseque no quadro uma URL nossa:

http://127.0.0.1:8000/api/books?name=hobbit
└─┬─┘  └───┬───┘ └┬─┘└────┬────┘└────┬─────┘
esquema   host  porta   caminho    query

E uma completa, com fragmento:

https://developer.mozilla.org:443/pt-BR/docs/Web/HTTP#recursos
└─┬──┘  └────────┬─────────┘└┬─┘└─────────┬────────┘└───┬───┘
esquema         host       porta       caminho      fragmento
  • Esquema — o protocolo da conversa: http, https (HTTP sobre conexão cifrada), mas também mailto, ftp. Define como falar com o servidor;
  • Host — o nome (ou IP) da máquina; é o que o DNS da aula 02 traduz;
  • Porta — o programa dentro da máquina. Cada esquema tem porta padrão (80 para http, 443 para https) — por isso ela quase nunca aparece; a nossa :8000 aparece justamente por não ser a padrão;
  • Caminho (path) — hierárquico, como pastas: identifica o recurso dentro do servidor;
  • Query — os pares chave=valor da aula 02: ajustam o pedido sem mudar o recurso pedido;
  • Fragmento — a âncora depois do #: aponta para uma parte dentro do documento. Detalhe importante: o navegador nunca envia o fragmento ao servidor — é uso local.

URI e URL: URL é a URI que, além de identificar, informa onde e como obter o recurso. Toda URL é uma URI; na prática da web os termos quase se confundem — o que importa é saber ler as partes.

Analogia sugerida: um endereço de encomenda completo. O esquema é o serviço de entrega; host e porta são o prédio e o apartamento (a dupla máquina + programa da aula 02); o caminho é o destinatário dentro do apartamento; a query são as instruções extras no pacote ("deixar na portaria"); e o fragmento é um bilhete que só o destinatário lê — o transportador nem fica sabendo que existe.

Para a turma: "Abram a aba Network e acessem uma URL com #alguma-coisa. Cadê o fragmento na requisição?" (não está — nunca é enviado)
Para a turma: "Por que https://google.com funciona sem porta e o nosso servidor exige o :8000?"

20 min Teoria [T-3] — REST: o estilo que organiza a web

Pontos a explicar:

  • Origem: REST (REpresentational State Transfer) foi definido por Roy T. Fielding no capítulo 5 de sua tese de doutorado, Architectural Styles and the Design of Network-based Software Architectures (University of California, Irvine, 2000). Fielding foi coautor da especificação do HTTP/1.1 e cofundador do projeto Apache — a tese identifica e nomeia os princípios arquiteturais que permitiram à web escalar;
  • Definição (Fielding): REST é um estilo arquitetural para sistemas de hipermídia distribuídos. Não é biblioteca nem framework: é um conjunto de restrições que, respeitadas, conferem ao sistema as propriedades da web — escalabilidade e evolução independente das partes;
  • As seis restrições: cliente–servidor (aula 01), stateless, cache, interface uniforme, sistema em camadas e código sob demanda (opcional). O curso aprofunda as duas em destaque; as demais ficam na menção;
  • Recurso — na formulação de Fielding, "qualquer informação que possa ser nomeada": um livro, a coleção de livros, um usuário. Cada recurso é identificado por uma URI — por isso a anatomia veio primeiro;
  • Representação — o que viaja na resposta não é o recurso, é uma representação dele num formato. Aponte para a tela: na memória do servidor o recurso é um objeto Book; o que sai pela rede é JSON. O mesmo recurso poderia viajar como XML, HTML ou PDF sem deixar de ser o mesmo recurso;
  • Interface uniforme — em vez de inventar um nome de operação para cada caso (/getBooks, /criarLivro, /apagar_livro.php), REST usa poucos verbos padronizados do HTTP sobre muitos substantivos (as URIs);
  • Stateless — cada requisição carrega toda a informação necessária para ser atendida; o servidor não guarda estado de sessão entre requisições. Fielding aponta os ganhos: visibilidade, confiabilidade e escalabilidade — e é por isso que, na aula de JWT, o token precisará viajar em cada requisição;
  • Honestidade intelectual: a tese de Fielding vai além (hipermídia, HATEOAS); o que o mercado chama de "API REST" é o núcleo recursos + verbos + status codes — e é o que usaremos.

Os verbos e o CRUD — a tabela para deixar no quadro a aula inteira. A última coluna mostra que a turma já implementou três das quatro linhas antes de conhecer a tabela:

Operação (CRUD)Verbo HTTPNa coleção /api/booksNo item /api/books/{book_id}Status típicoNo projeto
CreatePOSTcria um livro novo—201 Createdaula 02
ReadGETlista os livrosum livro específico200 OKaula 02

Introduza agora o vocabulário formal da RFC 9110 (Fielding e Reschke, 2022), que substituiu as RFCs 723x: um método é seguro quando não modifica o recurso (GET), e idempotente quando repeti-lo produz o mesmo efeito que executá-lo uma única vez. GET, PUT e DELETE são idempotentes; POST não é. Retome a observação do Passo 4: o segundo DELETE devolveu 404, mas o estado do servidor ficou idêntico — é exatamente isso que idempotência significa, e a mudança de status não a viola.

Mencione o PATCH (atualização parcial) sem usá-lo: nosso recurso tem um campo só, e o PUT com schema pequeno já resolve. PATCH volta como menção quando o Book tiver mais campos.

Boas práticas de URI (as que o projeto segue, registradas no ADR-0002):

  • URIs têm substantivos, não verbos — o verbo já vai no método HTTP. GET /api/books, nunca GET /api/getBooks;
  • Coleção no plural (/books), item = coleção + identificador (/books/3);
  • O mesmo parâmetro de path usa o mesmo nome em todas as rotas — sempre book_id, nunca id numa rota e book_id noutra;
  • Verbo certo para o efeito certo: GET nunca modifica nada. Navegadores, proxies e robôs assumem que GET é seguro para repetir.

Analogia sugerida: continuando o restaurante das aulas 01 e 02 — o cardápio é cheio de pratos (substantivos, recursos), mas os gestos do salão são poucos e padronizados: pedir, consultar, trocar, cancelar (verbos). Um prato novo entra no cardápio sem exigir gesto novo. É isso que "interface uniforme" quer dizer.

Para a turma: "Por que GET /api/books/delete/3 seria uma péssima ideia?" (verbo na URI; e um GET que apaga — um robô de indexação ou o preload do navegador poderia apagar livros sem que ninguém pedisse)
Para a turma: "Chamar o mesmo PUT duas vezes seguidas dá no mesmo? E o mesmo POST duas vezes?" (PUT é idempotente — substituir duas vezes pelo mesmo valor não muda nada; POST cria dois livros)

15 min Live-coding — validação na borda com Pydantic

A teoria falou em contrato. Falta cumpri-lo no ponto em que ele é violado hoje: o que a API aceita do cliente.

Passo 6 — o schema de entrada: fechando a porta

Por quê: é a dívida do Passo 3 e da aula 02. Queremos declarar a forma dos dados que aceitamos e deixar o framework validá-los antes de a nossa função rodar — exatamente como já acontece com book_id: int, agora para o corpo da requisição.

Apresente a biblioteca antes de usá-la: o Pydantic (criado por Samuel Colvin em 2017) é uma biblioteca de validação de dados que usa as anotações de tipo do Python como fonte das regras. É dela que o FastAPI tira toda a validação que vimos até aqui, e já está instalada — veio como dependência do FastAPI (confira na Tabela de Dependências do README).

Reproduza o defeito uma última vez, para que a correção tenha destinatário: no Swagger, POST /api/books com corpo {} → 500 Internal Server Error. Pela tabela de status codes da aula 02, 5xx é culpa do servidor — mas quem errou foi o cliente, e ele nem fica sabendo o que mandou errado.

Ajuste o import e declare o schema de entrada logo depois da classe Book:

from fastapi import FastAPI, HTTPException
from pydantic import BaseModel
class BookCreate(BaseModel):
    name: str

Um schema é uma classe que declara campos e tipos. BookCreate diz: "para criar um livro, exijo um name do tipo string". Agora use-o no POST, no lugar do dicionário:

@app.post("/api/books", status_code=201)
def create_book(book: BookCreate):
    new_book = Book(id=next_book_id(), name=book.name)
    books.append(new_book)
    return new_book

Duas mudanças: o parâmetro é BookCreate (o FastAPI valida o corpo contra o schema antes de chamar a função) e o acesso vira book.name — atributo, não chave.

Repita o POST com corpo {}: agora 422, e a resposta aponta o campo que falta ("Field required" em body → name). O erro mudou de família — 4xx, culpa do cliente, com diagnóstico de graça. Teste também {"name": 123} (422, "Input should be a valid string") e {"name": "O Senhor dos Anéis"} (201).

Vale explicitar o desenho que se formou: duas classes com papéis distintos. Book é o modelo do domínio — o que o sistema guarda. BookCreate é o contrato de entrada — o que o cliente pode mandar. Repare que o cliente não manda o id: quem o escolhe é o servidor, e por isso ele não aparece no schema de entrada.

Feche o passo mostrando a assimetria que sobrou. Abra /openapi.json, ache a resposta 200 de GET /api/books e leia em voz alta: "schema": {}. A entrada tem forma declarada; a saída, não — o FastAPI continua montando o JSON por inspeção dos atributos, como visto no Passo 2. Registre no quadro que a API só declara metade do próprio contrato, e siga: enquanto tudo o que o objeto tem pode ser publicado, declarar a saída seria repetir a classe Book em outro lugar, sem alterar uma única resposta. O dia em que o modelo guardar um campo que não pode sair, essa declaração deixa de ser redundante e passa a ser o filtro que impede o vazamento.

Passo 7 — a linha que falta no CRUD: PUT /api/books/{book_id}

Por quê: é o U da tabela, a única operação ainda ausente. E é a rota onde os dois lugares da teoria aparecem juntos: o id viaja no caminho (identifica o recurso), os dados novos viajam no corpo (a nova representação).

@app.put("/api/books/{book_id}")
def update_book(book_id: int, book: BookCreate):
    for stored_book in books:
        if stored_book.id == book_id:
            stored_book.name = book.name
            return stored_book
    raise HTTPException(status_code=404, detail="Book not found")
  • O corpo reusa BookCreate: atualizar exige os mesmos campos que criar, e o id nunca vem no corpo — ele já está na URI;
  • stored_book.name = ... — o objeto é mutável: trocamos o atributo no lugar, sem recriar nem reinserir na lista;
  • Não achou? O mesmo 404 do GET e do DELETE.

Teste no Swagger: renomeie o livro 1 para {"name": "Dom Casmurro (relido)"} → 200 com o livro atualizado; PUT no id 99 → 404. Execute o mesmo PUT duas vezes: a segunda não muda nada — a idempotência da teoria, ao vivo, em contraste com o POST, que criaria dois livros.

10 min Exercício em sala

Individual, com o que acabou de ser visto — o recurso Books vai ganhar um campo novo, author, opcional, com padrão "":

  1. Adicione o campo às duas classes, respeitando o papel de cada uma;

  3. Teste no Swagger: um POST com author, um POST sem author (o padrão assume) e o GET da lista — os três livros iniciais devem aparecer com author vazio, sem que a lista books seja alterada.

Gabarito (para o professor):

class Book:
    def __init__(self, id: int, name: str, author: str = ""):
        self.id = id
        self.name = name
        self.author = author


class BookCreate(BaseModel):
    name: str
    author: str = ""

No create_book, a construção do objeto ganha o argumento: Book(id=next_book_id(), name=book.name, author=book.author); no update_book, uma linha a mais: stored_book.author = book.author. O valor padrão no __init__ é o que permite que os três livros iniciais continuem sendo criados sem author.

Circule pela sala: os erros clássicos serão adicionar o campo em apenas uma das classes (o POST aceita mas a resposta não mostra — ou vice-versa) e esquecer de passar book.author no create_book, caso em que o campo entra, é validado e descartado em silêncio.

Encerre o exercício com a pergunta: "quantos lugares vocês tiveram que editar para acrescentar um campo?" (dois: o modelo e o schema de entrada) — e registre a observação, que vale para qualquer projeto: um campo do domínio se espalha por tantos arquivos quantas forem as fronteiras que ele atravessa.

5 min Fechamento

  • Síntese: uma API é o contrato que um software publica para ser usado por outro, ocultando a implementação (Parnas, 1972); uma URI tem esquema, host, porta, caminho, query e fragmento, e identifica um recurso (RFC 3986); REST (Fielding, 2000) usa poucos verbos padronizados sobre muitos substantivos, casando com o CRUD, e não guarda estado entre requisições; o recurso Book virou objeto, ganhou o ciclo completo — criar, ler, atualizar e remover — e uma regra de id que não colide; e o Pydantic passou a validar a entrada na borda, transformando o nosso 500 em 422 — enquanto a saída continua inferida pelo framework, contrato ainda por declarar.
  • Gancho para a aula 04: "O CRUD está completo e o contrato está declarado, mas os dados continuam voláteis: a cada reinício do servidor, tudo se perde — e o nosso id é calculado na unha, ainda por cima reaproveitando o número de um livro removido. Na próxima aula os dados ganham persistência: banco de dados MySQL, o ORM SQLModel no papel de tradutor entre Python e SQL, o AUTO_INCREMENT que resolve o id de vez, e o primeiro recurso persistente do mapa que desenhamos hoje — o User, com a rota de signup."
