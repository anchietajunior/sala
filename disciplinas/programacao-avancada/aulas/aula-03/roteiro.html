Aula 03 — APIs REST e URIs

Duração: ~2h  ·  Branch: aula-03-apis-rest-e-uris

Temas teóricos: REST, verbos HTTP e a estrutura de uma URI [T-3]

Objetivos — ao final, o aluno consegue:

  • Nomear as partes de uma URI (esquema, host, porta, caminho, query, fragmento) em qualquer endereço real;

  • Desenhar as URIs REST de um recurso novo, escolhendo verbo e status code adequados;
  • Validar entrada e saída de rotas FastAPI com schemas Pydantic e response_model, explicando por que o 422 substitui o 500;

15 min Teoria [T-3] — anatomia de uma URI

Pontos a explicar: na aula 02 prometemos a anatomia completa. Comece pela definição da RFC 3986: "uma URI (Uniform Resource Identifier) é uma sequência compacta de caracteres que identifica um recurso abstrato ou físico". O conceito foi proposto por Tim Berners-Lee no projeto original da web; a sintaxe genérica atual foi formalizada na RFC 3986 (Berners-Lee, Fielding e Masinter, 2005). O propósito é dar à rede uma forma uniforme de identificar qualquer recurso, independente de protocolo ou formato. Disseque no quadro uma URL nossa:

http://127.0.0.1:8000/api/books?name=hobbit
└─┬─┘  └───┬───┘ └┬─┘└────┬────┘└────┬─────┘
esquema   host  porta   caminho    query

E uma completa, com fragmento:

https://developer.mozilla.org:443/pt-BR/docs/Web/HTTP#recursos
└─┬──┘  └────────┬─────────┘└┬─┘└─────────┬────────┘└───┬───┘
esquema         host       porta       caminho      fragmento
  • Esquema — o "idioma" da conversa: http, https (HTTP sobre conexão cifrada), mas também mailto, ftp. Define como falar com o servidor;
  • Host — o nome (ou IP) da máquina; é o que o DNS da aula 02 traduz;
  • Porta — o programa dentro da máquina. Cada esquema tem porta padrão (80 para http, 443 para https) — por isso ela quase nunca aparece; a nossa :8000 aparece porque não é a padrão;
  • Caminho (path) — hierárquico, como pastas: identifica o recurso dentro do servidor;
  • Query — os pares chave=valor da aula 02: ajustam o pedido;
  • Fragmento — a âncora depois do #: aponta para uma parte dentro do documento. Detalhe importante: o navegador nunca envia o fragmento ao servidor — é uso local.

URI vs URL: URL é a URI que, além de identificar, diz onde e como buscar o recurso. Toda URL é uma URI; na prática da web, os termos quase se confundem — o importante é saber ler as partes.

Analogia sugerida: um endereço de encomenda completo — o esquema é o serviço de entrega (Sedex, transportadora), host + porta são o prédio e o apartamento (a dupla máquina + programa da aula 02), o caminho é o destinatário dentro do apartamento, a query são as instruções extras no pacote ("deixar na portaria"), e o fragmento é um post-it que só o destinatário lê — o correio nem fica sabendo.

Para a turma: "Abram a aba Network e acessem uma URL com #alguma-coisa. Cadê o fragmento na requisição?" (não está — nunca é enviado)
Para a turma: "Por que https://google.com funciona sem porta e o nosso servidor exige o :8000?"

20 min Teoria [T-3] — REST: o estilo que organiza a web

Pontos a explicar:

  • Origem: REST (REpresentational State Transfer) foi definido por Roy T. Fielding no capítulo 5 de sua tese de doutorado (UC Irvine, 2000). Fielding foi coautor da especificação do HTTP/1.1 e cofundador do projeto Apache — a tese identifica os princípios arquiteturais que permitiram à web escalar;
  • Definição (Fielding): REST é um estilo arquitetural para sistemas de hipermídia distribuídos. Não é biblioteca nem framework: é um conjunto de restrições (constraints) que, respeitadas, conferem ao sistema as propriedades da web — escalabilidade e evolução independente das partes;
  • As seis restrições: cliente–servidor (aula 01), stateless, cache, interface uniforme, sistema em camadas e código sob demanda (opcional). O curso aprofunda as duas em destaque; as demais ficam na menção;
  • Recurso — na formulação de Fielding, "qualquer informação que possa ser nomeada": um livro, a coleção de livros, um usuário. Cada recurso é identificado por uma URI (por isso a anatomia veio primeiro);
  • Representação — o que viaja na resposta não é o recurso, é uma representação dele num formato: para nossa API, JSON. O mesmo recurso poderia viajar como HTML, XML, PDF;
  • Interface uniforme (verbos) — em vez de inventar um nome de operação para cada caso (/getBooks, /criarLivro, /apagar_livro.php), REST usa poucos verbos padronizados do HTTP sobre muitos substantivos (as URIs);
  • Stateless — cada requisição contém toda a informação necessária para ser atendida; o servidor não guarda estado de sessão entre requisições. Fielding aponta os ganhos: visibilidade, confiabilidade e escalabilidade — e é por isso que, na aula de JWT, o token de autenticação precisará viajar em cada requisição;
  • Honestidade intelectual: a tese de Fielding vai além (hipermídia, HATEOAS); o que o mercado chama de "API REST" é o núcleo recursos + verbos + status codes — e é o que usaremos.

Os verbos e o CRUD — a tabela para deixar no quadro a aula inteira:

Operação (CRUD)Verbo HTTPNa coleção /api/booksNo item /api/books/{book_id}Status típico
CreatePOSTcria um livro novo—201 Created
ReadGETlista os livrosum livro específico200 OK
UpdatePUT—substitui os dados do livro200 OK
DeleteDELETE—remove o livro204 No Content

Introduza o vocabulário formal da RFC 9110: um método é seguro quando não modifica o recurso (GET) e idempotente quando repeti-lo produz o mesmo efeito que executá-lo uma vez (GET, PUT e DELETE são idempotentes; POST não).

Mencione o PATCH (atualização parcial) sem usar: nosso PUT com schema pequeno já resolve; PATCH volta como menção quando o recurso tiver mais campos.

Boas práticas de URI (as que o projeto segue, registradas no ADR-0002):

  • URIs têm substantivos, não verbos — o verbo já vai no método HTTP. GET /api/books, nunca GET /api/getBooks;
  • Coleção no plural (/books), item = coleção + id (/books/3);
  • O mesmo parâmetro de path usa o mesmo nome em todas as rotas — sempre book_id, nunca id numa rota e book_id noutra;
  • Verbo certo para o efeito certo: GET nunca modifica nada. Navegadores e robôs assumem que GET é seguro para repetir.

Analogia sugerida: continuando o restaurante das aulas 01 e 02 — o cardápio é cheio de pratos (substantivos, recursos), mas os gestos do salão são poucos e padronizados: pedir, consultar, trocar, cancelar (verbos). Qualquer prato novo entra no cardápio sem inventar gesto novo — é a interface uniforme.

Para a turma: "Por que GET /api/books/delete/3 seria uma péssima ideia?" (verbo na URI; e um GET que apaga — um robô de indexação ou o preload do navegador poderia apagar livros "sem querer")
Para a turma: "Chamar o mesmo PUT duas vezes seguidas dá no mesmo? E o mesmo POST duas vezes?" (PUT é idempotente — substituir duas vezes pelo mesmo valor não muda nada; POST cria dois livros)

40 min Live-coding — Pydantic e o CRUD completo

Passo 1 — reproduzir o problema: o 500 do dict cru

Por quê: ver o problema antes da solução. É o gancho que ficou armado na aula 02.

No Swagger (/docs), POST /api/books → Try it out → corpo {} → Execute: 500 Internal Server Error. O cliente mandou dados errados, mas quem quebrou fomos nós (book["name"] explodiu com KeyError). Pela tabela da aula 02, 5xx é culpa do servidor — e o cliente nem fica sabendo o que mandou errado.

Passo 2 — o primeiro schema: validação na borda

Por quê: declarar a forma dos dados que aceitamos e deixar o framework validar antes de a nossa função rodar — como já acontece com book_id: int, agora para o corpo.

Apresente a biblioteca: o Pydantic (criado por Samuel Colvin, 2017) é uma biblioteca de validação de dados que usa as anotações de tipo do Python como fonte das regras — é dela que o FastAPI tira toda a validação que vimos até aqui. Já está instalado: veio como dependência do FastAPI (confira na Tabela de Dependências do README). Troque a primeira linha do main.py e adicione o schema logo depois de app = FastAPI():

from fastapi import FastAPI, HTTPException
from pydantic import BaseModel

app = FastAPI()


class BookCreate(BaseModel):
    name: str

Um schema é uma classe que declara os campos e seus tipos. BookCreate diz: "para criar um livro, exijo um name do tipo string". Agora use-o no POST, no lugar do dict:

@app.post("/api/books", status_code=201)
def create_book(book: BookCreate):
    new_book = {"id": len(books) + 1, "name": book.name}
    books.append(new_book)
    return new_book

Duas mudanças: o parâmetro é BookCreate (o FastAPI valida o corpo contra o schema antes de chamar a função) e o acesso vira book.name — atributo de objeto, não chave de dicionário.

Repita o POST com corpo {}: agora 422, com a resposta apontando o campo que falta ("Field required" em body → name). O erro mudou de família — 4xx, culpa do cliente, com diagnóstico de graça. Teste também {"name": 123} e {"name": "O Senhor dos Anéis"}.

Passo 3 — schema de saída: response_model

Por quê: a entrada agora tem forma declarada; a saída ainda é promessa. Declarar o formato da resposta valida o que devolvemos e documenta a API de verdade (decisão do ADR-0002).

Adicione o schema do livro completo — o que sai tem id; o que entra não (quem escolhe o id é o servidor, e é por isso que são dois schemas):

class Book(BaseModel):
    id: int
    name: str

E declare o response_model nas três rotas de books:

@app.get("/api/books", response_model=list[Book])
def list_books(name: str = ""):
    ...

@app.get("/api/books/{book_id}", response_model=Book)
def read_book(book_id: int):
    ...

@app.post("/api/books", response_model=Book, status_code=201)
def create_book(book: BookCreate):
    ...

(Os corpos das funções não mudam — só a linha do decorator.) Abra o /docs: cada rota agora exibe o formato exato da resposta, com exemplo; os schemas Book e BookCreate aparecem na seção Schemas no fim da página. A rota /health fica como está — resposta fixa de uma chave não precisa de schema.

Passo 4 — Update: PUT /api/books/{book_id}

Por quê: a linha U da tabela CRUD. O id viaja no caminho (identifica o recurso); os dados novos viajam no corpo (a nova representação) — os dois lugares da teoria, juntos na mesma rota.

@app.put("/api/books/{book_id}", response_model=Book)
def update_book(book_id: int, book: BookCreate):
    for stored_book in books:
        if stored_book["id"] == book_id:
            stored_book["name"] = book.name
            return stored_book
    raise HTTPException(status_code=404, detail="Book not found")

Repare: o corpo reusa BookCreate — atualizar pede os mesmos campos que criar (o id nunca vem no corpo). Teste no Swagger: renomeie o livro 1 para {"name": "Dom Casmurro (relido)"} → 200 com o livro novo; PUT no id 99 → 404. Execute o mesmo PUT duas vezes: a segunda não muda nada — a idempotência da teoria, ao vivo.

Passo 5 — Delete: DELETE /api/books/{book_id}

Por quê: a última linha da tabela. E um status novo: 204 No Content — deu certo e não há o que devolver (o livro não existe mais).

@app.delete("/api/books/{book_id}", status_code=204)
def delete_book(book_id: int):
    for book in books:
        if book["id"] == book_id:
            books.remove(book)
            return
    raise HTTPException(status_code=404, detail="Book not found")

Sem response_model e com return vazio: resposta 204 não carrega corpo. Teste: DELETE no 2 → 204; GET /api/books → O Hobbit sumiu; DELETE no 2 de novo → 404 (já não existe — apagar duas vezes não é erro do servidor, é pedido por algo que não está lá).

Passo 6 — a resposta da aula 02: o bug do len(books) + 1

Por quê: com DELETE no ar, a pergunta que ficou aberta finalmente quebra de verdade — e em sala.

Salve o main.py (o --reload reinicia e a lista volta aos três livros — memória morre com o processo, lição da aula 02). Agora a sequência que provoca a colisão, pelo Swagger:

  1. DELETE /api/books/1 → 204. Restaram os ids 2 e 3, e len(books) agora é 2;
  2. POST /api/books com {"name": "Duna"} → o novo id é len(books) + 1 = 3... que já existe;
  3. GET /api/books: dois livros com id 3. GET /api/books/3 devolve só o primeiro que encontrar — Duna virou inalcançável.

A correção: o próximo id não pode depender do tamanho da lista, e sim de um contador monotônico — que só cresce. Logo depois da lista books, crie:

next_book_id = 4

E ajuste o POST:

@app.post("/api/books", response_model=Book, status_code=201)
def create_book(book: BookCreate):
    global next_book_id
    new_book = {"id": next_book_id, "name": book.name}
    next_book_id += 1
    books.append(new_book)
    return new_book

O global avisa ao Python que a função quer reatribuir a variável do módulo (sem ele, next_book_id += 1 criaria uma variável local e falharia). Repita a sequência: agora Duna nasce com id 4 — id de livro removido nunca é reaproveitado.

Gancho para a aula 04: esse contador é a versão artesanal do auto-increment, que o banco de dados fará por nós — junto com resolver o problema maior: os dados continuam morrendo a cada restart.

Checkpoint — como saber que funcionou:
  • POST com corpo {} devolve 422 apontando o campo name — o 500 da aula 02 não existe mais;
  • /docs mostra o formato de resposta das rotas de books e os schemas Book e BookCreate na seção Schemas;
  • PUT renomeia um livro (200) e devolve 404 para id inexistente; o mesmo PUT duas vezes dá o mesmo resultado;

15 min Exercício em sala

Individual, com o que acabou de ser visto — o recurso Books vai ganhar um campo novo:

  1. Adicione o campo author (string, opcional, padrão "") aos dois schemas;
  2. Ajuste create_book e update_book para gravar o novo campo;
  3. Teste no Swagger: um POST com author, um POST sem author (o padrão assume), e o GET da lista — os três livros iniciais devem aparecer com author vazio, sem mexer na lista (quem preenche é o response_model, pelo valor padrão do schema).

Gabarito (para o professor):

class BookCreate(BaseModel):
    name: str
    author: str = ""


class Book(BaseModel):
    id: int
    name: str
    author: str = ""

No create_book, o dicionário novo ganha a chave: {"id": next_book_id, "name": book.name, "author": book.author}; no update_book, uma linha a mais: stored_book["author"] = book.author.

Circule pela sala: os erros clássicos serão adicionar o campo só num dos schemas (o POST aceita mas a resposta não mostra — ou vice-versa) e esquecer de copiar book.author no create (o campo entra, valida e é descartado em silêncio).

O exercício é descartável: a branch da disciplina segue sem o campo author — quem quiser guardar a solução, guarde fora do projeto. A aula 04 parte do código sem ele.

5 min Fechamento

  • Síntese: uma URI tem esquema, host, porta, caminho, query e fragmento — e identifica um recurso; REST usa poucos verbos padronizados (GET, POST, PUT, DELETE) sobre muitos substantivos, casando com o CRUD; o servidor não guarda memória entre requisições (stateless); Pydantic valida na borda — entrada com schema no parâmetro, saída com response_model — e transformou nosso 500 em 422; e o CRUD de Books está completo, com ids que sobrevivem a remoções.
