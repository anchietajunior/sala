Aula 06 - Frontend com React e o consumo da API

Duração: ~2h10 (densa - administre o relógio nos checkpoints; se faltar tempo, o exercício vira tarefa)  ·  Branch: aula-06-frontend-com-react-e-o-consumo-da-api

Temas teóricos: aplicações de página única, componentes e estado (React); política de mesma origem e CORS; separação de responsabilidades no frontend; bibliotecas de estilo e de componentes; o token no navegador (Bloco 3 - frontend)

Objetivos - ao final, o aluno consegue:

  • Estender o model Book com pages e current_page e expor o Reading Progress como dado derivado, nunca armazenado;
  • Explicar a política de mesma origem, configurar o CORSMiddleware no FastAPI e verificar com curl a resposta ao preflight;
  • Criar um projeto React com Vite, configurar o Tailwind, explicar o papel de cada ferramenta (Node, npm, Vite, Tailwind) e situar o Tailwind entre as bibliotecas de estilo e de componentes;
  • Explicar o modelo de componentes do React - interface como função do estado - e organizar o código em pages, components e services, com useState, useEffect, props e componentes estilizados reutilizáveis;
  • Consumir a API com fetch: cadastro, login e o CRUD completo de Books - guardando o token no localStorage e enviando-o no header Authorization: Bearer - e demonstrar que a regra de dono continua sendo garantida pela API.

5 min Ponto de partida

Abra o Swagger. A API está completa: cadastro, login e o CRUD de Books autenticado, cada usuário operando só sobre os próprios livros. E o único cliente dela é o Swagger. Peça a um aluno para usar o sistema sem o Swagger: ele precisaria escrever requisições HTTP à mão, copiar o token, montar o header. Nenhum leitor faria isso.

O sistema tem dois problemas, e eles são o assunto de hoje:

  • Não existe interface. O User do glossário é uma pessoa; a API fala JSON. Falta o programa que roda no navegador, monta as telas e conversa com a API em nome dela;
  • Book só tem nome. O glossário define o Reading Progress como a página atual sobre o total de páginas - e a tabela books não guarda nenhum dos dois números. O sistema ainda não rastreia leitura nenhuma.

A aula resolve os dois, nessa ordem: primeiro o backend - as páginas e o progresso nos dados, e a permissão para que um cliente de outra origem leia as respostas -, depois a interface (React) que os exibe.

10 min Teoria - aplicações de página única, React, componentes e estado

Pontos a explicar:

  • Aplicação de página única (SPA): o navegador carrega um documento HTML e, a partir dele, um programa JavaScript que pede dados ao servidor e atualiza a tela sem recarregar a página. A ideia foi nomeada por Jesse James Garrett no ensaio "Ajax: A New Approach to Web Applications" (2005): a comunicação assíncrona entre navegador e servidor deixa de trocar páginas inteiras e passa a trocar dados. A API construída até aqui é exatamente o lado dos dados desse modelo; o que falta é o lado da tela;
  • React: biblioteca criada por Jordan Walke no Facebook, em uso interno desde 2011 e publicada como código aberto na JSConf US de 2013. A documentação oficial a define como "the library for web and native user interfaces" (react.dev). A ideia central é a interface declarativa: o componente descreve como a tela deve ficar para um dado estado; o React calcula o que mudar no DOM quando o estado muda. Em uma fórmula: UI = f(estado);
  • Componente: uma função JavaScript que devolve JSX - a sintaxe parecida com HTML que o Vite compila para chamadas JavaScript. Props são os parâmetros do componente: o pai passa dados e funções para o filho. Estado (useState) é o valor cuja mudança redesenha o componente. Efeito (useEffect) é código que roda depois de desenhar - o lugar de buscar dados quando a tela aparece. Os hooks (useState, useEffect) existem desde o React 16.8 (2019) e são a forma atual de escrever componentes;
  • Ferramentas: Node.js (Ryan Dahl, 2009) executa JavaScript fora do navegador - é o que roda as ferramentas de desenvolvimento; npm gerencia pacotes: package.json é o requirements.txt do Node, package-lock.json fixa as versões, node_modules/ é a venv. Vite (Evan You, 2020) é o servidor de desenvolvimento (entrega os módulos ao navegador e atualiza a tela ao salvar) e a ferramenta de build (empacota tudo em arquivos estáticos para produção);
  • Tailwind CSS (Adam Wathan, 2017): abordagem utility-first - cada classe faz uma coisa (p-2 é padding, rounded é borda arredondada, bg-blue-600 é cor de fundo) e o estilo é composto no próprio JSX. Não há um arquivo CSS por componente; o build inclui apenas as classes efetivamente usadas;
  • Dois servidores: em desenvolvimento, o Vite (porta 5173) entrega o programa; a API (porta 8000) entrega os dados. São origens diferentes - e o navegador impõe uma regra própria a requisições entre origens diferentes, que a API precisa atender antes de a primeira tela chamá-la.
Para a turma: "O que acontece com o DOM quando chamamos setBooks(...)?" (o React reexecuta a função do componente com o estado novo, compara o resultado com o que está na tela e altera apenas o que mudou - o programador nunca toca o DOM)
Para a turma: "Por que o frontend precisa de um servidor próprio, se ele roda no navegador?" (o navegador precisa receber o HTML e o JavaScript de algum lugar; em desenvolvimento o Vite faz isso e ainda recompila ao salvar. Em produção o build vira arquivos estáticos - e a API de dados continua a mesma)

10 min Live-coding 1 - o Book ganha páginas e o Reading Progress

Passo 1 - models.py: duas colunas e um dado derivado

Por quê: o Reading Progress é a página atual sobre o total de páginas. Os dois números são dados do livro; a porcentagem não é - ela se calcula a partir deles.

Em backend/models.py, dê ao Book as colunas e a property:

class Book(Base):
    __tablename__ = "books"

    id: Mapped[int] = mapped_column(primary_key=True)
    name: Mapped[str] = mapped_column(String(255))
    pages: Mapped[int]
    current_page: Mapped[int]
    user_id: Mapped[int] = mapped_column(ForeignKey("users.id"))
    created_at: Mapped[datetime] = mapped_column(server_default=func.now())

    @property
    def progress(self) -> int:
        return round(self.current_page * 100 / self.pages)
  • pages: Mapped[int] sem mapped_column: quando não há nada a configurar, o tipo Python basta - o SQLAlchemy deduz INTEGER NOT NULL. O String(255) do nome precisa do mapped_column porque o banco exige o tamanho;
  • progress é uma property, não uma coluna: é lida como atributo (book.progress) mas calculada a cada leitura. Armazenar a porcentagem criaria um dado que precisaria ser recalculado a cada mudança de current_page - e que estaria errado no instante em que alguém esquecesse. Dado derivado não se armazena. O glossário diz o mesmo: um Book está concluído quando o progresso chega a 100% - não existe um status guardado;
  • round devolve inteiro: 120 de 300 páginas são 40%; 1 de 3 são 33%.

Por quê: o model ganhou colunas e o create_all não altera tabela existente. Dado de aula é descartável.

Mac e Windows (dentro do cliente mysql)

Passo 3 - schemas.py: validar a entrada, publicar o progresso

Por quê: a API passa a receber dois números e a devolver três. A entrada precisa de regras (um livro tem ao menos uma página; ninguém está na página 400 de um livro de 300) e a saída precisa publicar o dado derivado.

Em backend/schemas.py, ajuste o import e os dois schemas do Book:

from pydantic import BaseModel, ConfigDict, EmailStr, Field, model_validator
class BookCreate(BaseModel):
    name: str = Field(min_length=1, max_length=255)
    pages: int = Field(gt=0)
    current_page: int = Field(default=0, ge=0)

    @model_validator(mode="after")
    def check_current_page(self):
        if self.current_page > self.pages:
            raise ValueError("current_page must not exceed pages")
        return self


class BookRead(BaseModel):
    model_config = ConfigDict(from_attributes=True)

    id: int
    name: str
    pages: int
    current_page: int
    progress: int
    user_id: int
  • Field(gt=0) e Field(ge=0): regras de um campo só, como o min_length do nome. current_page tem default=0 - cadastrar um livro é começar a lê-lo;
  • @model_validator(mode="after"): uma regra que envolve dois campos não cabe em um Field. O método roda depois que os campos individuais foram validados, recebe o objeto inteiro e levanta ValueError - que o FastAPI converte em 422 com a mensagem;
  • progress: int no BookRead: com from_attributes=True, o Pydantic lê book.progress como lê book.name - ele não sabe (nem precisa saber) que um é coluna e o outro é property. O contrato de saída publica o dado derivado; o cliente recebe a porcentagem pronta.

Passo 4 - routers/books.py: gravar os campos novos

Por quê: o schema mudou, mas as duas rotas que escrevem ainda só conhecem o nome. Um POST agora falharia com IntegrityError: a coluna pages é NOT NULL e ninguém a preenche.

Em create_book:

    new_book = models.Book(name=book.name, pages=book.pages,
                           current_page=book.current_page, user_id=current_user.id)

Em update_book, os três atributos:

    stored_book.name = book.name
    stored_book.pages = book.pages
    stored_book.current_page = book.current_page

Teste no Swagger, autorizado com o token de um usuário: POST /api/books com {"name": "Dom Casmurro", "pages": 300} → 201 com current_page: 0 e progress: 0. PUT com current_page: 120 → progress: 40. PUT com current_page: 400 → 422, current_page must not exceed pages. Registrar o avanço da leitura é atualizar o livro.

Checkpoint parcial: books recriada com pages e current_page; a resposta da API traz progress calculado; página atual acima do total responde 422.

8 min Teoria - a política de mesma origem e o CORS

Pontos a explicar:

  • Origem é a tripla esquema + host + porta, definida na RFC 6454, "The Web Origin Concept" (Adam Barth, IETF, 2011). http://localhost:5173 (o Vite) e http://127.0.0.1:8000 (a API) são origens diferentes duas vezes: host e porta. Bastaria uma;
  • Política de mesma origem (same-origin policy): introduzida no Netscape Navigator 2.0 (1995), junto com o JavaScript. Um script só pode ler respostas da origem de onde veio. O motivo é proteger o usuário: sem ela, qualquer página aberta em outra aba leria, com os cookies do usuário, as respostas do banco dele. A regra é do navegador, para o navegador;
  • CORS - Cross-Origin Resource Sharing: o mecanismo pelo qual o servidor declara quais origens podem ler suas respostas. Especificado por Anne van Kesteren, foi Recomendação W3C em 2014 e hoje vive no Fetch Standard da WHATWG. A declaração é um header na resposta: Access-Control-Allow-Origin: http://localhost:5173. Se o header não vem, ou vem com outra origem, o navegador descarta a resposta e o script recebe um erro de rede;
  • Preflight: requisições que o HTML puro não faria - método PUT/DELETE, ou headers como Authorization e Content-Type: application/json - exigem uma consulta prévia: o navegador envia OPTIONS com Access-Control-Request-Method e Access-Control-Request-Headers, perguntando se pode. Só com a resposta Access-Control-Allow-* ele envia a requisição real. Uma API FastAPI sem configuração não tem rota para OPTIONS: responde 405, e o navegador desiste;
  • Quem aplica é o navegador. O Swagger, o curl, um script Python: nenhum deles consulta CORS. Consequência: CORS não é autenticação nem proteção da API - a API continua protegida pelo token. CORS protege o usuário do navegador contra páginas que não são a nossa;
  • Configuração de desenvolvimento: a origem permitida é a do Vite. Em produção seria o endereço público do frontend - e nunca "*" numa API com token, o que anularia a proteção.

Para a turma: "O CORS impede alguém de chamar nossa API a partir de um script Python?" (não - só o navegador aplica a política. Quem protege a API é o token; o CORS protege quem está usando o navegador)
Para a turma: "Um POST /login com corpo JSON dispara preflight? E um GET /api/books com o token?" (ambos: Content-Type: application/json não é um dos três tipos que o HTML puro envia, e Authorization não está na lista de headers seguros. Todas as requisições do frontend vão passar pelo preflight)

7 min Live-coding 2 - a API libera a origem do frontend

Passo 5 - o preflight sem configuração

Por quê: antes de escrever a primeira tela, a API precisa responder à consulta que o navegador fará antes de cada requisição. O curl permite enviar essa consulta à mão, exatamente como o navegador a enviará.

Com o uvicorn rodando, em outro terminal:

Mac 
curl -i -X OPTIONS http://127.0.0.1:8000/signup \
  -H "Origin: http://localhost:5173" \
  -H "Access-Control-Request-Method: POST" \
  -H "Access-Control-Request-Headers: content-type"
Windows (PowerShell) 
curl.exe -i -X OPTIONS http://127.0.0.1:8000/signup `
  -H "Origin: http://localhost:5173" `
  -H "Access-Control-Request-Method: POST" `
  -H "Access-Control-Request-Headers: content-type"

No Windows, curl.exe com a extensão: no PowerShell, curl sozinho pode ser um apelido para outro comando. A resposta:

HTTP/1.1 405 Method Not Allowed
server: uvicorn
allow: POST
content-type: application/json

{"detail":"Method Not Allowed"}
  • -i mostra os headers da resposta; -X OPTIONS escolhe o método; cada -H é um header da consulta prévia: quem pergunta (Origin), qual método pretende usar e quais headers pretende enviar;
  • 405 com allow: POST: a rota /signup só conhece POST. Nenhum header Access-Control-Allow-* na resposta - para o navegador, isso é um "não", e o POST real nunca sairia;
  • No terminal do uvicorn: "OPTIONS /signup HTTP/1.1" 405 Method Not Allowed.

Passo 6 - o CORSMiddleware

Em backend/main.py, importe o middleware e registre-o logo após criar o app:

from fastapi.middleware.cors import CORSMiddleware
app.add_middleware(
    CORSMiddleware,
    allow_origins=["http://localhost:5173"],
    allow_methods=["*"],
    allow_headers=["*"],
)

Um middleware envolve todas as rotas: toda requisição passa por ele antes de chegar à rota, e toda resposta passa por ele na volta. O CORSMiddleware responde o preflight sozinho e acrescenta os headers Access-Control-Allow-* em toda resposta destinada a uma origem permitida. allow_origins é a lista de origens que podem ler as respostas; allow_methods e allow_headers com "*" liberam todos os métodos e headers para essas origens - o que o frontend precisa para enviar PUT, DELETE e o Authorization.

Passo 7 - o preflight respondido

O uvicorn recarrega sozinho. Repita o mesmo curl do passo 5:

HTTP/1.1 200 OK
vary: Origin
access-control-allow-methods: DELETE, GET, HEAD, OPTIONS, PATCH, POST, PUT
access-control-max-age: 600
access-control-allow-origin: http://localhost:5173
access-control-allow-headers: content-type

OK
  • access-control-allow-origin repete a origem que perguntou: é a autorização que o navegador procura;
  • access-control-allow-methods e access-control-allow-headers respondem às duas perguntas da consulta;
  • access-control-max-age: 600: o navegador guarda esta resposta por 600 segundos e não repete o preflight para a mesma requisição nesse intervalo.

Agora troque a origem da consulta para http://127.0.0.1:5173 e repita: a resposta é 400, Disallowed CORS origin, sem access-control-allow-origin. A lista é literal: localhost e 127.0.0.1 apontam para a mesma máquina, mas são origens diferentes.

Para a turma: "O curl recebeu a resposta 400 inteira. Então o CORS não bloqueou nada?" (não bloqueou, e nunca bloqueia no curl: os headers são instruções para o navegador. O curl mostra a conversa crua; quem decide descartar a resposta é o navegador, ao ler esses headers)
Checkpoint parcial: o preflight com Origin: http://localhost:5173 responde 200 com access-control-allow-origin: http://localhost:5173; com outra origem, 400. A API está pronta para o frontend.

5 min Teoria - separação de responsabilidades no frontend

Pontos a explicar:

  • O problema: cada tela do sistema precisa desenhar campos, guardar o que o usuário digitou e conversar com a API. Se as três coisas ficam no mesmo arquivo, uma mudança de rota na API obriga a abrir todas as telas, e um ajuste visual obriga a ler código de rede;
  • Separação de responsabilidades (separation of concerns): expressão cunhada por Edsger W. Dijkstra no texto "On the role of scientific thought" (EWD 447, 1974), que a descreve como "the only available technique for effective ordering of one's thoughts" - tratar um aspecto do problema de cada vez, isolado dos demais;
  • Ocultação de informação: David L. Parnas, em "On the Criteria To Be Used in Decomposing Systems into Modules" (Communications of the ACM, 1972), dá o critério para dividir: cada módulo "is characterized by its knowledge of a design decision which it hides from all others". A pergunta para cada arquivo é: que decisão ele esconde?;
  • No React: a biblioteca não impõe estrutura de pastas. A documentação oficial (Thinking in React, react.dev) recomenda o princípio da responsabilidade única: "a component should ideally only do one thing. If it ends up growing, it should be decomposed into smaller subcomponents";
  • A convenção do projeto - três pastas, cada uma escondendo uma decisão:
PastaResponsabilidadeEscondeNão faz
services/conversar com a APIURL, rotas, verbos HTTP, formato do corpo e da respostanada de tela
pages/uma tela inteirao estado da tela e a ordem das açõesnão monta URL nem escolhe verbo
components/um pedaço de telacomo aquele pedaço é desenhadonão chama a API nem guarda dados

O App.jsx fica na raiz de src/: ele só escolhe qual página aparece. Um componente recebe dados por props e avisa o pai por callbacks - funções recebidas por props, que ele chama quando algo acontece (um clique, um envio). A estrutura ao final da aula:

4 min Teoria - bibliotecas de estilo e componentes prontos

Pontos a explicar:

  • O problema: um campo de formulário bem acabado leva uma dúzia de classes Tailwind - borda, cantos, espaçamento, cor do texto, contorno de foco. O sistema terá oito campos e oito botões. Copiar as classes em cada tela repete a mesma decisão de aparência em cada uso, e mudar a cor primária vira uma busca pelo projeto inteiro;
  • Frameworks de componentes CSS: o Bootstrap (Mark Otto e Jacob Thornton, Twitter, 2011) popularizou classes prontas com nome de componente - btn btn-primary, card, form-control. É rápido de adotar, mas a aparência padrão é reconhecível, e personalizar exige sobrescrever o CSS do framework;
  • Utility-first: o Tailwind segue a linha do Atomic CSS, nomeado por Thierry Koblentz em "Challenging CSS Best Practices" (Smashing Magazine, 2013): classes pequenas, de uma propriedade cada, compostas no próprio HTML. Adam Wathan defende a abordagem no ensaio "CSS Utility Classes and 'Separation of Concerns'" (2017), e a documentação oficial dá a regra para a repetição: quando um conjunto de classes se repete, extraia um componente do framework de interface - no nosso caso, um componente React (tailwindcss.com, Styling with utility classes);
  • Bibliotecas de componentes sobre o Tailwind - todas entregam peças já estilizadas com as mesmas classes utilitárias:

const baseClasses = "rounded-lg px-4 py-2 text-sm font-semibold focus-visible:outline-2 focus-visible:outline-offset-2 focus-visible:outline-indigo-600";

const variantClasses = {
  primary: "bg-indigo-600 text-white shadow-xs hover:bg-indigo-500",
  secondary: "bg-white text-slate-700 shadow-xs ring-1 ring-slate-300 ring-inset hover:bg-slate-50",

10 min Live-coding 5 - os services e a página de cadastro

Passo 17 - services/api.js: uma função para falar com a API

Por quê: todos os services vão fazer a mesma coisa - montar headers, enviar JSON, ler JSON, tratar erro. Isso se escreve uma vez.

Crie a pasta frontend/src/services/ e, dentro dela, api.js:

const API_URL = "http://127.0.0.1:8000";

export async function request(path, { method = "GET", body } = {}) {
  const headers = { "Content-Type": "application/json" };
  const token = localStorage.getItem("token");
  if (token) {
    headers["Authorization"] = `Bearer ${token}`;
  }
  const response = await fetch(API_URL + path, {
    method,
    headers,
    body: body ? JSON.stringify(body) : undefined,
  });
  if (response.status === 204) {
    return null;
  }
  const data = await response.json();
  if (!response.ok) {
    const error = new Error(
      Array.isArray(data.detail) ? data.detail[0].msg : data.detail,
    );
    error.status = response.status;
    throw error;
  }
  return data;
}
  • fetch é a função do navegador para requisições HTTP; async/await são a mesma ideia do Python: a função espera a resposta sem travar a tela;
  • O token é lido do localStorage a cada requisição e vai no header Authorization: Bearer - o mesmo header que o botão Authorize do Swagger monta. Sem token guardado, o header não existe e a API responde 401, como deve;
  • JSON.stringify serializa o corpo; response.json() desserializa a resposta. 204 não tem corpo - e chamar json() nele quebraria;
  • Erro vira exceção com a mensagem da API: detail é texto nas HTTPException (Book not found, Invalid email or password) e uma lista no 422, onde cada item tem o msg do campo inválido. O error.status guarda o código HTTP para quem quiser tratá-lo.

Passo 18 - services/authService.js: cadastro e login

Por quê: as páginas vão pedir "cadastre este usuário" e "entre com este e-mail", sem saber qual rota ou qual verbo a API usa para isso.

Crie frontend/src/services/authService.js:

import { request } from "./api";

export function signup(name, email, password) {
  return request("/signup", { method: "POST", body: { name, email, password } });
}

export async function login(email, password) {
  const data = await request("/login", { method: "POST", body: { email, password } });
  return data.access_token;
}
  • Cada função tem o nome da ação, não da rota: quem chama signup(...) não precisa saber que existe um POST /signup;
  • login devolve só o token: o formato da resposta da API ({"access_token": ..., "token_type": "bearer"}) fica escondido aqui dentro;
  • signup não precisa de async: devolve a promessa do request diretamente, e quem chama faz o await. login precisa, porque trabalha com a resposta antes de devolver.

8 min Teoria - o token no navegador

Pontos a explicar:

  • O problema: a API é stateless - ela não guarda sessão, e o cliente precisa apresentar o token em toda requisição. O navegador então precisa guardar o token entre uma requisição e outra, e entre um F5 e outro;
  • O header: Authorization: Bearer <token> está definido na RFC 6750, "The OAuth 2.0 Authorization Framework: Bearer Token Usage" (IETF, 2012). Bearer é "portador": a RFC define o token como aquele que "any party in possession of [it] can use" - quem o tem, é. Por isso ele não se compartilha e por isso expira;
  • Onde guardar - localStorage: a API Web Storage (especificação W3C de 2013, hoje no HTML Standard da WHATWG) é um armazenamento chave-valor por origem, que sobrevive ao fechamento do navegador. Três métodos: setItem, getItem, removeItem. Ao contrário do cookie, o navegador não o envia sozinho: só o nosso JavaScript o lê e o coloca no header - o que elimina o ataque de requisição forjada entre sites (CSRF), já que outra página não consegue fazer o navegador anexá-lo;
  • O custo: qualquer script que rode na página lê o localStorage. Se um atacante conseguir injetar JavaScript na aplicação (XSS), ele lê o token. As mitigações, segundo o HTML5 Security Cheat Sheet da OWASP, são não confiar em script de terceiros, escapar tudo que vem do usuário (o React escapa por padrão) e manter o token com vida curta - as duas horas do exp;
  • A alternativa é o cookie com HttpOnly, ilegível por JavaScript - imune a XSS, mas exposto a CSRF e preso ao mesmo domínio. Nenhuma das duas é gratuita; para uma API consumida por uma SPA em outra origem, o token no header é a escolha coerente com a arquitetura.

Passo 22 - App.jsx: o estado que escolhe a página

Por quê: sem biblioteca de rotas, a aplicação tem três páginas e um estado decide qual aparece: o token.

Substitua src/App.jsx pela versão final:

import { useState } from "react";
import BooksPage from "./pages/BooksPage";
import LoginPage from "./pages/LoginPage";
import SignupPage from "./pages/SignupPage";

export default function App() {
  const [token, setToken] = useState(localStorage.getItem("token"));
  const [showSignup, setShowSignup] = useState(false);

  function handleLogin(newToken) {
    localStorage.setItem("token", newToken);
    setToken(newToken);
  }

  function handleLogout() {
    localStorage.removeItem("token");
    setToken(null);
  }

  if (token) {
    return <BooksPage onLogout={handleLogout} />;
  }
  if (showSignup) {
    return <SignupPage onDone={() => setShowSignup(false)} />;
  }
  return <LoginPage onLogin={handleLogin} onShowSignup={() => setShowSignup(true)} />;
}
  • useState(localStorage.getItem("token")): o estado inicial vem do que foi guardado. Ao dar F5, o usuário continua logado - o token sobreviveu no navegador;
  • handleLogin faz as duas coisas: guarda (para as próximas requisições e para o F5) e muda o estado (para a tela trocar agora). Só guardar não redesenharia nada; só mudar o estado se perderia no F5;

  • Três return condicionais: UI = f(estado) na forma mais literal. A BooksPage ainda não existe - o Vite vai reclamar do import até ela ser criada.

Passo 25 - pages/BooksPage.jsx: listar e cadastrar

Por quê: a página principal - a primeira que precisa de dados antes de o usuário fazer qualquer coisa.

Crie frontend/src/pages/BooksPage.jsx:

import { useEffect, useState } from "react";
import BookForm from "../components/BookForm";
import BookItem from "../components/BookItem";
import Button from "../components/Button";
import Card from "../components/Card";
import ErrorMessage from "../components/ErrorMessage";
import { createBook, listBooks } from "../services/bookService";

const emptyForm = { name: "", pages: "", current_page: "" };

export default function BooksPage({ onLogout }) {
  const [books, setBooks] = useState([]);
  const [form, setForm] = useState(emptyForm);
  const [error, setError] = useState("");

  useEffect(() => {
    loadBooks();
  }, []);

  async function loadBooks() {
    try {
      setBooks(await listBooks());
    } catch (err) {
      setError(err.message);
    }
  }

  function handleChange(event) {
    setForm({ ...form, [event.target.name]: event.target.value });
  }

  async function handleSubmit(event) {
    event.preventDefault();
    const book = {
      name: form.name,
      pages: Number(form.pages),
      current_page: Number(form.current_page),
    };
    try {
      await createBook(book);
      setForm(emptyForm);
      setError("");
      loadBooks();
    } catch (err) {
      setError(err.message);
    }
  }

  return (
    <main className="mx-auto grid max-w-lg gap-6 px-4 py-10">
      <header className="flex items-center justify-between">
        <h1 className="text-2xl font-bold">My books</h1>
        <Button variant="secondary" onClick={onLogout}>Log out</Button>
      </header>

      <Card>
        <BookForm form={form} onChange={handleChange} onSubmit={handleSubmit} />
      </Card>
      <ErrorMessage text={error} />

      <ul className="grid gap-4">
        {books.map((book) => (
          <BookItem key={book.id} book={book} />
        ))}
      </ul>
    </main>
  );
}

As peças novas:

  • useEffect(() => { loadBooks(); }, []): o efeito roda depois do primeiro desenho; o [] diz "só uma vez". Buscar dados dentro do corpo do componente, fora do efeito, dispararia uma requisição a cada redesenho;
  • form é um objeto com os três campos e handleChange serve aos três inputs do BookForm: [event.target.name] usa o atributo name do input como chave. O { ...form } copia o objeto - o React só redesenha quando recebe um objeto novo, nunca quando o mesmo é alterado por dentro;
  • Inputs entregam texto, mesmo com type="number"; a API valida pages: int. Number(...) converte antes de enviar;
  • books.map(...) transforma a lista de dados em lista de componentes - é assim que se repete em JSX. O key é a identidade de cada item para o React saber o que mudou entre uma lista e a seguinte: o id do banco serve exatamente para isso. Ele fica no elemento que o map devolve - o BookItem -, não no li de dentro;
  • Depois de criar, loadBooks() de novo: a lista vem da API, a fonte da verdade. O estado local não tenta adivinhar o que o banco gravou.

Teste o fluxo inteiro: cadastre-se, entre, cadastre dois livros com páginas, dê F5 - continua logado, a lista continua lá. Abra o console e digite localStorage.getItem("token"): o JWT, com os três blocos separados por ponto. Clique em Log out e repita: null.

export function updateBook(id, book) {

Reescreva o handleSubmit e acrescente as duas funções depois dele:

  async function handleSubmit(event) {
    event.preventDefault();
    const book = {
      name: form.name,
      pages: Number(form.pages),
      current_page: Number(form.current_page),
    };
    try {
      if (editingId === null) {
        await createBook(book);
      } else {
        await updateBook(editingId, book);
      }
      setForm(emptyForm);
      setEditingId(null);
      setError("");
      loadBooks();
    } catch (err) {
      setError(err.message);
    }
  }

  function startEditing(book) {
    setEditingId(book.id);
    setForm({ name: book.name, pages: book.pages, current_page: book.current_page });
  }

  async function handleDelete(id) {
    try {
      await deleteBook(id);
      loadBooks();
    } catch (err) {
      setError(err.message);
    }
  }

Passo 28 - o Reading Progress na tela

Por quê: a API já calcula a porcentagem; o componente só a desenha.

Substitua o BookItem.jsx pela versão final:

import Button from "./Button";
import Card from "./Card";

export default function BookItem({ book, onEdit, onDelete }) {
  return (
    <li>
      <Card>
        <div className="flex items-baseline justify-between gap-4">
          <strong>{book.name}</strong>
          <span className="text-sm text-slate-500">
            {book.current_page}/{book.pages} pages · {book.progress}%
          </span>
        </div>
        <div className="mt-3 h-2 rounded-full bg-slate-100">
          <div className="h-2 rounded-full bg-indigo-600" style={{ width: `${book.progress}%` }} />
        </div>
        <div className="mt-4 flex gap-2">
          <Button variant="secondary" onClick={() => onEdit(book)}>Edit</Button>
          <Button variant="danger" onClick={() => onDelete(book.id)}>Delete</Button>
        </div>
      </Card>
    </li>
  );
}
  • A barra são duas div: a de fundo (cinza, largura total) e a de progresso (índigo), cuja largura é a porcentagem; rounded-full arredonda as pontas. style={{ width: ... }} é o único estilo que o Tailwind não cobre - a largura vem de um dado, não de uma classe;
  • book.progress veio pronto da API. A tela não recalcula nada: se a regra do progresso mudar um dia, muda num lugar só - o model;
  • A mudança ficou inteira no componente: a página e o service não foram abertos. É a separação de responsabilidades funcionando - mudar o desenho de um livro é mudar o arquivo que desenha um livro.

Edite um livro e avance a página atual: a barra cresce. Chegue ao total: 100%, o livro está concluído - sem nenhum campo de status, como o glossário define.

10 min Exercício em sala

Individual - o token dura duas horas. Quando ele vence, a API responde 401 em toda requisição de books e a tela mostra Invalid or expired token em vermelho, mas continua na lista - o usuário precisa descobrir sozinho que deve sair e entrar de novo.

  1. Em pages/BooksPage.jsx, trate o 401: quando qualquer requisição falhar com err.status === 401, chame onLogout() em vez de mostrar a mensagem;
  2. Teste sem esperar duas horas: no console, localStorage.setItem("token", "abc") e F5. A listagem falha com 401 e a aplicação deve voltar sozinha à tela de login.

Gabarito (para o professor): uma função na página concentra a decisão, e os três catch passam a chamá-la:

  function handleError(err) {
    if (err.status === 401) {
      onLogout();
    } else {
      setError(err.message);
    }
  }

O error.status que o services/api.js anexa à exceção existe para isso. Erro clássico a circular: tratar o 401 dentro do próprio services/api.js apagando o token - funciona para books, mas o login com senha errada também é 401, e a tela de login passaria a se comportar de forma estranha. A decisão pertence a quem sabe em que tela está: a página.

  • Síntese: o Book ganhou pages e current_page, e o Reading Progress nasceu como dado derivado - uma property do model, publicada pelo BookRead, nunca armazenada; o frontend é uma aplicação de página única (Garrett, 2005), servida por outra origem, e a política de mesma origem (RFC 6454) exigiu que a API declarasse, por CORS, quem pode ler suas respostas - o CORSMiddleware responde o preflight OPTIONS, verificado com o curl antes de existir a primeira tela, e o navegador aplica a regra; o React desenha a interface como função do estado - useState para o que muda, useEffect para buscar dados, props e callbacks para conversar com o pai -, com Vite servindo e empacotando, Tailwind estilizando no JSX e npm gerenciando as dependências como o pip; o código foi separado por responsabilidade (Dijkstra, 1974; Parnas, 1972): services escondem a API, pages guardam o estado de cada tela, components só desenham o que recebem; entre as bibliotecas de estilo - do Bootstrap aos componentes prontos sobre o Tailwind, como Tailwind Plus, daisyUI e shadcn/ui -, o projeto adotou o padrão de copiar e adaptar: Button, TextInput, ErrorMessage e Card concentram a aparência, com rótulo em todo campo, foco visível e erro anunciado; o token vive no localStorage e viaja no header Authorization: Bearer (RFC 6750), com o custo assumido do XSS e a defesa da vida curta; e o CRUD inteiro - cadastro, login, listar, criar, editar, apagar - roda na tela, com a garantia de que cada um só mexe nos próprios livros continuando onde sempre esteve: na API.
