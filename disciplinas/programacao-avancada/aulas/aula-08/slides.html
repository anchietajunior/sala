Testar é procurar defeitos

Testar é o processo de executar um programa com a intenção de encontrar erros.

O teste de programas pode ser usado para mostrar a presença de defeitos, mas nunca para mostrar a sua ausência.

  • A primeira definição é de Glenford Myers (The Art of Software Testing, 1979); a segunda, de Edsger Dijkstra (Notes on Structured Programming, 1970) - em tradução livre;
  • Uma suíte que passa diz que os cenários escritos funcionam - não que não exista defeito.

MYERS, G. - 1979 · DIJKSTRA, E. W. - EWD 249, 1970

Teste automatizado: código que verifica código

  • Um programa que executa outro programa e compara o resultado obtido com o esperado - roda em segundos, quantas vezes for preciso, sempre igual;
  • A família xUnit: Kent Beck publicou o SUnit, para Smalltalk (Simple Smalltalk Testing: With Patterns, 1994); com Erich Gamma, o JUnit para Java (1997), que levou o modelo a quase todas as linguagens;
  • pytest (Holger Krekel, 2004): um teste é uma função cujo nome começa com test_, e a verificação é um assert comum.

BECK, K. - Simple Smalltalk Testing, 1994 · BECK, K.; GAMMA, E. - Test Infected, 1998 · docs.pytest.org

Arrange, Act, Assert: preparar, agir, verificar


def test_user_lists_only_own_books(client, clarice, machado_admin):
    create_book(client, machado_admin, name="Dom Casmurro")
    create_book(client, clarice, name="A Hora da Estrela")

    response = client.get("/api/books", headers=clarice)

    assert [book["name"] for book in response.json()] == ["A Hora da Estrela"]
  • Arrange: o cenário - dois usuários, um livro de cada;
  • Act: uma única ação sobre o que se testa;
  • Assert: o resultado esperado. Uma linha em branco separa as três partes.

WAKE, B. - 3A: Arrange, Act, Assert, xp123.com, 2001

A pirâmide de testes

COHN, M. - Succeeding with Agile, 2009 · VOCKE, H. - The Practical Test Pyramid, 2018

Por que não testar tudo pela interface

  • Mike Cohn (2009): muitos testes de unidade na base, alguns no meio, poucos pela interface no topo;
  • Os testes do topo são os que mais se parecem com o uso real - e os mais lentos, os que dependem de tudo estar no ar;
  • Quando um teste de ponta a ponta falha, o defeito pode estar na tela, na API, na regra ou no banco. Quando um teste de unidade falha, ele aponta a função.

VOCKE, H. - The Practical Test Pyramid, martinfowler.com, 2018

Recapitulando - o que é um teste automatizado

  • Testar é procurar defeitos (Myers, 1979) - e o teste nunca prova a ausência deles (Dijkstra, 1970);
  • Teste automatizado: código que verifica código; família xUnit e pytest;
  • Arrange, Act, Assert;
  • Pirâmide: muitos de unidade, alguns de integração, poucos de ponta a ponta.

Teste de regressão: o defeito vira teste

Teste repetido depois de uma modificação para garantir que ela não introduziu defeitos nem expôs defeitos nas partes não alteradas do software.

ISTQB - regression testing, tradução livre · BECK, K. - Test-Driven Development: By Example, 2002

Recapitulando - como projetar e classificar testes

  • Caixa preta: casos pela especificação; caixa branca: casos pelos caminhos do código (Myers, 1979);
  • Unidade, integração e aceitação: o que cada nível isola ou junta (ISTQB);
  • Regressão: o teste que reproduz o defeito antes da correção e fica na suíte.

Teste de unidade: o model sozinho


@pytest.mark.parametrize(
    ("current_page", "pages", "expected_progress"),
    [(0, 300, 0), (120, 300, 40), (1, 3, 33), (300, 300, 100)],
)
def test_progress_is_the_current_page_over_the_total_of_pages(current_page, pages, expected_progress):
    book = Book(name="Dom Casmurro", pages=pages, current_page=current_page, user_id=1)

    assert book.progress == expected_progress
  • O pytest descobre arquivos test_*.py e funções test_*; o nome é a frase que aparece quando o teste falha;
  • parametrize: o mesmo teste roda uma vez para cada linha da tabela de casos;
  • Sem banco e sem HTTP: o Book é um objeto Python comum até entrar numa sessão.

def test_admin_can_access_a_book_of_another_user():
    admin = User(id=1, role=Role.ADMIN)
    book_of_another_user = Book(user_id=2)

    assert not user.can_access(book_of_another_user)

Etapa 1 · Backend

Fixture: um banco de teste novo para cada teste


@pytest.fixture
def engine():
    test_engine = create_engine("sqlite://", connect_args={"check_same_thread": False},
                                poolclass=StaticPool)
    Base.metadata.create_all(test_engine)
    yield test_engine
    Base.metadata.drop_all(test_engine)
  • Fixture é a injeção de dependência do pytest: o teste declara um parâmetro com o nome dela e o pytest a executa antes; o que vem depois do yield limpa - mesmo se o teste falhar;
  • SQLite em memória ("sqlite://"): nasce vazio, recebe as tabelas e desaparece no fim do teste. O StaticPool mantém uma conexão só, para todas as sessões verem o mesmo banco;
  • As fixtures ficam em tests/conftest.py, que o pytest carrega sozinho.

dependency_overrides: as rotas usam o banco de teste


@pytest.fixture

@pytest.fixture
def clarice(client):
    return signup_and_login(client, "Clarice Lispector", "clarice@exemplo.com")


@pytest.fixture
def machado_admin(client, engine):
    headers = signup_and_login(client, "Machado de Assis", "machado@exemplo.com")
    with Session(engine) as session:
        statement = select(models.User).where(models.User.email == "machado@exemplo.com")
        machado = session.scalars(statement).one()
        machado.role = models.Role.ADMIN
        session.commit()
    return headers

Testar a interface pelo que o usuário vê

"The more your tests resemble the way your software is used, the more confidence they can give you."

  • Princípio da Testing Library (Kent C. Dodds, 2018): quanto mais o teste se parece com o uso real, mais confiança ele dá;
  • O teste encontra os elementos como uma pessoa: pelo texto, pelo rótulo do campo, pelo papel de acessibilidade (button, heading, link);
  • Classes CSS e estrutura interna mudam sem quebrar o teste.

DODDS, K. C. - Testing Library, Guiding Principles, testing-library.com

Síntese da aula

  • Testar é procurar defeitos (Myers, 1979), e o teste mostra a presença de defeitos, nunca a ausência (Dijkstra, 1970); o teste automatizado é código que verifica código - xUnit (Beck, 1994; Beck e Gamma, 1997), pytest (Krekel, 2004) e a estrutura Arrange-Act-Assert;
  • A pirâmide (Cohn, 2009; Vocke, 2018): muitos de unidade, alguns de integração, poucos de ponta a ponta; caixa preta projeta pela especificação, caixa branca pelos caminhos do código (Myers, 1979); unidade, integração e aceitação são níveis do ISTQB;
  • Backend: testes de unidade do model sem banco; testes de integração caixa preta pelo TestClient, com SQLite em memória ligado pelo dependency_overrides e fixtures de usuários; um defeito real reproduzido em vermelho e corrigido em verde - o teste de regressão fica na suíte;
  • Frontend: Vitest e Testing Library testam componentes e services pelo que o usuário vê, com dublês na borda da rede (Meszaros, 2007); Playwright percorre os critérios de aceitação num navegador de verdade.
