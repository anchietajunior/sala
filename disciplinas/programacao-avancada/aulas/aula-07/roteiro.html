Aula 07 - Autorização e controle de acesso baseado em papéis

Duração: ~2h15 (densa - administre o relógio nos checkpoints; se faltar tempo, o exercício vira tarefa)  ·  Branch: aula-07-autorizacao-e-controle-de-acesso-baseado-em-papeis

Linha de construção: Etapa 1 - banco de dados (o campo role) → Etapa 2 - backend (a API analisa o papel) → Etapa 3 - frontend (o Admin Dashboard)

Temas teóricos: autenticação vs autorização, matriz de acesso e RBAC [T-9]; princípios de proteção de Saltzer e Schroeder; falhas de autorização do OWASP API Security Top 10; 401, 403 e 404; a interface esconde, a API proíbe

Objetivos - ao final, o aluno consegue:

  • Distinguir autenticação de autorização e situar o RBAC entre os modelos de controle de acesso, a partir da matriz de acesso;
  • Modelar papéis com um enum do Python mapeado para uma coluna ENUM do MySQL, com o menor privilégio como padrão do próprio banco;
  • Concentrar a regra de acesso a Books em um único método do model e aplicá-la em todas as rotas - o Admin acessa todos os livros, o User apenas os próprios;
  • Proteger um conjunto de rotas por papel com a dependency require_admin e escolher entre 401, 403 e 404 com base na RFC 9110;
  • Construir no React o Admin Dashboard em /admin e demonstrar que esconder a página é conveniência da interface - quem protege os dados é a API.

5 min Ponto de partida

Abra backend/routers/books.py na tela. A regra que decide quem acessa cada livro está escrita quatro vezes: uma no filtro da listagem e três nas comparações das rotas de um livro só:

statement = select(models.Book).where(models.Book.user_id == current_user.id)   # list_books

if book is None or book.user_id != current_user.id:                # read_book
if stored_book is None or stored_book.user_id != current_user.id:  # update_book
if book is None or book.user_id != current_user.id:                # delete_book

Agora abra o glossário do produto (CONTEXT.md) e leia a definição de Admin: um User que lê, edita e apaga os Books de todos os Users e acessa o Admin Dashboard, uma tela com as quantidades de Users e de Books cadastrados. O código atual tem dois problemas diante dessa definição:

  • Todos os Users são iguais. A tabela users não tem como registrar que alguém é Admin - não há papel nenhum no sistema;
  • A regra de acesso está espalhada. Acrescentar a exceção do Admin significa editar quatro lugares - e esquecer um deles é deixar uma rota com a regra antiga.

Os dois problemas pertencem ao mesmo assunto: autorização. A construção segue a ordem das camadas, de baixo para cima, porque cada camada depende da que está abaixo dela:

  1. Banco de dados - o papel é um dado: sem a coluna, não há o que consultar;
  2. Backend - a API lê o papel e decide o acesso: sem essa decisão, a interface não teria o que mostrar nem o que proteger;
  3. Frontend - a interface mostra o que o papel permite.

15 min Teoria [T-9] - autenticação, autorização e controle de acesso baseado em papéis

Pontos a explicar:

  • Duas perguntas diferentes. A Internet Security Glossary (RFC 4949, R. Shirey, IETF, 2007) define, em tradução livre:
    • autenticação: "o processo de verificar uma alegação de que uma entidade do sistema possui determinado valor de atributo" - a pergunta quem é você?;
    • autorização: "uma aprovação concedida a uma entidade do sistema para acessar um recurso do sistema" - a pergunta o que você pode fazer?.
    A autenticação vem primeiro: só se decide o que alguém pode fazer depois de saber quem ele é. No projeto, o JWT e a dependency get_current_user respondem a primeira pergunta; a segunda ainda não tem resposta no código;
  • A matriz de acesso (Butler Lampson, Protection, 1971): o modelo formal de toda decisão de acesso. As linhas são os sujeitos (quem pede), as colunas são os objetos (o que é pedido) e cada célula guarda os direitos do sujeito sobre o objeto. Autorizar é consultar uma célula;
  • O problema da matriz é a administração: com milhares de usuários e milhões de objetos, manter célula por célula é inviável. Os modelos de controle de acesso são formas de gerar a matriz a partir de regras;
  • RBAC - Role-Based Access Control. Proposto por David Ferraiolo e Richard Kuhn no artigo Role-Based Access Controls (15th National Computer Security Conference, NIST, 1992), como alternativa para organizações civis e comerciais aos modelos discricionário e obrigatório do Orange Book (TCSEC, 1985), pensados para o meio militar. A formulação mais citada é de Sandhu, Coyne, Feinstein e Youman (Role-Based Access Control Models, IEEE Computer, 1996), em tradução livre: "no RBAC, permissões são associadas a papéis, e usuários são designados aos papéis apropriados, adquirindo assim as permissões desses papéis". Virou norma em 2004 (ANSI INCITS 359);
  • Por que papéis: a permissão não é dada à pessoa, é dada ao papel. Promover alguém é trocar o papel dela; mudar o que um papel pode fazer muda, de uma vez, todas as pessoas que o têm;
  • No projeto, dois papéis: admin e user. Mas atenção ao detalhe que o código vai mostrar: a regra "o User acessa os próprios livros" não é RBAC - ela depende da relação entre o usuário e o recurso (book.user_id), não do papel. O OWASP (Authorization Cheat Sheet) recomenda justamente combinar papéis com atributos e relações. O sistema de hoje é essa combinação: o papel decide se a relação de dono importa.

A matriz de acesso do projeto, para o quadro (Machado é Admin, Clarice é User; o livro 1 é do Machado, o 2 é da Clarice):

sujeito \ objetoBook 1 (do Machado)Book 2 (da Clarice)Admin Dashboard
Machado (admin)ler, editar, apagarler, editar, apagarver
Clarice (user)-ler, editar, apagar-
Para a turma: "Entra um terceiro usuário com o papel user. Quantas regras novas precisamos escrever?" (nenhuma - as células da linha dele são geradas pelas regras do papel e da relação de dono. É esse o ganho de não administrar a matriz célula por célula)

15 min Etapa 1 - Banco de dados: o campo role

Passo 1 - models.py: o enum Role e a coluna role

Por quê: o papel é um conjunto fechado de valores - só existem admin e user. Um texto livre aceitaria "Admin", "adm" ou "root"; um enum não. No projeto, a tabela nasce do model: declarar a coluna no User é o que leva o campo ao banco quando o create_all recria a tabela.

Em backend/models.py, acrescente o import do enum, o Enum do SQLAlchemy e a classe Role, e dê ao User a coluna nova:

import enum
from datetime import datetime

from sqlalchemy import Enum, ForeignKey, String, func
from sqlalchemy.orm import Mapped, mapped_column

from database import Base


class Role(enum.Enum):
    ADMIN = "admin"
    USER = "user"


class User(Base):
    __tablename__ = "users"

    id: Mapped[int] = mapped_column(primary_key=True)
    name: Mapped[str] = mapped_column(String(100))
    email: Mapped[str] = mapped_column(String(255), unique=True)
    password: Mapped[str] = mapped_column(String(255))
    role: Mapped[Role] = mapped_column(
        Enum(Role, values_callable=lambda roles: [role.value for role in roles]),
        server_default=Role.USER.value,
    )
    created_at: Mapped[datetime] = mapped_column(server_default=func.now())

Há dois Enum neste arquivo, e a diferença precisa ficar clara:

  • enum.Enum é da biblioteca padrão do Python (PEP 435, de Barry Warsaw, Eli Bendersky e Ethan Furman, no Python 3.4): define o conjunto de valores. Cada membro tem nome (ADMIN, em maiúsculas por ser constante) e valor ("admin"). No código, compara-se user.role == Role.ADMIN - nunca com uma string solta;
  • Enum(Role, ...) é do SQLAlchemy: o tipo da coluna. No MySQL ele vira ENUM('admin','user') - o próprio banco recusa qualquer outro valor;
  • values_callable: por padrão o SQLAlchemy guardaria o nome do membro ('ADMIN'). A função recebe o enum e devolve a lista de valores - ['admin', 'user'] -, que é o que o banco passa a guardar e o que se escreve no SQL;
  • server_default=Role.USER.value - o DEFAULT 'user' fica no banco, como o created_at com func.now(): qualquer INSERT que não informe o papel, venha da API ou de um script, cria um usuário comum. O menor privilégio é o padrão.

Passo 3 - os cadastros recebem o papel do banco

Por quê: o DEFAULT da coluna precisa ser visto trabalhando - e o cadastro é o INSERT que ainda não sabe que o papel existe.

No Swagger, POST /signup com o corpo de sempre - Machado e depois Clarice:

{"name": "Machado de Assis", "email": "machado@exemplo.com", "password": "segredo123"}

No terminal do uvicorn, o echo mostra o comando que desceu para o banco:

INSERT INTO users (name, email, password) VALUES (%(name)s, %(email)s, %(password)s)

O INSERT não cita role (nem created_at). No cliente mysql:

SELECT id, email, role FROM users;

Os dois aparecem como user: quem preencheu o papel foi o DEFAULT do banco. O menor privilégio não depende de o código lembrar dele.

Passo 4 - promover um Admin

Por quê: conceder um papel é uma operação administrativa. A API pública não a oferece - quem promove é quem tem acesso ao banco.

Mac e Windows (dentro do cliente mysql) 
UPDATE users SET role = 'admin' WHERE email = 'machado@exemplo.com';
SELECT id, email, role FROM users;

Mostre também a constraint trabalhando: UPDATE users SET role = 'root' WHERE email = 'clarice@exemplo.com'; - o MySQL recusa com Data truncated for column 'role'. Fora da lista do ENUM, nenhum valor entra.

Checkpoint parcial - o banco: SHOW CREATE TABLE users exibe a coluna role com DEFAULT 'user'; o INSERT do cadastro não cita o papel e o banco grava user; depois do UPDATE, Machado é admin e Clarice é user no SELECT; um papel fora da lista é recusado.

12 min Teoria - princípios de proteção e as falhas de autorização mais comuns

Pontos a explicar:

  • Os princípios de Saltzer e Schroeder. Em The Protection of Information in Computer Systems (Proceedings of the IEEE, 1975), Jerome Saltzer e Michael Schroeder reuniram oito princípios de projeto de mecanismos de proteção - ainda hoje a base dos guias de segurança. Três deles organizam a aula (tradução livre):
    • Padrões à prova de falha (fail-safe defaults): "basear as decisões de acesso em permissão, e não em exclusão". O padrão é negar; o acesso é a exceção que precisa ser provada. No projeto: o DEFAULT 'user' e uma regra que só devolve verdadeiro quando há permissão explícita;
    • Mediação completa (complete mediation): "todo acesso a todo objeto deve ser verificado quanto à autoridade". Toda rota que toca um livro passa pela verificação - não basta proteger a listagem;
    • Menor privilégio (least privilege): "todo programa e todo usuário do sistema deve operar com o menor conjunto de privilégios necessário para completar o trabalho". Todo cadastro nasce user.
  • As falhas que o OWASP mais encontra. O OWASP API Security Top 10 (edição de 2023) classifica as falhas de autorização em três níveis - e cada um tem um ponto correspondente no projeto:
    • API1 - Broken Object Level Authorization (BOLA): acessar um objeto alheio trocando o id na URL (GET /api/books/2). É a primeira da lista desde a primeira edição (2019);
    • API3 - Broken Object Property Level Authorization: alterar uma propriedade que o cliente não deveria controlar. Com a coluna role na tabela, enviar "role": "admin" no cadastro é exatamente essa tentativa - o mass assignment. O caso que popularizou o termo: em 2012, Egor Homakov explorou essa falha numa aplicação Rails do GitHub e ganhou permissão de escrita em um repositório que não era dele;
    • API5 - Broken Function Level Authorization (BFLA): chamar uma função administrativa sendo usuário comum - a rota do Admin Dashboard que vamos criar.
  • 401, 403 e 404 (RFC 9110, HTTP Semantics, IETF, 2022), em tradução livre:
    • 401 Unauthorized: "a requisição não foi aplicada porque não possui credenciais de autenticação válidas para o recurso" - apesar do nome, é falha de autenticação: a API não sabe quem é;
    • 403 Forbidden: "o servidor entendeu a requisição, mas se recusa a atendê-la" - falha de autorização: a API sabe quem é, e não permite;
    • A mesma seção do 403 prevê: "um servidor de origem que deseje 'esconder' a existência atual de um recurso proibido pode, em vez disso, responder 404". É o que as rotas de books já fazem com livro alheio.
SituaçãoRespostaPor quê
Sem token, ou token inválido401a API não sabe quem é
User pede livro de outro User404a existência do livro é informação: não se confirma
User chama rota administrativa403a rota é pública no Swagger: não há o que esconder
Para a turma: "Por que o livro alheio responde 404 e a rota administrativa responde 403?" (o id de um livro é dado do sistema: confirmar que /api/books/2 existe permite enumerar os livros alheios. Já a existência de /api/admin/stats está documentada no Swagger - esconder não protege nada, e o 403 diz a verdade ao cliente)

30 min Etapa 2 - Backend: a API analisa o papel

Passo 5 - o cadastro ignora o papel enviado pelo cliente

Por quê: a primeira análise do papel na API é uma recusa: o cliente não escolhe o próprio papel. Com um campo de privilégio na tabela, a pergunta óbvia de um atacante é: "e se eu mandar o papel no cadastro?".

No Swagger, POST /signup com um campo a mais:

{"name": "Cecília Meireles", "email": "cecilia@exemplo.com",
 "password": "segredo123", "role": "admin"}

A resposta é 201 e, no cliente mysql, SELECT id, email, role FROM users; mostra user. O UserCreate declara apenas name, email e password, e o Pydantic ignora campos que o schema não declara: o schema de entrada funciona como uma lista do que o cliente pode enviar. É a defesa contra o mass assignment - copiar para o objeto do banco tudo o que veio na requisição. Nenhuma linha de código mudou: a proteção já existia no contrato de entrada.

Passo 6 - models.py: is_admin e can_access

Por quê: a regra de acesso precisa existir em um lugar. Quem sabe se um usuário pode acessar um livro é o próprio usuário - o método fica no model User.

No User, depois do created_at:

    @property
    def is_admin(self) -> bool:
        return self.role == Role.ADMIN

    def can_access(self, book: "Book") -> bool:
        return self.is_admin or book.user_id == self.id
  • is_admin é uma property, como o progress do Book: lida como atributo (user.is_admin), calculada a partir do papel. O nome diz a pergunta que responde;
  • can_access é a regra da matriz em uma linha: o Admin acessa qualquer livro (RBAC); os demais, só os que têm o próprio id em user_id (a relação de dono). Só devolve True quando há permissão explícita - o padrão à prova de falha;
  • "Book" entre aspas: a classe Book é definida mais abaixo no arquivo. A anotação como texto (forward reference, PEP 484) é avaliada depois, quando o nome já existe.

Passo 7 - routers/books.py: as rotas usam a regra

Por quê: mediação completa - cada rota que toca um livro consulta a mesma regra.

A listagem: o filtro pelo dono passa a valer só para quem não é Admin:

@router.get("", response_model=list[BookRead])
def list_books(name: str = "", session: Session = Depends(get_session),
               current_user: models.User = Depends(get_current_user)):
    statement = select(models.Book)
    if not current_user.is_admin:
        statement = statement.where(models.Book.user_id == current_user.id)
    if name != "":
        statement = statement.where(models.Book.name.contains(name))
    return session.scalars(statement).all()

E as três comparações viram uma chamada ao método - em read_book e delete_book:

    if book is None or not current_user.can_access(book):
        raise HTTPException(status_code=404, detail="Book not found")

Em update_book:

    if stored_book is None or not current_user.can_access(stored_book):
        raise HTTPException(status_code=404, detail="Book not found")
  • A consulta da listagem é montada em etapas, como o filtro por nome já fazia: começa com todos os livros e recebe o where do dono apenas quando a regra exige;
  • O create_book não muda: o dono continua vindo do token. O Admin cria livros em nome próprio - o papel amplia o que ele acessa, não em nome de quem ele escreve;
  • Se a regra mudar - um terceiro papel que só lê, por exemplo -, a alteração acontece em can_access, e as rotas a herdam.

Teste no Swagger com o token da Clarice: crie um livro e liste - só o dela. Com o token do Machado: GET /api/books traz os livros dos dois, e PUT no livro da Clarice responde 200. Com o token da Clarice, GET no livro do Machado continua 404.

O token do Machado foi emitido antes do UPDATE que o promoveu, e passou a valer como Admin sem novo login. O token carrega quem ele é (sub), não o que ele pode: o get_current_user busca o usuário no banco a cada requisição, e o papel vem junto. Rebaixar alguém também vale na hora.

Passo 8 - security.py: a dependency require_admin

Por quê: o Admin Dashboard precisa de rotas que só o Admin chama - autorização no nível da função, não do objeto.

No fim de backend/security.py:

def require_admin(current_user: models.User = Depends(get_current_user)) -> models.User:
    if not current_user.is_admin:
        raise HTTPException(status_code=403, detail="Admin role required")
    return current_user
  • Uma dependency que depende de outra: o require_admin declara get_current_user, que já verifica o token e busca o usuário. Sem token, o 401 acontece antes; com token, a decisão é sobre o papel;
  • 403, não 404: a API sabe quem é e recusa - a tabela da teoria.

Por quê: a rota nova precisa de um contrato de saída, e a interface vai precisar saber o papel de quem entrou.

No topo de backend/schemas.py, depois do import do Pydantic:

from models import Role

Passo 10 - routers/admin.py: o router protegido inteiro

Por quê: as rotas administrativas formam um recurso próprio, com prefixo próprio - e com a verificação de papel declarada uma vez para todas elas.

Crie backend/routers/admin.py:

from fastapi import APIRouter, Depends
from sqlalchemy import func, select
from sqlalchemy.orm import Session

import models
from database import get_session
from schemas import AdminStats
from security import require_admin

router = APIRouter(prefix="/api/admin", tags=["admin"],
                   dependencies=[Depends(require_admin)])


@router.get("/stats", response_model=AdminStats)
def read_stats(session: Session = Depends(get_session)):
    users_count = session.scalar(select(func.count(models.User.id)))
    books_count = session.scalar(select(func.count(models.Book.id)))
    return AdminStats(users_count=users_count, books_count=books_count)

E registre o router no backend/main.py:

from routers import admin, books, users
app.include_router(users.router)
app.include_router(books.router)
app.include_router(admin.router)
  • dependencies=[Depends(require_admin)] no router: toda rota deste arquivo exige o papel, inclusive as que forem criadas depois. Ninguém precisa lembrar de proteger a próxima rota - a mediação completa vira estrutura;
  • func.count gera o COUNT(...) do SQL; session.scalar devolve o valor da única linha do resultado - o número, pronto. O banco conta; nenhuma linha viaja para o Python;
  • def, não async def: a rota usa a sessão do SQLAlchemy, que é bloqueante - roda na threadpool, como as demais rotas com banco.

Passo 11 - routers/users.py: o login devolve o papel

    return TokenResponse(access_token=create_access_token(user.id), role=user.role)

Teste no Swagger: POST /login do Machado mostra "role": "admin". Com o token dele, GET /api/admin/stats → 200 com users_count e books_count. Com o token da Clarice → 403 Admin role required. Sem token → 401. O Swagger agrupa a rota nova na seção admin.

Checkpoint parcial - o backend: sem nenhuma tela nova, o Swagger já prova a autorização inteira: o cadastro ignora "role"; o User lista só os próprios livros e recebe 404 no livro alheio; o Admin lista todos e edita o livro da Clarice; GET /api/admin/stats responde 401, 403 ou 200 conforme quem chama; o login devolve role.

5 min Teoria - a interface esconde, a API proíbe

Pontos a explicar:

  • Tudo o que está no navegador pertence ao usuário. O JavaScript, o localStorage e as requisições podem ser lidos e alterados pelas ferramentas do desenvolvedor. Uma verificação feita só no frontend é uma sugestão, não uma proteção;
  • O Authorization Cheat Sheet do OWASP manda validar a permissão em toda requisição, no servidor e negar por padrão. A verificação no frontend tem outra função: usabilidade - não mostrar um link que levaria a um erro;
  • Por que o papel vai na resposta do login, e não dentro do token: a interface precisa do papel apenas para decidir o que desenhar. A API não confia nele - ela consulta o banco a cada requisição. Se o papel estivesse no token e a API o lesse de lá, um Admin rebaixado continuaria Admin até o token expirar;
  • O custo assumido: a interface conhece o papel do momento do login. Promovido ou rebaixado, o usuário vê a mudança na tela depois de sair e entrar de novo - nas rotas, ela vale na hora.

25 min Etapa 3 - Frontend: o Admin Dashboard no React

Passo 12 - o login entrega o papel

Por quê: o service esconde o formato da resposta da API; quem chama recebe só o que precisa - agora, o token e o papel.

Em frontend/src/services/authService.js:

export async function login(email, password) {
  const data = await request("/login", { method: "POST", body: { email, password } });
  return { token: data.access_token, role: data.role };
}

Em frontend/src/pages/LoginPage.jsx, dentro do try do handleSubmit:

      const { token, role } = await login(email, password);
      onLogin(token, role);

A desestruturação (const { token, role } = ...) extrai as duas propriedades do objeto em duas constantes.

Passo 13 - App.jsx: o papel e o endereço escolhem a página

Por quê: o projeto não usa biblioteca de rotas. O App já escolhe a página pelo estado; agora escolhe também pelo endereço.

import { useState } from "react";
import AdminDashboardPage from "./pages/AdminDashboardPage";
import BooksPage from "./pages/BooksPage";
import LoginPage from "./pages/LoginPage";
import SignupPage from "./pages/SignupPage";

export default function App() {
  const [token, setToken] = useState(localStorage.getItem("token"));
  const [role, setRole] = useState(localStorage.getItem("role"));
  const [showSignup, setShowSignup] = useState(false);

  function handleLogin(newToken, newRole) {
    localStorage.setItem("token", newToken);
    localStorage.setItem("role", newRole);
    setToken(newToken);
    setRole(newRole);
  }

  function handleLogout() {
    localStorage.removeItem("token");
    localStorage.removeItem("role");
    setToken(null);
    setRole(null);
  }

  if (token) {
    const isAdmin = role === "admin";
    if (window.location.pathname === "/admin" && isAdmin) {
      return <AdminDashboardPage onLogout={handleLogout} />;
    }
    return <BooksPage isAdmin={isAdmin} onLogout={handleLogout} />;
  }
  if (showSignup) {
    return <SignupPage onDone={() => setShowSignup(false)} />;
  }
  return <LoginPage onLogin={handleLogin} onShowSignup={() => setShowSignup(true)} />;
}
  • O papel segue o mesmo caminho do token: estado inicial lido do localStorage, gravado no login, apagado no logout;
  • window.location.pathname é o caminho do endereço atual (/admin em http://localhost:5173/admin). O servidor do Vite devolve o mesmo index.html para qualquer caminho - quem interpreta o caminho é o App;
  • Quem não é Admin e digita /admin recebe a página de livros: a interface não oferece o que o papel não permite.

Passo 14 - os componentes TextLink e StatCard

Por quê: a aparência mora nos componentes estilizados - as páginas não repetem classes do Tailwind.

Crie frontend/src/components/TextLink.jsx:

export default function TextLink({ href, children }) {
  return (
    <a href={href} className="rounded text-sm font-semibold text-indigo-600 hover:text-indigo-500 focus-visible:outline-2 focus-visible:outline-offset-2 focus-visible:outline-indigo-600">
      {children}
    </a>
  );
}

import ErrorMessage from "../components/ErrorMessage";

import { getStats } from "../services/adminService";

export default function AdminDashboardPage({ onLogout }) {
  const [stats, setStats] = useState(null);
  const [error, setError] = useState("");

  useEffect(() => {
    async function loadStats() {
      try {
        setStats(await getStats());
      } catch (err) {
        setError(err.message);
      }
    }
    loadStats();
  }, []);

  return (
    <main className="mx-auto grid max-w-lg gap-6 px-4 py-10">
      <header className="flex items-center justify-between">
        <h1 className="text-2xl font-bold">Admin Dashboard</h1>
        <div className="flex items-center gap-4">

        </div>

10 min A prova com dois usuários

Por quê: autorização só se demonstra com dois papéis lado a lado - e com alguém tentando contornar a regra.

  1. No React (http://localhost:5173), entre como Clarice: título My books, só os livros dela, nenhum link de Admin. Digite /admin na barra de endereço: a página de livros continua;
  2. Saia e entre como Machado: título All books, com os livros da Clarice na lista, e o link Admin Dashboard no cabeçalho. Edite o livro da Clarice pela tela - funciona;
  3. Clique em Admin Dashboard: os cards com as quantidades de Users e de Books, iguais a um SELECT COUNT(*) no cliente mysql;
  4. A tentativa de contornar: saia, entre como Clarice, abra as ferramentas do desenvolvedor (Application → Local Storage), troque role para admin e recarregue /admin. A tela do Admin Dashboard abre - e mostra apenas Admin role required. Na aba Network, a chamada a /api/admin/stats respondeu 403. A interface foi enganada; a API, não;
  5. No cliente mysql, rebaixe o Machado (UPDATE users SET role = 'user' WHERE email = 'machado@exemplo.com';). Na tela dele o link continua - a interface conhece o papel do login -, mas o próximo acesso ao Admin Dashboard responde 403.
Checkpoint - como saber que funcionou:
  • Banco de dados: SHOW CREATE TABLE users exibe `role` enum('admin','user') NOT NULL DEFAULT 'user'; o cadastro grava user sem citar o papel no INSERT; um UPDATE com papel fora da lista é recusado pelo MySQL;
  • Backend: o signup com "role": "admin" no corpo cria um usuário user; routers/books.py não compara mais user_id nas rotas de um livro - a regra vive em User.can_access;
  • Backend: User lista só os próprios livros e recebe 404 em GET, PUT e DELETE de livro alheio; Admin lista todos e lê, edita e apaga qualquer livro; o POST cria em nome de quem pede;
  • Backend: GET /api/admin/stats responde 401 sem token, 403 para User e 200 com users_count e books_count para Admin; o login devolve role;
  • Frontend: só o Admin vê o link e o Admin Dashboard em /admin; com o papel adulterado no localStorage, a página abre sem dados e com a mensagem do 403.

10 min Exercício em sala

Individual - o Admin Dashboard ganha uma terceira quantidade:

  1. Acrescente ao AdminStats o campo finished_books_count: a quantidade de Books concluídos - pelo glossário, um Book está concluído quando o Reading Progress chega a 100%;
  2. Calcule o número na rota GET /api/admin/stats;
  3. Mostre um terceiro StatCard no Admin Dashboard, com o rótulo Finished books.

Gabarito (para o professor): no schemas.py, finished_books_count: int no AdminStats. Na rota:

    finished_books_count = session.scalar(
        select(func.count(models.Book.id)).where(models.Book.current_page == models.Book.pages)
    )
    return AdminStats(users_count=users_count, books_count=books_count,
                      finished_books_count=finished_books_count)

E na página, <StatCard label="Finished books" value={stats.finished_books_count} /> - o grid de duas colunas leva o terceiro card para a linha de baixo. O ponto a discutir: o aluno tende a tentar where(models.Book.progress == 100), e não funciona - progress é uma property do Python, não uma coluna; o banco não a conhece. A condição equivalente em SQL compara as duas colunas: página atual igual ao total de páginas.

5 min Fechamento

  • Teoria: autenticação responde quem é, autorização responde o que pode (RFC 4949); toda decisão de acesso é uma célula da matriz de Lampson (1971), e o RBAC (Ferraiolo e Kuhn, 1992; Sandhu et al., 1996) gera a matriz a partir de papéis - no projeto, combinado com a relação de dono;
  • A ordem da construção: de baixo para cima, porque cada camada depende da que está abaixo - primeiro o dado, depois a decisão, por último a apresentação;
  • Banco de dados: o papel é um enum do Python mapeado para um ENUM do MySQL com DEFAULT 'user' - o menor privilégio como padrão do próprio banco; conceder o papel de Admin é um UPDATE, fora da API;
  • Backend: o schema de entrada ignora o que não declara e fecha o mass assignment; a regra de acesso a Books vive em User.can_access e toda rota de um livro a consulta - mediação completa e padrão à prova de falha (Saltzer e Schroeder, 1975); a dependency require_admin, declarada no router, protege todas as rotas administrativas de uma vez; BOLA, mass assignment e BFLA são as falhas de autorização que o OWASP mais encontra; 401 é "não sei quem é", 403 é "sei e não permito", e o 404 esconde o que não deve ser confirmado (RFC 9110);
  • Frontend: o Admin Dashboard em /admin aparece só para o Admin - mas a tela é conveniência: quem protege os dados é a API, que consulta o papel no banco a cada requisição.
