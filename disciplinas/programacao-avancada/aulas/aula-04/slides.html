Nossos dados morrem a cada restart

O CRUD de Books está completo — GET, POST, PUT e DELETE — sobre uma lista de objetos em memória, com o BookCreate validando a entrada e o next_book_id() calculando o id a partir do último da lista. E, ainda assim:

  • Os dados morrem com o processo — todo restart devolve a lista aos três livros de fábrica;
  • O id é reaproveitado — removido o último livro, o próximo cadastro nasce com o id do removido.

O modelo relacional

"O modelo relacional fornece um meio de descrever dados apenas por sua estrutura natural — sem sobrepor qualquer estrutura adicional para fins de representação na máquina."

  • Origem: proposto por Edgar F. Codd, matemático da IBM, no artigo A Relational Model of Data for Large Shared Data Banks (Communications of the ACM, 1970);
  • Propósito: desacoplar o uso dos dados da forma como são armazenados — o programa muda, o banco fica.

CODD, E. F. — A Relational Model of Data for Large Shared Data Banks, CACM, 1970

O banco gera a chave primária sozinho

  • Auto-increment: um contador que só cresce, mantido pelo próprio banco;
  • Não morre com o processo — e não reaproveita o número de um registro removido;
  • É tudo que a conta do nosso next_book_id() — somar 1 ao id do último da lista — não consegue garantir;
  • A conta artesanal se aposenta hoje.

SQL — a língua dos bancos relacionais

  • Origem: nasceu como SEQUEL (Structured English Query Language), de Donald Chamberlin e Raymond Boyce (IBM, 1974), no projeto System R — a primeira implementação do modelo de Codd;
  • Padronizada como SQL pela ANSI (1986) e pela ISO (1987) — o padrão até hoje;
  • Declarativa: descreve o que se quer, não como buscar — quem escolhe o algoritmo é o banco.

CHAMBERLIN, D.; BOYCE, R. — SEQUEL: A Structured English Query Language, ACM SIGFIDET, 1974

MySQL

  • Sistema gerenciador de banco de dados relacional, criado por Michael Widenius e David Axmark (1995);
  • Código aberto; hoje mantido pela Oracle;
  • Um dos bancos mais usados da web — e o banco da disciplina;
  • Um servidor MySQL hospeda vários databases; o nosso será o reading_tracker.

Documentação oficial do MySQL — dev.mysql.com/doc

O SQL de hoje


CREATE TABLE books (
    id INT AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(255) NOT NULL,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);

INSERT INTO books (name) VALUES ('Dom Casmurro');

SELECT id, name FROM books;

Este é o último CREATE TABLE digitado à mão — daqui em diante, quem o escreve é o ORM.

Recapitulando — modelo relacional

  • Dados em tabelas: linhas são registros, colunas são atributos tipados;
  • A chave primária identifica a linha; o auto-increment a gera;
  • Constraints (NOT NULL, UNIQUE) são defendidas pelo banco, sozinho;
  • SQL é declarativa: o quê, não como.

A nossa API vira cliente de outro servidor

A partir de hoje o backend são dois processos: o uvicorn (porta 8000) e o servidor MySQL (porta 3306) — e a nossa API é o cliente do banco.

  • O MySQL é um servidor como o uvicorn: um processo que escuta uma porta e atende pedidos;
  • A conversa com ele passa pelo cliente de linha de comando do MySQL — é nele que o SQL desta aula é digitado.

O banco do projeto e o SQL na mão


CREATE DATABASE reading_tracker;
USE reading_tracker;

CREATE TABLE books ( ... );   -- o CREATE do slide anterior
INSERT INTO books (name) VALUES ('Dom Casmurro');
SELECT id, name FROM books;
DESCRIBE books;
  • O id veio 1 sem ninguém pedir; o created_at se preencheu sozinho;
  • INSERT com nome NULL → ERROR 1048: Column 'name' cannot be null — a constraint trabalhando, mesmo por fora da API;
  • Ao final, DROP TABLE books; — daqui em diante, quem escreve o CREATE TABLE é o ORM.

Dois mundos que não se encaixam

  • O programa pensa em objetos: classes, atributos, referências (book.name);
  • O banco pensa em relações: tabelas, linhas, chaves;
  • A fricção entre os dois modelos tem nome: descompasso objeto-relacional (object-relational impedance mismatch);
  • Sem ajuda, todo acesso vira tradução manual: montar strings SQL, executar, converter linha em objeto — em cada rota.

FOWLER, M. — Patterns of Enterprise Application Architecture, 2002

ORM — Object-Relational Mapping

Técnica que traduz automaticamente entre o mundo dos objetos e o mundo das relações: o programa manipula objetos; o ORM emite o SQL.

  • classe ↔ tabela  ·  atributo ↔ coluna  ·  objeto ↔ linha

FOWLER, M. — Patterns of Enterprise Application Architecture, 2002

O ORM é um tradutor

FOWLER, M. — Patterns of Enterprise Application Architecture, 2002 · docs.sqlalchemy.org

SQLAlchemy

  • O ORM da disciplina, criado por Michael Bayer (2006) — o mais maduro do ecossistema Python e padrão de fato da indústria;
  • Os padrões que estruturam os ORMs foram catalogados por Martin Fowler (PoEAA, 2002):
    • Active Record — o objeto sabe se salvar (book.save());
    • Data Mapper — uma camada separada move os dados; o objeto nem sabe que banco existe;
    • Unit of Work — acumular mudanças e gravá-las juntas, numa transação;
  • O SQLAlchemy implementa o Data Mapper e o Unit of Work: nossos objetos não têm .save() — quem grava é a Session.

FOWLER, M. — Patterns of Enterprise Application Architecture, 2002 · docs.sqlalchemy.org

O ORM não elimina o SQL — ele o gera

  • Quem não lê SQL não sabe o que o próprio programa faz;
  • Por isso a aula começou com SQL na mão;
  • E por isso ligaremos o echo=True: cada operação imprime no terminal o SQL emitido;
  • SQL cru continua tendo vez: consultas analíticas complexas, ajuste fino de performance;
  • Para o CRUD de uma aplicação, o ORM é o padrão da indústria.

Recapitulando — ORM

  • Objetos e relações não se encaixam: descompasso objeto-relacional;
  • ORM traduz: classe ↔ tabela, atributo ↔ coluna, objeto ↔ linha;
  • SQLAlchemy (Bayer, 2006): Data Mapper + Unit of Work — a Session grava, o objeto não;
  • A tradução pode (e deve) ser lida: echo=True.

database.py — a conexão


from sqlalchemy import create_engine
from sqlalchemy.orm import DeclarativeBase, Session

DATABASE_URL = "mysql+pymysql://root@127.0.0.1:3306/reading_tracker"

engine = create_engine(DATABASE_URL, echo=True)


class Base(DeclarativeBase):
    pass


def get_session():
    with Session(engine) as session:
        yield session
  • engine — ponto único de conexão (echo=True: didático e deliberado);
  • Base — a classe-mãe declarativa: quem herda dela se registra como tabela no metadata;
  • get_session — o canal com o banco: cada requisição abre a sua sessão;
  • O with fecha a sessão sozinho — no fim da requisição ou se a rota der erro.

models.py — o model Book


from datetime import datetime

from sqlalchemy import String, func
from sqlalchemy.orm import Mapped, mapped_column

from database import Base


class Book(Base):
    __tablename__ = "books"

    id: Mapped[int] = mapped_column(primary_key=True)
    name: Mapped[str] = mapped_column(String(255))
    created_at: Mapped[datetime] = mapped_column(server_default=func.now())
Compare com a classe Book do main.py: o mesmo recurso como classe — mas a antiga guarda estado na memória; esta descreve uma tabela. Cada campo é Mapped: mapeado para uma coluna.

O model, linha a linha

  • class Book(Base) — herdar de Base é o que diz "esta classe é uma tabela": no import, ela se registra no metadata;
  • __tablename__ = "books" — o nome da tabela é declarado, não adivinhado — lower_case_snake no singular, como no ADR-0002;
  • primary_key=True num inteiro → PRIMARY KEY e AUTO_INCREMENT: o objeto nasce sem id, o banco atribui um no INSERT — e a conta do next_book_id() se aposenta;
  • String(255) — o MySQL exige tamanho para VARCHAR: Mapped[str] escolhe o tipo, String(255) fixa a largura — e, sem | None, a coluna nasce NOT NULL;
  • server_default=func.now() — server porque quem preenche é o banco: vira o DEFAULT CURRENT_TIMESTAMP; func.now() é a função SQL NOW() escrita em Python;
  • Convenção do ADR-0002: colunas de data/hora com sufixo _at.

create_all — a tabela nasce do model


from fastapi import Depends, FastAPI, HTTPException
from pydantic import BaseModel, ConfigDict
from sqlalchemy import select
from sqlalchemy.orm import Session

import models
from database import Base, engine, get_session

Base.metadata.create_all(engine)

app = FastAPI()
  • O import models vem antes: é ele que registra Book no metadata da Base;
  • Na subida do uvicorn, o echo mostra o CREATE TABLE books (...) — o SQL do quadro, escrito pelo ORM;
  • Conferir no mysql: SHOW TABLES; e DESCRIBE books;.

create_all cria — nunca altera

  • create_all cria o que não existe; tabela existente fica intocada;
  • Mudou o model? Na disciplina: DROP TABLE e deixar recriar — dado de aula é descartável;
  • No mundo real, mudanças de schema são versionadas com migrations (Alembic, no ecossistema Python) — fica na menção, não é tema do curso.

BookRead — o contrato de saída


class BookCreate(BaseModel):
    name: str


class BookRead(BaseModel):
    model_config = ConfigDict(from_attributes=True)

    id: int
    name: str
  • Cada rota vai declarar response_model=BookRead: o contrato do que sai, como o BookCreate é o do que entra — o model tem created_at, o contrato não: a resposta publica o que o cliente precisa, não a tabela inteira;
  • BookRead, não Book: este nome agora pertence ao model do banco;
  • from_attributes=True — o schema vai ler um objeto do ORM: campos em atributos (book.name), não em chaves (book["name"]).

Uma sessão por requisição


def get_session():
    with Session(engine) as session:
        yield session
  • Depends(get_session) — injeção de dependência: a rota declara o que precisa, o framework entrega pronto e garante o fechamento, com sucesso ou erro;
  • yield, não return: a função entrega a sessão, a rota roda, e só então o with fecha;
  • É inversão de controle: no FastAPI, recurso caro ou compartilhado — conexão, sessão, credencial — se declara, não se constrói dentro da rota.

POST /api/books sobre o banco


@app.post("/api/books", response_model=BookRead, status_code=201)
def create_book(book: BookCreate, session: Session = Depends(get_session)):
    new_book = models.Book(name=book.name)
    session.add(new_book)
    session.commit()
    session.refresh(new_book)
    return new_book
  • add — anota a intenção; nada foi ao banco;
  • commit — executa o INSERT e confirma a transação;
  • refresh — recarrega o que o banco gerou: o id do auto-increment e o created_at do DEFAULT;
  • models.Book(...) não passa id nem created_at — as duas colunas que o CREATE TABLE preenche sozinho;
  • É o Unit of Work da teoria, ao vivo.

GET /api/books — a consulta


@app.get("/api/books", response_model=list[BookRead])
def list_books(name: str = "", session: Session = Depends(get_session)):
    statement = select(models.Book)
    if name != "":
        statement = statement.where(models.Book.name.contains(name))
    return session.scalars(statement).all()
  • select(models.Book) — o statement: a pergunta montada, ainda não feita. A consulta é um valor Python — dá para completar por partes;
  • .contains(name) — vira LIKE '%name%' no SQL (confira no echo): busca por pedaço do nome, sem diferenciar maiúsculas no MySQL — o papel do antigo .lower();
  • scalars(statement).all() — executa e devolve os objetos Book; nada de tuplas para desempacotar.

GET por id — busca pela chave


@app.get("/api/books/{book_id}", response_model=BookRead)
def read_book(book_id: int, session: Session = Depends(get_session)):
    book = session.get(models.Book, book_id)
    if book is None:
        raise HTTPException(status_code=404, detail="Book not found")
    return book
  • session.get — busca direta pela chave primária, sem select nem where: a chave é o caminho mais curto até a linha;
  • O for que varria a lista se aposenta;
  • Devolve o objeto ou None — e None vira o mesmo 404 de sempre: o contrato da API não mudou, só o armazém.

PUT — o UPDATE nasce de um atributo


@app.put("/api/books/{book_id}", response_model=BookRead)
def update_book(book_id: int, book: BookCreate,
                session: Session = Depends(get_session)):
    stored_book = session.get(models.Book, book_id)
    if stored_book is None:
        raise HTTPException(status_code=404, detail="Book not found")
    stored_book.name = book.name
    session.commit()
    session.refresh(stored_book)
    return stored_book
  • Trocar o atributo basta: a sessão rastreia os objetos que carregou; o commit percebe a mudança e emite o UPDATE sozinho (confira no echo);
  • É o Unit of Work outra vez — agora sem add.

DELETE


@app.delete("/api/books/{book_id}", status_code=204)
def delete_book(book_id: int, session: Session = Depends(get_session)):
    book = session.get(models.Book, book_id)
    if book is None:
        raise HTTPException(status_code=404, detail="Book not found")
    session.delete(book)
    session.commit()
  • Mesmo desenho: buscar pela chave, 404 se não existir, e então agir;
  • session.delete anota a remoção; o commit emite o DELETE;
  • A resposta segue 204, sem corpo.

main.py não guarda mais estado

  • Nenhuma rota usa a lista — apague de uma vez: a classe Book, a lista books e a função next_book_id();
  • O arquivo ficou com app, schemas e rotas: todo dado mora no banco;
  • A API por fora é a mesma — mesmas URIs, mesmos códigos de status; mudou o que há por trás delas.

O dado que sobrevive

  • Reinicie o uvicorn (Ctrl+C e subir de novo);
  • GET /api/books → os livros continuam lá;
  • Remova o de maior id e cadastre um novo: o id do removido não volta — o auto-increment segue do ponto mais alto, ao contrário da conta do finado next_book_id().

Síntese da aula

  • Modelo relacional (Codd, 1970): tabelas, linhas, colunas, chaves primárias e constraints que o banco defende sozinho;
  • SQL (Chamberlin & Boyce, 1974): a língua declarativa desse mundo — escrita à mão uma vez, na vida;
  • ORM: classe ↔ tabela, atributo ↔ coluna, objeto ↔ linha; o SQLAlchemy é Data Mapper com Unit of Work (add/commit/refresh, e o UPDATE que nasce de um atributo trocado);
  • O create_all materializou o model Book na tabela que antes escrevemos à mão;
  • O CRUD inteiro agora persiste: restart não apaga livro, id removido não volta, e o main.py deixou de guardar estado.
