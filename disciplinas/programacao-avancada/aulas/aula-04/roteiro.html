Aula 04 — Banco de dados e ORMs

Duração: ~2h  ·  Branch: aula-04-banco-de-dados-e-orms

Temas teóricos: o que é um ORM, SQL vs ORM [T-7]

Objetivos — ao final, o aluno consegue:

  • Explicar o modelo relacional (tabela, linha, coluna, chave primária) e situar sua origem;
  • Escrever SQL básico — CREATE TABLE, INSERT, SELECT — no cliente do MySQL;
  • Definir o que é um ORM, explicar o descompasso objeto-relacional e comparar SQL cru com ORM;
  • Configurar a conexão FastAPI → SQLAlchemy → MySQL (engine, Base e sessão) e declarar o model Book;
  • Migrar o CRUD de Books da memória para o banco, explicando add/commit/refresh e as consultas com select.
Antes da aula: peça com antecedência, no grupo da turma, que os alunos baixem o instalador do MySQL — no Windows o download passa de 300 MB e a rede da universidade não dá conta de 30 downloads simultâneos. Quem chegar com o MySQL já instalado ganha 15 minutos de aula.

5 min Ponto de partida

Abra o backend na tela. O CRUD de Books está completo — GET (lista e item), POST, PUT e DELETE — sobre uma lista de objetos Book em memória, com o schema BookCreate validando a entrada e a função next_book_id() calculando o próximo id a partir do último da lista.

Ainda assim, esse código carrega duas fraquezas graves:

  • Os dados morrem com o processo. Todo restart do uvicorn devolve a lista aos três livros de fábrica;
  • O id é reaproveitado. next_book_id() soma 1 ao id do último livro: remova o último e o próximo cadastro nasce com o id do removido — dois livros diferentes, na história da API, com o mesmo identificador.

Hoje o CRUD inteiro se muda para uma casa fora do processo — um banco de dados. E entre o Python e o banco entra um tradutor, o ORM. Por fora, a API não muda: mesmas URIs, mesmos códigos de status. Por dentro, cada rota troca a lista pelo banco.

20 min Teoria [T-7] — o modelo relacional e o SQL

Pontos a explicar:

  • Origem: o modelo relacional foi proposto por Edgar F. Codd, matemático da IBM, no artigo "A Relational Model of Data for Large Shared Data Banks" (Communications of the ACM, 1970). Antes dele, cada sistema gravava dados num formato próprio, e os programas precisavam conhecer a estrutura física dos arquivos; a proposta de Codd foi organizar tudo em relações — tabelas — e desacoplar o uso dos dados da forma como são armazenados;
  • Definição (Codd): "o modelo relacional fornece um meio de descrever dados apenas por sua estrutura natural — isto é, sem sobrepor qualquer estrutura adicional para fins de representação na máquina". É a independência de dados: o programa muda, o banco fica; o banco se reorganiza, o programa nem percebe;
  • O vocabulário: tabela (uma relação: o conjunto de todos os books), linha (um registro: um book), coluna (um atributo tipado: name VARCHAR(255)), chave primária (a coluna que identifica a linha com unicidade — nosso id) e constraint (regra que o banco defende sozinho: NOT NULL, UNIQUE);
  • Auto-increment: o banco sabe gerar a chave primária sozinho, com um contador que só cresce — não morre com o processo e não reaproveita o número de um registro removido. É tudo que a conta do nosso next_book_id() não consegue garantir;
  • SQL: a linguagem para conversar com bancos relacionais. Nasceu como SEQUEL (Structured English Query Language), de Donald Chamberlin e Raymond Boyce (IBM, 1974), dentro do projeto System R — a primeira implementação do modelo de Codd; foi padronizada como SQL pela ANSI em 1986 e pela ISO em 1987, e é o padrão até hoje. É uma linguagem declarativa: descreve o que se quer (SELECT ... WHERE ...), não como buscar — quem decide o algoritmo é o banco;
  • MySQL: sistema gerenciador de banco de dados relacional criado por Michael Widenius e David Axmark (1995), código aberto, hoje mantido pela Oracle. É o banco da disciplina — e um dos mais usados da web.

O SQL que interessa hoje — deixe no quadro (vamos digitá-lo de verdade daqui a pouco):

CREATE TABLE book (
    id INT AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(255) NOT NULL,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);

INSERT INTO book (name) VALUES ('Dom Casmurro');

SELECT id, name FROM book;

Este será o último CREATE TABLE que alguém digita à mão: daqui a pouco quem o escreve é o ORM. Mas só se confia em um tradutor quando se conhecem as duas línguas — por isso o SQL vem primeiro.

Analogia sugerida: a tabela é uma planilha com regras: cada coluna tem tipo declarado, uma coluna identifica a linha (chave primária) e certas regras a "planilha" defende sozinha — recusa nome vazio, recusa id repetido. A diferença para a planilha de verdade: ninguém edita célula à mão; toda conversa passa por uma linguagem formal, o SQL.

Para a turma: "Nosso next_book_id() soma 1 ao id do último livro da lista. Que problemas essa conta tem?" (dois: remove-se o último livro e o id dele renasce no próximo cadastro; e a lista inteira — conta incluída — morre no restart. O auto-increment do banco resolve os dois)
Para a turma: "Por que name NOT NULL no banco, se o BookCreate já recusa corpo sem name?" (deixe a pergunta ecoar — a resposta aparece no live-coding, quando o banco recusar um INSERT sem nome digitado por fora da API)

Passo 3 — o SQL do quadro, ao vivo

Por quê: antes de delegar ao ORM, cada aluno cria uma tabela, insere e consulta uma vez na vida com as próprias mãos.

Mac e Windows (dentro do cliente mysql) 
CREATE TABLE book (
    id INT AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(255) NOT NULL,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);

INSERT INTO book (name) VALUES ('Dom Casmurro');

SELECT id, name FROM book;
DESCRIBE book;

Pontos a mostrar no resultado: o id veio 1 sem ninguém pedir (auto-increment); o created_at se preencheu sozinho (DEFAULT CURRENT_TIMESTAMP); o DESCRIBE exibe a estrutura da tabela. Agora tente gravar um livro sem nome:

INSERT INTO book (name) VALUES (NULL);

O MySQL recusa com ERROR 1048: Column 'name' cannot be null — é a constraint trabalhando. A API valida na porta de entrada; o banco defende o dado contra qualquer caminho — inclusive este cliente mysql, que não passa pela API.

Para fechar, apague a tabela:

DROP TABLE book;

Digitamos o SQL para aprender; daqui em diante, quem escreve CREATE TABLE é o ORM — e precisamos da tabela fora do caminho para vê-lo trabalhar.

Checkpoint parcial: todos com o MySQL de pé, banco reading_tracker criado (visível no SHOW DATABASES) e a cena do Column 'name' cannot be null vista. A tabela book foi apagada ao final — SHOW TABLES; deve responder Empty set.

20 min Teoria [T-7] — ORM: o tradutor entre dois mundos

Pontos a explicar:

  • O problema: nosso programa pensa em objetos (classes, atributos, referências — o book.name que o CRUD manipula); o banco pensa em relações (tabelas, linhas, chaves). São modelos formais diferentes, e a fricção entre eles tem nome: descompasso objeto-relacional (object-relational impedance mismatch). Sem ajuda, todo acesso a banco vira tradução manual: montar strings SQL, executar, converter linha em objeto, repetir em cada rota;
  • A solução: ORM — Object-Relational Mapping, mapeamento objeto-relacional. É a técnica que faz a tradução automática entre os dois mundos: classe ↔ tabela, atributo ↔ coluna, objeto ↔ linha. O programa manipula objetos Python; o ORM emite o SQL;
  • Base conceitual: os padrões que estruturam os ORMs modernos foram catalogados por Martin Fowler em Patterns of Enterprise Application Architecture (2002): Active Record (o objeto sabe se salvar: book.save()), Data Mapper (uma camada separada move dados entre objetos e banco — o objeto nem sabe que banco existe) e Unit of Work (acumular mudanças e gravá-las juntas, numa transação);
  • SQLAlchemy: o ORM da disciplina, criado por Michael Bayer em 2006 — o mais maduro do ecossistema Python e padrão de fato da indústria. Implementa o Data Mapper e o Unit of Work do catálogo de Fowler: nossos objetos não têm .save(); quem grava é a Session (o session.add() + session.commit() que veremos já já);
  • Duas fronteiras, duas declarações: o Book atravessa duas fronteiras na mesma requisição — JSON↔objeto na API e objeto↔linha no banco. A primeira já tem dono: os schemas Pydantic. O SQLAlchemy assume a segunda, com os models. As duas declarações se parecem (um campo por linha, com tipo), mas cada uma é especializada na sua fronteira: o schema valida e filtra o que entra e sai; o model descreve a coluna que o banco cria e defende;
  • Honestidade intelectual — o ORM não elimina o SQL: ele o gera. Quem não lê SQL não sabe o que o próprio programa faz — por isso a aula começou com SQL na mão, e por isso vamos ligar o echo=True do SQLAlchemy: cada operação imprimirá no terminal o SQL emitido. SQL cru continua tendo vez (consultas analíticas complexas, ajuste fino de performance); para o CRUD de uma aplicação, o ORM é o padrão da indústria.

SQL cru vs ORM — a tabela para o quadro:

SQL cru (driver direto)ORM (SQLAlchemy)
Consultastring SQL montada à mãoexpressão Python: select(Book).where(...)
Resultadotuplas cruas, conversão manualobjetos Book prontos
Criação do schemaCREATE TABLE à mãogerado dos models (create_all)
Erro de digitação no SQLexplode em produção, em runtimeatributo inexistente falha no Python, na hora
Trocar de bancoreescrever dialetos do SQLtrocar a string de conexão (em geral)
Controle fino do SQLtotalparcial — o ORM decide a forma final

Analogia sugerida: o ORM é um tradutor juramentado entre dois países: o país dos objetos (Python) e o país das tabelas (MySQL). Você redige o documento na sua língua; ele produz a versão oficial na outra — com fé pública, mas sem mágica: a tradução existe e pode ser lida (echo=True). E como todo tradutor, tem sotaque: quem nunca leu a língua de destino não percebe quando a tradução saiu ruim.

Para a turma: "Nosso projeto já tem um mapeamento parecido com classe↔tabela, em outra fronteira. Qual?" (os schemas Pydantic: classe ↔ JSON. O ORM faz o mesmo papel na outra fronteira: classe ↔ tabela — o Book vai atravessar as duas na mesma requisição)
Para a turma: "Se o ORM gera o SQL sozinho, por que perdemos tempo digitando SQL à mão?" (porque o programador é responsável pelo que o tradutor emite — sem ler SQL, não há como diagnosticar consulta lenta ou errada)

45 min Live-coding — SQLAlchemy e o CRUD sobre o banco

Passo 4 — instalar as dependências

Por quê: três pacotes novos, um por camada da conversa: o ORM, o driver que fala o protocolo do MySQL e a criptografia que o método de login do MySQL moderno exige.

Mac e Windows (venv ativo, dentro de projeto/backend) 
pip install sqlalchemy pymysql cryptography
pip freeze > requirements.txt
  • sqlalchemy — o ORM;
  • pymysql — o driver: implementa em Python puro o protocolo de rede do MySQL (é ele quem realmente conversa na porta 3306);
  • cryptography — exigida pelo PyMySQL para o método de autenticação padrão do MySQL 8+ (caching_sha2_password).

Reforce a arquitetura: o FastAPI não sabe que banco existe; o SQLAlchemy traduz objetos em SQL; o PyMySQL leva o SQL pela rede. O pip freeze registra as versões novas; a Tabela de Dependências do README vai acompanhar (passo final).

Passo 5 — database.py: a conexão

Por quê: a configuração de conexão é uma só para o projeto inteiro — merece arquivo próprio. É a primeira vez que o main.py deixa de ser o único arquivo do backend (estrutura por tipo de arquivo — decisão do ADR-0002).

Crie backend/database.py:

from sqlalchemy import create_engine
from sqlalchemy.orm import DeclarativeBase, Session

DATABASE_URL = "mysql+pymysql://root@127.0.0.1:3306/reading_tracker"

engine = create_engine(DATABASE_URL, echo=True)


class Base(DeclarativeBase):
    pass


def get_session():
    with Session(engine) as session:
        yield session

Disseque a DATABASE_URL — é uma URI, e a anatomia de uma URI a lê inteira:

mysql+pymysql://root@127.0.0.1:3306/reading_tracker
└─────┬──────┘  └┬─┘ └───┬───┘ └┬─┘ └──────┬──────┘
 dialeto+driver user    host  porta   banco (caminho)
  • Esquema virou dialeto+driver: "fale a língua do MySQL, usando o PyMySQL como telefone";
  • Quem tem senha no root (Windows) escreve root:minhasenha@... — usuário e senha antes do @, como numa URL de verdade;
  • engine — o ponto único de conexão com o banco. echo=True é didático e deliberado: imprime no terminal todo SQL emitido (em produção, desliga-se);
  • Base — a classe-mãe declarativa do ORM: toda classe que herdar dela fica registrada como tabela no metadata, o catálogo interno do SQLAlchemy. O corpo é só pass porque o trabalho todo vem da herança de DeclarativeBase;
  • get_session — a sessão: o canal por onde as operações passam. Cada requisição abre a sua, usa e fecha. O with é quem garante o fechamento — no fim da requisição ou se a rota levantar um erro no meio do caminho;
  • yield em vez de return: a função entrega a sessão, o FastAPI executa a rota, e só então a execução volta para cá e o with fecha. Como o parâmetro self da POO, é um mecanismo que o framework opera — a rota só declara que precisa.

Tudo que é banco mora neste arquivo: o endereço, o motor, a classe-mãe dos models e a sessão. Os outros arquivos importam a peça de que precisam e não sabem de mais nada.

Passo 6 — models.py: o model Book

Por quê: a tabela book que criamos à mão, agora declarada como classe — o mapeamento classe↔tabela da teoria, linha por linha.

Crie backend/models.py:

from datetime import datetime

from sqlalchemy import String, func
from sqlalchemy.orm import Mapped, mapped_column

from database import Base


class Book(Base):
    __tablename__ = "book"

    id: Mapped[int] = mapped_column(primary_key=True)
    name: Mapped[str] = mapped_column(String(255))
    created_at: Mapped[datetime] = mapped_column(server_default=func.now())

Pare um segundo antes de explicar linha a linha e peça à turma que compare esta classe com a classe Book que está no main.py. É o mesmo recurso como classe — mas a antiga guarda estado na memória do processo; esta descreve uma tabela. Mapped é literal: "este atributo é mapeado para uma coluna" — o mapeamento objeto-relacional da teoria, palavra por palavra. A classe antiga está com os dias contados: ao final da migração, o model a substitui por completo.

Agora compare com o CREATE TABLE do quadro, coluna a coluna:

  • class Book(Base) — herdar de Base é o que diz "esta classe é uma tabela": no momento do import, ela se registra no metadata;
  • __tablename__ = "book" — o nome da tabela é declarado, não adivinhado. Seguimos a convenção do ADR-0002: lower_case_snake no singular;
  • id: Mapped[int] = mapped_column(primary_key=True) — primary_key=True num inteiro → o MySQL ganha PRIMARY KEY e AUTO_INCREMENT, e a conta do next_book_id() se aposenta. Repare que o objeto recém-criado ainda não tem id — ele nasce sem, e o banco atribui um no INSERT;
  • String(255) — o MySQL exige tamanho para VARCHAR; a anotação str sozinha não basta nesse dialeto — Mapped[str] escolhe o tipo da coluna, String(255) fixa a largura. Como não há Mapped[str | None], a coluna nasce NOT NULL — a constraint que o passo 3 viu trabalhar;
  • server_default=func.now() — server porque quem preenche é o banco, não o Python: vira o DEFAULT CURRENT_TIMESTAMP do quadro. func.now() não executa nada aqui — é a função SQL NOW() escrita em Python, carimbada pelo MySQL na hora do INSERT;
  • Convenção do ADR-0002: colunas de data/hora com sufixo _at.
O from database import Base é o único elo entre os dois arquivos — e é um elo de mão única: models.py conhece a Base, mas continua sem saber endereço de banco, senha ou porta. Conexão é assunto do database.py; forma dos dados é assunto daqui.

Passo 7 — create_all: a tabela nasce do model

Por quê: o momento-síntese da aula — o ORM escreve, sozinho, o SQL que digitamos à mão no passo 3.

No topo do main.py, ajuste os imports e chame o create_all antes de criar o app:

from fastapi import Depends, FastAPI, HTTPException
from pydantic import BaseModel, ConfigDict
from sqlalchemy import select
from sqlalchemy.orm import Session

import models
from database import Base, engine, get_session

Base.metadata.create_all(engine)

app = FastAPI()

Detalhe que importa: o import models vem antes do create_all — é ao importar o módulo que a classe Book se registra no metadata da Base; sem o import, o create_all não teria nada a criar. (ConfigDict, Depends, select e Session entram em cena nos próximos passos.)

Suba o servidor e olhe o terminal:

Mac e Windows (iguais, venv ativo, dentro de projeto/backend) 
uvicorn main:app --reload

O echo=True mostra o ORM trabalhando: um DESCRIBE para ver se a tabela existe e, como não existe, o CREATE TABLE book (...) completo — compare com o do quadro. Confirme no cliente mysql:

SHOW TABLES;
DESCRIBE book;
create_all cria o que não existe — ele nunca altera tabela existente. Mudou o model? Na disciplina: DROP TABLE e deixe recriar (dado de aula é descartável — decisão registrada em docs/convencoes.md). No mundo real, mudanças de schema são versionadas com migrations (a ferramenta do ecossistema é o Alembic) — fica na menção, não é tema do curso.

Passo 8 — BookRead: o contrato de saída

Por quê: até aqui as rotas devolvem objetos da lista e o FastAPI os serializa por conta própria, sem contrato declarado. Com o banco, quem sai da rota passa a ser um objeto do ORM — e a resposta ganha um contrato explícito.

Logo depois do BookCreate, que não muda:

class BookRead(BaseModel):
    model_config = ConfigDict(from_attributes=True)

    id: int
    name: str

Três decisões para verbalizar:

  • response_model — cada rota vai declarar response_model=BookRead (ou list[BookRead]): é o contrato do que sai, como o BookCreate é o contrato do que entra. Repare que o model tem created_at e o contrato não: a resposta publica o que o cliente precisa, não a tabela inteira;
  • O nome BookRead (e não só Book): o nome Book agora pertence ao model do banco — dois "Book" no mesmo arquivo confundiriam mais que o sufixo;
  • from_attributes=True — a novidade. Schemas leem dicionários por padrão; o BookRead vai ler um objeto models.Book, buscando os campos em atributos (book.name) e não em chaves (book["name"]). Essa linha autoriza o Pydantic a fazer a leitura por atributo — sem ela, a rota quebraria ao devolver o objeto do ORM.

Falta a última peça, e ela já está escrita: o get_session do passo 5. Volte ao database.py, mostre-o de novo na tela e apresente o conceito novo do FastAPI: Depends — injeção de dependência. A rota declara "preciso de uma sessão de banco" e o framework entrega uma pronta antes de a função rodar, garantindo o fechamento depois — sucesso ou erro. É inversão de controle: quem gerencia o recurso é o framework, não nós. Vale a generalização: no FastAPI, todo recurso caro ou compartilhado — conexão, sessão, credencial — se declara como dependência, em vez de ser construído dentro da função.

Passo 9 — POST /api/books sobre o banco

Por quê: a primeira rota a migrar é o POST — com o banco vazio, é ela que povoa a tabela para as leituras que vêm depois.

Substitua a rota create_book inteira:

@app.post("/api/books", response_model=BookRead, status_code=201)
def create_book(book: BookCreate, session: Session = Depends(get_session)):
    new_book = models.Book(name=book.name)
    session.add(new_book)
    session.commit()
    session.refresh(new_book)
    return new_book

O trio add/commit/refresh é o Unit of Work da teoria, ao vivo:

  • session.add(new_book) — anota a intenção na sessão; nada foi ao banco ainda;
  • session.commit() — executa o INSERT e confirma a transação: só aqui o dado existe de verdade;
  • session.refresh(new_book) — recarrega o objeto com o que o banco gerou: o id do auto-increment e o created_at do DEFAULT CURRENT_TIMESTAMP.

Repare no que a linha do models.Book(...) não traz: nenhum id e nenhum created_at. Os dois são preenchidos pelo banco no INSERT — exatamente as duas colunas que, no CREATE TABLE do quadro, tinham AUTO_INCREMENT e DEFAULT. E a chamada ao next_book_id() sumiu — a função ficou sem uso; ela sai de vez na limpeza do passo 13.

Teste no Swagger (/docs): POST /api/books com {"name": "Dom Casmurro"} → 201 com id 1. No terminal do uvicorn, o echo mostra o INSERT e o COMMIT. No cliente mysql, SELECT * FROM book; — a linha está lá, com o created_at que a API não devolve. Cadastre mais dois (O Hobbit, Clean Code): os três livros de fábrica agora são linhas do banco, criadas pela API.

Passo 10 — GET /api/books: a consulta

Por quê: a listagem é a primeira consulta ORM do projeto — e o filtro por nome vira SQL de verdade.

@app.get("/api/books", response_model=list[BookRead])
def list_books(name: str = "", session: Session = Depends(get_session)):
    statement = select(models.Book)
    if name != "":
        statement = statement.where(models.Book.name.contains(name))
    return session.scalars(statement).all()
  • select(models.Book) — o statement: a pergunta montada, ainda não feita. A consulta é um valor Python — dá para guardar em variável e completar por partes, como o where condicional faz;
  • .contains(name) — vira LIKE '%name%' no SQL emitido (confira no echo): busca por pedaço do nome, como o filtro em memória fazia. No MySQL a comparação padrão não diferencia maiúsculas — o papel do antigo .lower(), agora por conta do banco;
  • session.scalars(statement) — executa e devolve os objetos Book da consulta (scalars porque extrai o objeto de cada linha do resultado); .all() materializa a lista. Nada de tuplas para desempacotar: o que volta é o objeto.

Teste: GET /api/books lista os três; GET /api/books?name=hobbit devolve um — e o terminal mostra o SELECT ... WHERE book.name LIKE %s com parâmetro, não com o valor colado na string.

Passo 11 — GET /api/books/{book_id}: busca pela chave

Por quê: buscar pela chave primária é a operação mais comum de um banco — e tem atalho próprio.

@app.get("/api/books/{book_id}", response_model=BookRead)
def read_book(book_id: int, session: Session = Depends(get_session)):
    book = session.get(models.Book, book_id)
    if book is None:
        raise HTTPException(status_code=404, detail="Book not found")
    return book
  • session.get(models.Book, book_id) — busca direta pela chave primária, sem select nem where: a chave é o caminho mais curto até a linha. O for que varria a lista se aposenta;
  • Devolve o objeto ou None — e None vira o mesmo 404 de sempre: o contrato da API não mudou, só o armazém.

Passo 12 — PUT e DELETE

Por quê: as duas últimas rotas seguem o mesmo desenho — buscar pela chave, 404 se não existir, e então agir.

@app.put("/api/books/{book_id}", response_model=BookRead)
def update_book(book_id: int, book: BookCreate, session: Session = Depends(get_session)):
    stored_book = session.get(models.Book, book_id)
    if stored_book is None:
        raise HTTPException(status_code=404, detail="Book not found")
    stored_book.name = book.name
    session.commit()
    session.refresh(stored_book)
    return stored_book


@app.delete("/api/books/{book_id}", status_code=204)
def delete_book(book_id: int, session: Session = Depends(get_session)):
    book = session.get(models.Book, book_id)
    if book is None:
        raise HTTPException(status_code=404, detail="Book not found")
    session.delete(book)
    session.commit()
  • No PUT, trocar o atributo basta: a sessão rastreia os objetos que carregou; o commit percebe a mudança e emite o UPDATE sozinho (confira no echo) — é o Unit of Work outra vez, agora sem add;
  • No DELETE, session.delete anota a remoção e o commit emite o DELETE; a resposta segue 204, sem corpo.

15 min Exercício em sala

Individual — o model vai ganhar um campo novo, e o caminho passa por uma pegadinha deliberada:

Gabarito (para o professor): a falha do item 4 é OperationalError: Unknown column 'author' — o create_all viu que a tabela book já existia e não a alterou (a nota do passo 7, agora sentida na pele: é para isso que existem migrations). 5 min Fechamento

  • Síntese: o modelo relacional (Codd, 1970) organiza dados em tabelas, linhas e colunas, com chaves primárias e constraints que o banco defende sozinho; SQL (Chamberlin & Boyce, 1974) é a língua declarativa desse mundo; um ORM traduz entre objetos e relações — classe↔tabela, atributo↔coluna, objeto↔linha — e o SQLAlchemy faz isso como Data Mapper com Unit of Work (add/commit/refresh, e o UPDATE que nasce de um atributo trocado); o create_all materializou o model Book na tabela que antes escrevemos à mão; e o CRUD inteiro agora persiste — restart não apaga livro, id removido não volta, e o main.py deixou de guardar estado.
