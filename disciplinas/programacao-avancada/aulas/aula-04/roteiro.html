Aula 04 — Banco de dados e ORMs

Duração: ~2h  ·  Branch: aula-04-banco-de-dados-e-orms

Temas teóricos: o que é um ORM, SQL vs ORM [T-7]

Objetivos — ao final, o aluno consegue:

  • Explicar o modelo relacional (tabela, linha, coluna, chave primária) e situar sua origem;
  • Escrever SQL básico — CREATE TABLE, INSERT, SELECT — no cliente do MySQL;
  • Definir o que é um ORM, explicar o descompasso objeto-relacional e comparar SQL cru com ORM;
  • Configurar a conexão FastAPI → SQLAlchemy → MySQL (engine e sessão) e declarar o model User;
  • Implementar a rota persistente POST /signup, explicando add/commit/refresh e por que a senha nunca volta na resposta.
Antes da aula: peça com antecedência, no grupo da turma, que os alunos baixem o instalador do MySQL — no Windows o download passa de 300 MB e a rede da universidade não dá conta de 30 downloads simultâneos. Quem chegar com o MySQL já instalado ganha 15 minutos de aula.

5 min Ponto de partida

Abra o backend na tela. O CRUD de Books está completo — GET (lista e item), POST, PUT e DELETE — com schemas Pydantic validando entrada e saída, e um contador monotônico next_book_id gerando ids que sobrevivem a remoções.

Ainda assim, esse código carrega duas fraquezas graves:

  • Os dados morrem com o processo. Todo restart do uvicorn devolve a lista aos três livros de fábrica;
  • O contador de ids é artesanal. Funciona, mas mora na memória do processo: morre junto com ela.

Hoje os dados ganham uma casa fora do processo — um banco de dados. E entre o Python e o banco entra um tradutor, o ORM. O primeiro recurso a se mudar para lá é o User, com a rota POST /signup. Os Books continuam em memória: a mudança do User já exercita o caminho inteiro — conexão, model, schema e escrita — e é sobre esse caminho, não sobre a quantidade de rotas, que a aula é.

20 min Teoria [T-7] — o modelo relacional e o SQL

Pontos a explicar:

  • Origem: o modelo relacional foi proposto por Edgar F. Codd, matemático da IBM, no artigo "A Relational Model of Data for Large Shared Data Banks" (Communications of the ACM, 1970). Antes dele, cada sistema gravava dados num formato próprio, e os programas precisavam conhecer a estrutura física dos arquivos; a proposta de Codd foi organizar tudo em relações — tabelas — e desacoplar o uso dos dados da forma como são armazenados;
  • Definição (Codd): "o modelo relacional fornece um meio de descrever dados apenas por sua estrutura natural — isto é, sem sobrepor qualquer estrutura adicional para fins de representação na máquina". É a independência de dados: o programa muda, o banco fica; o banco se reorganiza, o programa nem percebe;
  • O vocabulário: tabela (uma relação: o conjunto de todos os users), linha (um registro: um user), coluna (um atributo tipado: email VARCHAR(255)), chave primária (a coluna que identifica a linha com unicidade — nosso id) e constraint (regra que o banco defende sozinho: UNIQUE, NOT NULL);
  • Auto-increment: o banco sabe gerar a chave primária sozinho, com um contador que só cresce e não morre com o processo — é o papel que o next_book_id cumpre à mão no nosso código, agora feito pelo próprio banco;
  • SQL: a linguagem para conversar com bancos relacionais. Nasceu como SEQUEL (Structured English Query Language), de Donald Chamberlin e Raymond Boyce (IBM, 1974), dentro do projeto System R — a primeira implementação do modelo de Codd; foi padronizada como SQL pela ANSI em 1986 e pela ISO em 1987, e é o padrão até hoje. É uma linguagem declarativa: descreve o que se quer (SELECT ... WHERE ...), não como buscar — quem decide o algoritmo é o banco;
  • MySQL: sistema gerenciador de banco de dados relacional criado por Michael Widenius e David Axmark (1995), código aberto, hoje mantido pela Oracle. É o banco da disciplina — e um dos mais usados da web.

O SQL que interessa hoje — deixe no quadro (vamos digitá-lo de verdade daqui a pouco):

CREATE TABLE user (
    id INT AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    email VARCHAR(255) NOT NULL UNIQUE,
    password VARCHAR(255) NOT NULL,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);

INSERT INTO user (name, email, password)
VALUES ('Machado de Assis', 'machado@exemplo.com', 'segredo123');

SELECT id, name, email FROM user;

Este será o último CREATE TABLE que alguém digita à mão: daqui a pouco quem o escreve é o ORM. Mas só se confia em um tradutor quando se conhecem as duas línguas — por isso o SQL vem primeiro.

Analogia sugerida: a tabela é uma planilha com regras: cada coluna tem tipo declarado, uma coluna identifica a linha (chave primária) e certas regras a "planilha" defende sozinha — recusa dois e-mails iguais, recusa nome vazio. A diferença para a planilha de verdade: ninguém edita célula à mão; toda conversa passa por uma linguagem formal, o SQL.

Para a turma: "Nosso next_book_id resolve o problema do id repetido — mas que problema ele não resolve?" (ele mora na memória: no restart, volta ao 4 — o auto-increment do banco sobrevive)
Para a turma: "Por que email UNIQUE no banco, se dá para verificar no Python antes de gravar?" (deixe a pergunta ecoar — a resposta completa aparece no live-coding, quando o banco barrar um e-mail duplicado que o nosso código deixou passar)

20 min Teoria [T-7] — ORM: o tradutor entre dois mundos

Pontos a explicar:

  • O problema: nosso programa pensa em objetos (classes, atributos, referências — o book.name do Pydantic); o banco pensa em relações (tabelas, linhas, chaves). São modelos formais diferentes, e a fricção entre eles tem nome: descompasso objeto-relacional (object-relational impedance mismatch). Sem ajuda, todo acesso a banco vira tradução manual: montar strings SQL, executar, converter linha em objeto, repetir em cada rota;
  • A solução: ORM — Object-Relational Mapping, mapeamento objeto-relacional. É a técnica que faz a tradução automática entre os dois mundos: classe ↔ tabela, atributo ↔ coluna, objeto ↔ linha. O programa manipula objetos Python; o ORM emite o SQL;
  • Base conceitual: os padrões que estruturam os ORMs modernos foram catalogados por Martin Fowler em Patterns of Enterprise Application Architecture (2002): Active Record (o objeto sabe se salvar: user.save()), Data Mapper (uma camada separada move dados entre objetos e banco — o objeto nem sabe que banco existe) e Unit of Work (acumular mudanças e gravá-las juntas, numa transação);
  • SQLAlchemy: o ORM da disciplina, criado por Michael Bayer em 2006 — o mais maduro do ecossistema Python e padrão de fato da indústria. Implementa o Data Mapper e o Unit of Work do catálogo de Fowler: nossos objetos não têm .save(); quem grava é a Session (o session.add() + session.commit() que veremos já já);
  • Duas fronteiras, duas declarações: o User atravessa duas fronteiras na mesma requisição — JSON↔objeto na API e objeto↔linha no banco. A primeira já tem dono: os schemas Pydantic. O SQLAlchemy assume a segunda, com os models. As duas declarações se parecem (um campo por linha, com tipo), mas cada uma é especializada na sua fronteira: o schema valida e filtra o que entra e sai; o model descreve a coluna que o banco cria e defende;
  • Honestidade intelectual — o ORM não elimina o SQL: ele o gera. Quem não lê SQL não sabe o que o próprio programa faz — por isso a aula começou com SQL na mão, e por isso vamos ligar o echo=True do SQLAlchemy: cada operação imprimirá no terminal o SQL emitido. SQL cru continua tendo vez (consultas analíticas complexas, ajuste fino de performance); para o CRUD de uma aplicação, o ORM é o padrão da indústria.

SQL cru vs ORM — a tabela para o quadro:

SQL cru (driver direto)ORM (SQLAlchemy)
Consultastring SQL montada à mãoexpressão Python: select(User).where(...)
Resultadotuplas cruas, conversão manualobjetos User prontos
Criação do schemaCREATE TABLE à mãogerado dos models (create_all)
Erro de digitação no SQLexplode em produção, em runtimeatributo inexistente falha no Python, na hora
Trocar de bancoreescrever dialetos do SQLtrocar a string de conexão (em geral)
Controle fino do SQLtotalparcial — o ORM decide a forma final

Analogia sugerida: o ORM é um tradutor juramentado entre dois países: o país dos objetos (Python) e o país das tabelas (MySQL). Você redige o documento na sua língua; ele produz a versão oficial na outra — com fé pública, mas sem mágica: a tradução existe e pode ser lida (echo=True). E como todo tradutor, tem sotaque: quem nunca leu a língua de destino não percebe quando a tradução saiu ruim.

Para a turma: "Nosso projeto já tem um mapeamento parecido com classe↔tabela, em outra fronteira. Qual?" (os schemas Pydantic: classe ↔ JSON. O ORM faz o mesmo papel na outra fronteira: classe ↔ tabela — o User vai atravessar as duas na mesma requisição)
Para a turma: "Se o ORM gera o SQL sozinho, por que perdemos tempo digitando SQL à mão?" (porque o programador é responsável pelo que o tradutor emite — sem ler SQL, não há como diagnosticar consulta lenta ou errada)

Passo 4 — instalar as dependências

Por quê: três pacotes novos, um por camada da conversa: o ORM, o driver que fala o protocolo do MySQL e a criptografia que o método de login do MySQL moderno exige.

Mac e Windows (venv ativo, dentro de projeto/backend) 
pip install sqlalchemy pymysql cryptography
pip freeze > requirements.txt
  • sqlalchemy — o ORM;
  • pymysql — o driver: implementa em Python puro o protocolo de rede do MySQL (é ele quem realmente conversa na porta 3306);
  • cryptography — exigida pelo PyMySQL para o método de autenticação padrão do MySQL 8+ (caching_sha2_password).

Reforce a arquitetura: o FastAPI não sabe que banco existe; o SQLAlchemy traduz objetos em SQL; o PyMySQL leva o SQL pela rede. O pip freeze registra as versões novas; a Tabela de Dependências do README vai acompanhar (passo final).

Passo 5 — database.py: a conexão

Por quê: a configuração de conexão é uma só para o projeto inteiro — merece arquivo próprio. É a primeira vez que o main.py deixa de ser o único arquivo do backend (estrutura por tipo de arquivo — decisão do ADR-0002).

Crie backend/database.py:

from sqlalchemy import create_engine
from sqlalchemy.orm import DeclarativeBase, Session

DATABASE_URL = "mysql+pymysql://root@127.0.0.1:3306/reading_tracker"

engine = create_engine(DATABASE_URL, echo=True)


class Base(DeclarativeBase):
    pass


def get_session():
    with Session(engine) as session:
        yield session

Disseque a DATABASE_URL — é uma URI, e a anatomia de uma URI a lê inteira:

mysql+pymysql://root@127.0.0.1:3306/reading_tracker
└─────┬──────┘  └┬─┘ └───┬───┘ └┬─┘ └──────┬──────┘
 dialeto+driver user    host  porta   banco (caminho)
  • Esquema virou dialeto+driver: "fale a língua do MySQL, usando o PyMySQL como telefone";
  • Quem tem senha no root (Windows) escreve root:minhasenha@... — usuário e senha antes do @, como numa URL de verdade;
  • engine — o ponto único de conexão com o banco. echo=True é didático e deliberado: imprime no terminal todo SQL emitido (em produção, desliga-se);
  • Base — a classe-mãe declarativa do ORM: toda classe que herdar dela fica registrada como tabela no metadata, o catálogo interno do SQLAlchemy. O corpo é só pass porque o trabalho todo vem da herança de DeclarativeBase;
  • get_session — a sessão: o canal por onde as operações passam. Cada requisição abre a sua, usa e fecha. O with é quem garante o fechamento — no fim da requisição ou se a rota levantar um erro no meio do caminho;
  • yield em vez de return: a função entrega a sessão, o FastAPI executa a rota, e só então a execução volta para cá e o with fecha. Como o parâmetro self da POO, é um mecanismo que o framework opera — a rota só declara que precisa.

Tudo que é banco mora neste arquivo: o endereço, o motor, a classe-mãe dos models e a sessão. Os outros arquivos importam a peça de que precisam e não sabem de mais nada.

Passo 6 — models.py: o model User

Por quê: a tabela user que criamos à mão, agora declarada como classe — o mapeamento classe↔tabela da teoria, linha por linha.

Crie backend/models.py:

from datetime import datetime

from sqlalchemy import String, func
from sqlalchemy.orm import Mapped, mapped_column

from database import Base


class User(Base):
    __tablename__ = "user"

    id: Mapped[int] = mapped_column(primary_key=True)
    name: Mapped[str] = mapped_column(String(100))
    email: Mapped[str] = mapped_column(String(255), unique=True)
    password: Mapped[str] = mapped_column(String(255))
    created_at: Mapped[datetime] = mapped_column(server_default=func.now())

Pare um segundo antes de explicar linha a linha e peça à turma que compare esta classe com o schema BookCreate, que está no main.py. A forma é a mesma — um campo por linha, com tipo —, mas a declaração é outra: o schema diz name: str e fala de JSON; o model diz name: Mapped[str] e fala de coluna. Mapped é literal: "este atributo é mapeado para uma coluna" — o mapeamento objeto-relacional da teoria, palavra por palavra.

Agora compare com o CREATE TABLE do quadro, coluna a coluna:

  • class User(Base) — herdar de Base é o que diz "esta classe é uma tabela": no momento do import, ela se registra no metadata;
  • __tablename__ = "user" — o nome da tabela é declarado, não adivinhado. Seguimos a convenção do ADR-0002: lower_case_snake no singular;
  • id: Mapped[int] = mapped_column(primary_key=True) — primary_key=True num inteiro → o MySQL ganha PRIMARY KEY e AUTO_INCREMENT, e o contador artesanal do main.py se aposenta. Repare que o objeto recém-criado ainda não tem id — ele nasce sem, e o banco atribui um no INSERT;
  • String(100) — o MySQL exige tamanho para VARCHAR; a anotação str sozinha não basta nesse dialeto — Mapped[str] escolhe o tipo da coluna, String(100) fixa a largura;
  • unique=True — a constraint mora no banco, não no Python: é o UNIQUE que recusou o Machado duplicado;
  • server_default=func.now() — server porque quem preenche é o banco, não o Python: vira o DEFAULT CURRENT_TIMESTAMP do quadro. func.now() não executa nada aqui — é a função SQL NOW() escrita em Python, carimbada pelo MySQL na hora do INSERT;
  • Convenção do ADR-0002: colunas de data/hora com sufixo _at.
O from database import Base é o único elo entre os dois arquivos — e é um elo de mão única: models.py conhece a Base, mas continua sem saber endereço de banco, senha ou porta. Conexão é assunto do database.py; forma dos dados é assunto daqui.

Passo 7 — create_all: a tabela nasce do model

Por quê: o momento-síntese da aula — o ORM escreve, sozinho, o SQL que digitamos à mão no passo 3.

No topo do main.py, ajuste os imports e chame o create_all antes de criar o app:

from fastapi import Depends, FastAPI, HTTPException
from pydantic import BaseModel, ConfigDict
from sqlalchemy import select
from sqlalchemy.orm import Session

import models
from database import Base, engine, get_session

Base.metadata.create_all(engine)

app = FastAPI()

Detalhe que importa: o import models vem antes do create_all — é ao importar o módulo que a classe User se registra no metadata da Base; sem o import, o create_all não teria nada a criar. (ConfigDict, Depends, select e Session entram em cena nos próximos passos.)

Suba o servidor e olhe o terminal:

Mac e Windows (iguais, venv ativo, dentro de projeto/backend) 
uvicorn main:app --reload

O echo=True mostra o ORM trabalhando: um DESCRIBE para ver se a tabela existe e, como não existe, o CREATE TABLE user (...) completo — compare com o do quadro. Confirme no cliente mysql:

SHOW TABLES;
DESCRIBE user;
create_all cria o que não existe — ele nunca altera tabela existente. Mudou o model? Na disciplina: DROP TABLE e deixe recriar (dado de aula é descartável — decisão registrada em docs/convencoes.md). No mundo real, mudanças de schema são versionadas com migrations (a ferramenta do ecossistema é o Alembic) — fica na menção, não é tema do curso.

Passo 8 — os schemas do User

Por quê: o User atravessa duas fronteiras na mesma requisição — JSON↔objeto (na entrada e na saída da API) e objeto↔linha (no banco). O model do passo 6 cuidou da segunda; faltam os schemas da primeira. Os schemas de Book não se movem: a fronteira deles é a mesma de sempre.

Logo depois dos schemas de Book:

class UserCreate(BaseModel):
    name: str
    email: str
    password: str


class UserRead(BaseModel):
    model_config = ConfigDict(from_attributes=True)

    id: int
    name: str
    email: str

Três decisões para verbalizar:

  • São dois schemas pelo mesmo motivo de Book/BookCreate: o que entra não tem id; o que sai não tem password. A senha entra e nunca mais sai — o response_model é o filtro;
  • O nome UserRead (e não só User): o nome User já pertence ao model do banco — dois "User" no mesmo projeto confundiriam mais que o sufixo;
  • from_attributes=True — a novidade. Até hoje os schemas de saída leram dicionários; o UserRead vai ler um objeto models.User, buscando os campos em atributos (user.email) e não em chaves (user["email"]). Essa linha autoriza o Pydantic a fazer a leitura por atributo — sem ela, a rota quebraria ao devolver o objeto do ORM.

Falta a última peça, e ela já está escrita: o get_session do passo 5. Volte ao database.py, mostre-o de novo na tela e apresente o conceito novo do FastAPI: Depends — injeção de dependência. A rota declara "preciso de uma sessão de banco" e o framework entrega uma pronta antes de a função rodar, garantindo o fechamento depois — sucesso ou erro. É inversão de controle: quem gerencia o recurso é o framework, não nós. Vale a generalização: no FastAPI, todo recurso caro ou compartilhado — conexão, sessão, credencial — se declara como dependência, em vez de ser construído dentro da função.

Passo 9 — POST /signup

Por quê: é a rota de cadastro do mapa REST do projeto — e a primeira escrita persistente que ele terá.

No fim do main.py:

@app.post("/signup", response_model=UserRead, status_code=201)
def signup(user: UserCreate, session: Session = Depends(get_session)):
    # password stored in plain text on purpose — hashing comes
    # with authentication (ADR-0001)
    new_user = models.User(name=user.name, email=user.email, password=user.password)
    session.add(new_user)
    session.commit()
    session.refresh(new_user)
    return new_user

O trio add/commit/refresh é o Unit of Work da teoria, ao vivo:

  • session.add(new_user) — anota a intenção na sessão; nada foi ao banco ainda;
  • session.commit() — executa o INSERT e confirma a transação: só aqui o dado existe de verdade;
  • session.refresh(new_user) — recarrega o objeto com o que o banco gerou: o id do auto-increment e o created_at do DEFAULT CURRENT_TIMESTAMP. Sem o refresh, o objeto em memória ficaria desatualizado em relação à linha recém-gravada.

Repare também no que a linha do models.User(...) não traz: nenhum id e nenhum created_at. Os dois são preenchidos pelo banco no INSERT — exatamente as duas colunas que, no CREATE TABLE do quadro, tinham AUTO_INCREMENT e DEFAULT.

Vale reforçar o nome da rota: /signup é a exceção pragmática à regra do substantivo — cadastro é ação, e quase toda API real o nomeia assim.

Teste no Swagger (/docs): POST /signup com

{"name": "Machado de Assis", "email": "machado@exemplo.com", "password": "segredo123"}

Resposta 201 com id, name e email — sem a senha. No terminal do uvicorn, o echo mostra o INSERT e o COMMIT. No cliente mysql:

SELECT * FROM user;

Lá está a linha — com a senha em texto puro, legível. Pare a aula e aponte isso: qualquer pessoa com acesso ao banco lê a senha de todos. É um erro grave e deliberado (ADR-0001): a correção — guardar apenas o hash da senha, nunca ela — pertence ao mecanismo de autenticação, que o projeto ainda não tem. Anote no quadro: "dívida: senha em texto puro".

Passo 10 — o dado que sobrevive

Derrube o uvicorn (Ctrl+C) e suba de novo. No Swagger: GET /api/books → a lista voltou aos três livros (memória, morreu). No mysql: SELECT * FROM user; → o Machado continua lá (banco, sobreviveu). Passo 11 — o e-mail duplicado: 500 → 409

Por quê: o padrão da disciplina — provocar a falha antes de corrigi-la.

No Swagger, repita o signup do Machado, idêntico. Resultado: 500 Internal Server Error — no terminal, uma IntegrityError: Duplicate entry 'machado@exemplo.com'. É a cena do passo 3, agora pela API: o banco defendeu a regra (o UNIQUE barrou), mas a resposta é vergonhosa — 5xx diz "a culpa é do servidor", quando o cliente é que pediu um e-mail já usado. Erro causado pelo pedido é 4xx. O código certo: 409 Conflict — o pedido é válido, mas conflita com o estado atual do recurso.

Adicione a verificação no início da função signup, antes de criar o new_user:

    statement = select(models.User).where(models.User.email == user.email)
    existing_user = session.scalars(statement).first()
    if existing_user is not None:
        raise HTTPException(status_code=409, detail="Email already registered")

Primeira consulta ORM do projeto, em duas linhas de propósito — a consulta ganha nome antes de ser executada:

  • select(models.User).where(...) — o statement: a pergunta montada, ainda não feita. Repare como a expressão Python parece SQL (é a coluna da tabela comparativa da teoria) e como a condição usa ==, o operador de comparação de sempre;
  • session.scalars(statement) — executa e devolve os objetos User da consulta (scalars porque extrai o objeto de cada linha do resultado); .first() pega o primeiro, ou None se não houver nenhum. Nada de tuplas para desempacotar: o que volta é o objeto.

Confira no echo: foi emitido um SELECT ... WHERE user.email = %s com parâmetro, não com o valor colado na string. Repita o signup duplicado: 409, com mensagem clara.

E se duas requisições com o mesmo e-mail chegarem ao mesmo tempo, ambas passando pelo if? A última linha de defesa continua sendo o UNIQUE no banco — por isso a constraint existe mesmo com a verificação no Python. (Era a resposta completa da pergunta lançada na teoria.)

15 min Exercício em sala

Individual — o model vai ganhar um campo novo, e o caminho passa por uma pegadinha deliberada:

  1. Adicione ao model User o campo age (inteiro): age: Mapped[int];
  2. Adicione age: int aos dois schemas (UserCreate e UserRead) e passe-o na criação do models.User(...);
  3. Teste um signup novo no Swagger e observe a falha (por que a coluna não existe, se o model tem o campo?);
  4. Corrija: DROP TABLE user; no mysql, reinicie o uvicorn e assista ao create_all recriar a tabela — agora com age. Repita o signup: 201, com a idade na resposta e no SELECT.

Gabarito (para o professor): no model, age: Mapped[int] entre name e email (posição livre) — sem mapped_column(...), porque não há nada a configurar: INT não pede tamanho como o VARCHAR; nos schemas, age: int; na rota, models.User(name=user.name, age=user.age, email=user.email, password=user.password). A falha do item 3 é OperationalError: Unknown column 'age' — o create_all viu que a tabela user já existia e não a alterou (a nota do passo 7, agora sentida na pele: é para isso que existem migrations).

Circule pela sala: os erros clássicos serão esquecer o age=user.age na construção do models.User (o INSERT tenta gravar NULL numa coluna NOT NULL → IntegrityError) e esquecer o DROP TABLE (a falha do item 3 nunca se resolve sozinha).

O exercício é descartável: a branch da disciplina segue sem o campo age. Ao final, desfaça as mudanças, DROP TABLE user; e reinicie, para que o model volte ao original.

5 min Fechamento

  • Síntese: o modelo relacional (Codd, 1970) organiza dados em tabelas, linhas e colunas, com chaves primárias e constraints que o banco defende sozinho; SQL (Chamberlin & Boyce, 1974) é a língua declarativa desse mundo; um ORM traduz entre objetos e relações — classe↔tabela, atributo↔coluna, objeto↔linha — e o SQLAlchemy faz isso como Data Mapper com Unit of Work (add/commit/refresh), com os models de um lado da fronteira do banco e os schemas Pydantic do lado da fronteira da API; o create_all materializou o model User na tabela que antes escrevemos à mão; e o projeto ganhou sua primeira rota persistente, POST /signup — respondendo 201 sem devolver a senha e 409 no e-mail repetido, com uma dívida anotada no quadro: a senha em texto puro.
