Aula 02 — Ciclo de vida de uma requisição

Duração: ~2h  ·  Branch: aula-02-ciclo-de-vida-de-uma-requisicao

Temas teóricos: DNS, HTTP e o caminho navegador→servidor→resposta [T-4] · servidores web e o papel do uvicorn [T-5]

Objetivos — ao final, o aluno consegue:

  • Descrever o caminho completo de uma requisição, do endereço digitado à resposta na tela, incluindo o papel do DNS;
  • Ler uma requisição e uma resposta HTTP cruas, identificando método, caminho, headers, status code e corpo;
  • Classificar status codes pelas famílias 2xx/3xx/4xx/5xx e dizer de quem é a "culpa" (cliente ou servidor);
  • Distinguir path params de query params, criar rotas FastAPI que os recebem e explicar a validação automática de tipos;
  • Implementar as primeiras rotas do recurso Books em memória — listar, buscar por nome, obter por id e criar via POST — testando tudo pelo Swagger UI (/docs).

5 min Ponte — onde paramos

Retome o estado do projeto: um backend FastAPI com uma rota, servida pelo uvicorn. O main.py de partida (branch aula-01-inicio-do-projeto-e-frameworks) é:

from fastapi import FastAPI

app = FastAPI()


@app.get("/health")
def read_root():
    return {"status": "Ok"}
Se o main.py de algum aluno ainda tiver a rota / da aula passada, peça para trocar pela versão acima antes de começar — /health é a rota de "o servidor está vivo?" que o projeto vai manter até o fim do curso.

Pergunta de aquecimento: na aula passada digitamos http://127.0.0.1:8000/health e apareceu um JSON. Hoje dissecamos tudo o que acontece entre uma coisa e outra — e no fim a turma vai enxergar essa viagem em qualquer site que abrir.

10 min Teoria [T-4] — DNS: como o navegador acha o servidor

Pontos a explicar:

  • unirios.com.br é um nome; a rede só entende números (endereços IP). Antes de qualquer pedido, o navegador precisa traduzir nome → IP.
  • Essa tradução é o DNS — a "agenda de contatos da internet". Ninguém decora o número do amigo; procura pelo nome.
  • A consulta em etapas (simplificada): cache do navegador/sistema → resolvedor do provedor → servidores raiz → servidores do .br → servidor autoritativo do domínio → IP.
  • Com o IP na mão, o navegador abre uma conexão com o servidor numa porta: a dupla IP + porta identifica a máquina e o programa dentro dela.
  • Por isso nosso endereço tem :8000 — é a porta onde o uvicorn está escutando. Várias aplicações servidoras convivem na mesma máquina, cada uma na sua porta.
  • 127.0.0.1 já é um IP — não há consulta DNS nenhuma. É o endereço de loopback: "esta própria máquina". A requisição nem sai do computador.

Analogia sugerida: a agenda do celular — você toca no nome "Mãe", o telefone descobre o número e só então liga. O DNS faz isso com nomes de sites; 127.0.0.1 é já digitar o número direto.

Para a turma: "Por que 127.0.0.1:8000 funcionou na aula passada mesmo para quem estava sem internet?"
Para a turma: "O que acontece se dois programas na mesma máquina tentarem escutar a porta 8000?" (deixe alguém tentar depois: subir dois uvicorn — o segundo falha com "address already in use")

20 min Teoria [T-4] — anatomia do HTTP

Pontos a explicar: encontrado o servidor, cliente e servidor trocam mensagens de texto com formato fixo. Mostre as duas mensagens do nosso /health cruas, no quadro ou slide:

A requisição que o navegador envia:

GET /health HTTP/1.1
Host: 127.0.0.1:8000
User-Agent: Mozilla/5.0 (Macintosh; ...)
Accept: */*
  • Linha de pedido: método (GET — "me dê"), caminho (/health) e versão do protocolo;
  • Headers: pares chave–valor com metadados do pedido (quem pede, o que aceita);
  • Corpo: um GET normalmente não tem — corpo entra quando enviamos dados (veremos com POST).

A resposta que o servidor devolve:

HTTP/1.1 200 OK
server: uvicorn
content-type: application/json
content-length: 15

{"status":"Ok"}
  • Linha de status: versão + status code (200 OK);
  • Headers: metadados da resposta — content-type avisa "o corpo é JSON", e é por isso que o navegador o exibe formatado;
  • Corpo: o JSON que vimos na tela. A "tela bonita" é só o corpo; o resto viaja escondido.

Status codes — o código diz de quem é a culpa:

  • 2xx — deu certo (200 OK, 201 Created);
  • 3xx — vá para outro lugar (redirecionamento);
  • 4xx — o cliente pediu errado (404 Not Found, 422 dados inválidos);
  • 5xx — o servidor quebrou (500 Internal Server Error).

Analogia sugerida: no restaurante da aula 01 — 404: pediu um prato que não está no cardápio (culpa da mesa); 500: a cozinha pegou fogo (culpa da cozinha).

Para a turma: "Quem escolhe o status code de cada resposta — o navegador ou o nosso código?"
Para a turma: "Vocês já viram um 404 hoje? E um 500? Onde?" (todo mundo já viu; deixe contarem)

Feche o bloco desenhando a viagem completa no quadro: digitou o endereço → DNS traduz nome em IP → conexão com IP:porta → requisição HTTP viaja → servidor processa → resposta HTTP volta → navegador mostra o corpo. É o ciclo de vida que dá nome à aula.

15 min Live-coding — espiando a conversa

Nada de código novo ainda: vamos ver o que a teoria descreveu. Todos com o servidor rodando:

Mac e Windows (iguais, com o venv ativo, dentro de projeto/backend) 
uvicorn main:app --reload

Passo 1 — DevTools do navegador

Por quê: o navegador registra cada requisição que faz — é a ferramenta de inspeção que a turma vai usar o semestre inteiro.

  1. Abra http://127.0.0.1:8000/health;
  2. F12 (ou clique direito → Inspecionar) → aba Network → recarregue a página;
  3. Clique na requisição health: mostre Status (200), Request Headers e Response Headers — apontando cada parte vista na teoria (repare no server: uvicorn e no content-type: application/json).

Passo 2 — a resposta crua no terminal com curl

Por quê: sem a interface do navegador, sobra só o protocolo — dá para ver que é texto mesmo.

Mac (num segundo terminal) 
curl -i http://127.0.0.1:8000/health
Windows (PowerShell, num segundo terminal) 
curl.exe -i http://127.0.0.1:8000/health
No PowerShell, curl sem .exe é um apelido para outro comando (Invoke-WebRequest) — o .exe garante o curl de verdade, que já vem no Windows 10+.

O -i mostra a linha de status e os headers antes do corpo. Depois troque por -v:

Mac 
curl -v http://127.0.0.1:8000/health
Windows (PowerShell) 
curl.exe -v http://127.0.0.1:8000/health

Com -v aparecem as duas direções: as linhas com > são a requisição enviada, as com < são a resposta — a conversa completa da teoria, ao vivo.

Passo 3 — provocando um 404

Por quê: ver a família 4xx acontecer.

No navegador (com a aba Network aberta), acesse http://127.0.0.1:8000/nada: status 404, corpo {"detail":"Not Found"}. Quem respondeu isso? O FastAPI — não existe rota para /nada, e ele avisa educadamente que o pedido está errado.

15 min Teoria [T-5] — servidores web e o papel do uvicorn

Pontos a explicar:

  • Um servidor web é um programa que fica escutando uma porta e fala HTTP: recebe bytes da rede, interpreta, responde.
  • No nosso projeto são dois programas cooperando: o uvicorn (servidor) cuida da rede — sockets, bytes, o protocolo HTTP; o FastAPI (framework) cuida da aplicação — decidir qual função responde e montar o JSON.
  • O uvicorn traduz: bytes que chegam viram objetos Python entregues ao FastAPI; o retorno do FastAPI vira bytes de novo. O contrato entre os dois tem nome: ASGI — qualquer servidor ASGI roda nossa app (é padrão, não casamento).
  • Reveja a linha server: uvicorn nos headers de resposta do live-coding: é ele se identificando.
  • O --reload é serviço do uvicorn: ele vigia os arquivos e reinicia a aplicação — o FastAPI nem fica sabendo.
  • Em produção costuma haver ainda outra camada na frente (um nginx da vida) — só mencionar; não é tema do curso.

Analogia sugerida: continuando o restaurante — o uvicorn é o recepcionista bilíngue: atende o telefone (rede/HTTP), traduz o pedido para a língua da cozinha (Python) e traduz o prato de volta. A cozinha (FastAPI + nossas funções) nunca fala com a rua diretamente.

Para a turma: "Quando rodamos uvicorn main:app, quem está no comando do programa: o nosso código ou o deles?" (gancho com a inversão de controle da aula 01 — nosso código só é chamado quando chega requisição)

10 min Teoria — parâmetros: dados que viajam na URL

Pontos a explicar: nossas rotas até aqui respondem sempre a mesma coisa. Sistemas de verdade recebem entrada de dados — e, na web, o primeiro lugar onde dados viajam é a própria URL. Há dois lugares para eles:

  • Path parameters — um pedaço variável do caminho. Identificam qual coisa queremos. São obrigatórios: sem eles, o caminho nem existe;
  • Query parameters — pares chave=valor depois do ?, separados por &. Ajustam, filtram ou configuram o pedido. Costumam ser opcionais, com um padrão sensato.

Mostre exemplos que a turma usa todo dia (abra no navegador, se quiser):

https://github.com/torvalds/linux
        └─ path: identifica o usuário e o repositório

https://www.google.com/search?q=fastapi
        └─ query: q é o termo buscado

https://www.youtube.com/watch?v=9bZkp7q19f0&t=42
        └─ dois query params: o vídeo (v) e o segundo em que começa (t)

Regra de bolso: path identifica o recurso; query ajusta o pedido. (A anatomia completa de uma URI — esquema, host, porta — é assunto da aula 03.)

Para a turma: "Na URL de uma busca do Google, o que é caminho e o que é query? Por que o termo buscado não vai no caminho?"
Para a turma: "No YouTube, por que o t=42 (começar aos 42 segundos) faz sentido como query param, e não como parte do caminho?"

30 min Live-coding — o primeiro recurso: Books

Teoria vista; agora os parâmetros entram no código — direto no que interessa: o primeiro recurso do Reading Tracker, os Books. Ainda sem banco de dados: uma lista Python em memória faz as vezes dele por enquanto.

Passo 1 — o nome da função não é a rota

Por quê: desfazer uma confusão comum antes de criar rotas novas — e limpar uma sobra da aula 01.

Em main.py, renomeie read_root para read_health:

@app.get("/health")
def read_health():
    return {"status": "Ok"}

Salve e recarregue /health: nada mudou. A rota vem do decorator (@app.get("/health")), não do nome da função — o nome é para humanos lerem.

Passo 2 — a lista de livros e o prefixo /api

Por quê: precisamos de dados para servir. E as rotas do sistema ganham o prefixo /api: quando o frontend React chegar, ficará óbvio o que é API e o que é tela.

Logo depois de app = FastAPI(), crie a lista:

books = [
    {"id": 1, "name": "Dom Casmurro"},
    {"id": 2, "name": "O Hobbit"},
    {"id": 3, "name": "Clean Code"},
]

Uma lista de dicionários, cada livro com id e name — o nosso "banco" provisório.

Passo 3 — listar a coleção: GET /api/books

Por quê: a rota mais simples do recurso: devolver todos os livros.

@app.get("/api/books")
def list_books():
    return books

Teste no navegador: /api/books devolve os três livros — a lista de dicionários vira JSON sozinha, trabalho do framework.

Passo 4 — um livro pelo id: path param em ação

Por quê: o path param identifica qual livro queremos — a teoria virando código. E, pela primeira vez, somos nós que escolhemos o status code da resposta.

Troque a primeira linha do main.py para importar também o HTTPException:

from fastapi import FastAPI, HTTPException

E crie a rota:

@app.get("/api/books/{book_id}")
def read_book(book_id: int):
    for book in books:
        if book["id"] == book_id:
            return book
    raise HTTPException(status_code=404, detail="Book not found")

Explique as novidades:

  • O {book_id} do caminho vira automaticamente o argumento book_id da função — mesmo nome, obrigatório;
  • book_id: int — o path param tem tipo: o FastAPI converte o texto da URL para inteiro e valida (validação na borda, de graça);
  • Se o laço não encontra o livro, nós escolhemos a resposta: HTTPException com 404 e mensagem nossa.

Teste, com a aba Network aberta, anotando os status codes no quadro: /api/books/1 → 200; /api/books/99 → 404; /api/books/abc → 422 — o FastAPI recusou sozinho ("abc" não é inteiro) e nossa função nem chegou a rodar. Família 4xx nos dois casos: o pedido está errado.

Passo 5 — buscar pelo nome: query param em ação

Por quê: a query ajusta o pedido — a mesma rota de listagem, agora com filtro opcional.

Evolua a rota de listagem:

@app.get("/api/books")
def list_books(name: str = ""):
    if name == "":
        return books
    return [book for book in books if name.lower() in book["name"].lower()]

name não está no caminho — então vira query param: viaja depois do ? na URL. Tem default, logo é opcional: sem ele, a rota lista tudo como antes.

Teste: /api/books?name=hobbit devolve só O Hobbit — o .lower() dos dois lados torna a busca indiferente a maiúsculas (?name=HOBBIT também funciona).

Deixe no quadro uma referência de consulta rápida: a FastAPI Cheat Sheet do DevSheets (devsheets.io/sheets/fastapi) — as seções Path Parameters e Query Parameters resumem exatamente o que acabamos de fazer (e mostram validações extras, como Path() e Query(), que não usaremos por enquanto). Vale como material de apoio no exercício e em casa.

Passo 6 — Swagger: a API documentada de graça

Por quê: na aula 01 espiamos o /docs por 30 segundos; agora ele tem o que mostrar — e o próximo passo vai precisar dele.

Abra http://127.0.0.1:8000/docs:

  • As três rotas listadas, sem escrevermos uma linha de documentação — o framework leu nossos decorators, tipos e defaults;
  • Expanda GET /api/books/{book_id}: parâmetro com tipo e obrigatoriedade; em GET /api/books, o name aparece como opcional — tudo veio da assinatura das funções;
  • Try it out: execute uma chamada pela interface e mostre que ela exibe o comando curl equivalente, o status e o corpo — o Swagger é um cliente HTTP, como o navegador e o curl;
  • Repare no 422 já documentado como resposta possível.

Mencione: em produção muitas equipes restringem o /docs; no nosso projeto ele fica sempre aberto — aqui é ferramenta de ensino (decisão registrada no ADR-0002).

Passo 7 — criar um livro: POST /api/books

Por quê: até aqui só lemos (GET). Criar algo é outro verbo — POST — com os dados viajando no corpo da requisição, aquele corpo que o GET não usa.

@app.post("/api/books", status_code=201)
def create_book(book: dict):
    new_book = {"id": len(books) + 1, "name": book["name"]}
    books.append(new_book)
    return new_book
  • book: dict — o FastAPI entrega o JSON do corpo como dicionário. Cru, sem validação — na aula 03 o Pydantic assume esse posto;
  • status_code=201 — "Created": a resposta certa para criação, direto da tabela de status codes de hoje;
  • O id novo é len(books) + 1 — funciona porque ainda não removemos livros.

A barra de endereço do navegador só faz GET — para o POST, use o Swagger: /docs → POST /api/books → Try it out → corpo {"name": "O Senhor dos Anéis"} → Execute. Resposta 201 com o livro criado; confira com GET /api/books.

Dois ganchos para deixar armados: (1) envie um POST sem o campo name — 500! O dict cru não valida nada; é este buraco que o Pydantic fecha na aula 03. (2) Salve qualquer arquivo (o --reload reinicia o servidor) e liste os livros de novo: o livro criado sumiu — dados em memória morrem com o processo; é este buraco que o banco de dados fecha na aula 04.
Para a turma: "Se um dia removermos um livro, o que quebra no len(books) + 1?" (deixe a resposta em aberto — volta na aula 03)

Passo 8 — registrar os endpoints no README

Por quê: o README conta o estado do projeto; agora ele tem rotas demais para ficarem sem índice.

Adicione ao projeto/README.md, depois da seção "Backend — como rodar":

## Endpoints

| Método | Rota | O que faz |
| ------ | ---- | --------- |
| GET | /health | Verifica se a API está no ar |
| GET | /api/books | Lista os livros; query param opcional name busca pelo nome |
| GET | /api/books/{book_id} | Um livro pelo id (404 se não existir) |
| POST | /api/books | Cria um livro na lista em memória |

A documentação interativa (Swagger) fica em http://127.0.0.1:8000/docs
Checkpoint — como saber que funcionou:
  • /api/books lista os três livros e /api/books?name=hobbit filtra;
  • /api/books/99 devolve o nosso 404 e /api/books/abc devolve 422;
  • Um POST pelo Swagger cria o livro com 201 — e ele aparece no GET seguinte; um POST sem name devolve 500 — e a turma sabe explicar por que o 422 é culpa do cliente e o 500 é culpa nossa;
  • /docs lista as quatro rotas e executa chamadas pelo "Try it out".

10 min Exercício em sala

Individual, com o que acabou de ser visto:

  1. Criar uma rota GET /repeat/{word} que recebe uma palavra no caminho e um query param times (inteiro, padrão 2);
  2. Responder um JSON com word, times e result — a palavra repetida times vezes (dica: em Python, "la" * 3 é "lalala");
  3. Testar pelo Swagger (/docs) — incluindo uma chamada que provoque um 422.

Gabarito (para o professor):

@app.get("/repeat/{word}")
def read_repeated_word(word: str, times: int = 2):
    return {"word": word, "times": times, "result": word * times}

Circule pela sala: os erros clássicos serão esquecer o tipo em times (aí "abc" não dá 422 — bom gancho para reforçar a validação) e tentar pôr times no caminho da rota.

  • Gancho para a aula 03: "Hoje o recurso Books nasceu, mas fizemos tudo no instinto — dict cru no POST, verbos escolhidos no olho. Semana que vem o código sobe de patamar: o livro deixa de ser um dicionário e vira uma classe, o recurso ganha o ciclo completo — inclusive o DELETE, que finalmente responde à pergunta do len(books) + 1 — e o dict cru dá lugar a schemas Pydantic. E teremos a teoria que dá nome a tudo isso: o que é uma API, o que é REST e como se lê uma URI. E os dados que somem a cada restart? Banco de dados, aula 04."
