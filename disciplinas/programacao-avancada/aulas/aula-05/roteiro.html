Aula 05 — Relações 1:N e o CRUD de Books

Duração: ~2h  ·  Branch: aula-05-relacoes-1-n-e-o-crud-de-books

Temas teóricos: sem tema novo da ementa — a aula aprofunda o modelo relacional [T-7]: relações 1:N, chave estrangeira e integridade referencial.

Objetivos — ao final, o aluno consegue:

  • Explicar o que é uma relação 1:N e justificar em que lado dela mora a chave estrangeira;
  • Definir integridade referencial e demonstrar o banco defendendo-a (filho órfão recusado, pai com filhos protegido);
  • Declarar a relação User–Book no SQLModel com foreign_key e Relationship;
  • Reconstruir o CRUD de Books sobre o MySQL, nas rotas do mapa REST da aula 03 (/users/{user_id}/books e /books/{book_id});
  • Apontar a falha de segurança deliberada do user_id explícito na URL e conectá-la ao ADR-0001.
Antes da aula: o exercício da aula 04 (campo age) era descartável — confira que todos desfizeram as mudanças e que o models.py voltou ao original. O banco pode ter ficado vazio depois do DROP TABLE user; não é problema: o primeiro checkpoint do live-coding recria um User pelo Swagger.

20 min Teoria — relações 1:N, chave estrangeira e integridade referencial

Pontos a explicar:

  • Origem — ligar dados por valor, não por ponteiro: antes do modelo relacional, os bancos navegacionais (hierárquicos, como o IMS da IBM, e de rede, como os do padrão CODASYL) ligavam registros por ponteiros físicos: o programa precisava navegar a estrutura para chegar ao dado. A proposta de Edgar F. Codd (1970) foi radical também nisso: relações se ligam por valores compartilhados — uma tabela referencia a outra guardando o valor da chave dela. É essa ideia que hoje ganha nome e sintaxe;
  • Modelar antes de criar tabelas: em 1976, Peter Chen publicou "The Entity-Relationship Model — Toward a Unified View of Data" (ACM Transactions on Database Systems, vol. 1, n. 1) — o modelo entidade-relacionamento. A proposta: descrever o domínio como entidades (as "coisas": User, Book), relacionamentos (as associações entre elas: "cadastrou", "pertence a") e cardinalidades — quantos de um lado se associam a quantos do outro: 1:1, 1:N, N:M;
  • O nosso caso é 1:N: um User tem muitos Books; cada Book pertence a exatamente um User. (A aula 06 adiciona a segunda relação 1:N do projeto: um Book tem muitos Reading Updates. N:M — ex.: alunos e disciplinas — exige uma tabela associativa; não teremos nenhuma no curso, fica a menção);
  • Chave estrangeira (foreign key): a materialização da relação. Definição formal, do livro clássico de C. J. Date (An Introduction to Database Systems, 8ª ed., 2003): uma coluna (ou conjunto de colunas) de uma tabela cujos valores devem ser, obrigatoriamente, valores da chave primária da tabela referenciada. No nosso caso: book.user_id só aceita valores que existam em user.id;
  • A FK mora sempre no lado N: cada Book aponta para o seu único dono — uma coluna escalar basta. O contrário não funciona: o User precisaria guardar uma lista de ids numa coluna só, e o lado N é ilimitado;
  • Integridade referencial: a garantia — defendida pelo banco, não pelo programa — de que nenhuma referência quebra: o banco recusa o filho órfão (INSERT de book com user_id inexistente) e protege o pai com filhos (DELETE de user que ainda tem books). É o mesmo papel do UNIQUE da aula 04: regra no banco, última linha de defesa. O comportamento padrão do MySQL é RESTRICT (recusar); existem alternativas declaráveis — ON DELETE CASCADE (apagar o pai leva os filhos) e ON DELETE SET NULL — que ficam na menção.

O SQL de hoje — deixe no quadro (é ele que o ORM vai escrever por nós daqui a pouco):

CREATE TABLE book (
    id INT AUTO_INCREMENT PRIMARY KEY,
    title VARCHAR(200) NOT NULL,
    pages INT NOT NULL,
    user_id INT NOT NULL,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (user_id) REFERENCES user(id)
);

Analogia sugerida: a chave estrangeira é o número de matrícula numa lista de presença. A lista (book) não copia a ficha do aluno — anota só a matrícula (user.id). A secretaria (o banco) recusa presença com matrícula inexistente e não deixa cancelar a matrícula de quem tem presenças registradas: a referência nunca quebra.

Para a turma: "Por que a coluna da relação fica no book (um user_id), e não no user (uma coluna books)?" (uma coluna guarda um valor escalar; o lado N é ilimitado — a "lista de ids" explodiria a célula. No 1:N, o filho aponta para o pai)
Para a turma: "Quem impede, hoje, um book do user 999?" (por enquanto, nada — a tabela nem existe. Depois do create_all: a FOREIGN KEY. O banco defende a relação sozinho, como defendeu o e-mail único na aula 04)

25 min Live-coding — o model Book e a relação no banco

Passo 1 — models.py: o Book e os dois lados da relação

Por quê: a tabela do quadro, declarada como classe — e, junto dela, a novidade que o SQL não tem: a relação navegável como objetos Python.

Em backend/models.py, adicione a linha books ao User, a classe Book e o import novo (Relationship):

from datetime import datetime

from sqlmodel import Field, Relationship, SQLModel


class User(SQLModel, table=True):
    id: int | None = Field(default=None, primary_key=True)
    name: str = Field(max_length=100)
    email: str = Field(max_length=255, unique=True)
    password: str = Field(max_length=255)
    created_at: datetime = Field(default_factory=datetime.now)

    books: list["Book"] = Relationship(back_populates="user")


class Book(SQLModel, table=True):
    id: int | None = Field(default=None, primary_key=True)
    title: str = Field(max_length=200)
    pages: int
    user_id: int = Field(foreign_key="user.id")
    created_at: datetime = Field(default_factory=datetime.now)

    user: User | None = Relationship(back_populates="books")

Linha a linha, contra o CREATE TABLE do quadro:

  • pages: int — sem Field(...): só o chamamos quando há algo a configurar (o INT não exige tamanho como o VARCHAR); a anotação basta;
  • user_id: int = Field(foreign_key="user.id") — a chave estrangeira. A string é "tabela.coluna" (nomes do banco, minúsculos, não os da classe): é a linha FOREIGN KEY (user_id) REFERENCES user(id) do quadro. Repare que ela é uma coluna comum — um inteiro — com uma configuração a mais;
  • books e user (Relationship) — não viram colunas. Existem só no mundo Python: são a relação materializada como objetos navegáveis — user.books é uma lista de Book; book.user é o dono. É o ORM da aula 04 cumprindo a promessa de traduzir os dois mundos: a FK é como o banco expressa a relação; o Relationship, como o Python a expressa. O F maiúsculo de Field e o R maiúsculo de Relationship marcam a diferença: um configura coluna, o outro não gera coluna nenhuma;
  • list["Book"] com o nome entre aspas — quando o User é lido, a classe Book ainda não existe (está mais abaixo no arquivo). As aspas dizem ao Python "resolva esse nome depois";
  • user: User | None — o mesmo "ou nada" do id: um Book recém-criado na memória ainda não teve o dono carregado do banco;
  • back_populates — declara que User.books e Book.user são os dois lados da mesma relação, e o ORM os mantém coerentes;
  • Convenções de sempre (ADR-0002): tabela no singular (book, do nome da classe), FK <tabela>_id, datetime com sufixo _at.

Passo 3 — integridade referencial ao vivo

Por quê: antes de escrever qualquer rota, ver o banco defendendo a relação sozinho — a cena vai se repetir pela API no próximo bloco.

Mac e Windows (dentro do cliente mysql) 
-- filho órfão: user 999 não existe
INSERT INTO book (title, pages, user_id)
VALUES ('Dom Casmurro', 208, 999);
-- ERROR 1452: Cannot add or update a child row:
--   a foreign key constraint fails

-- com um dono real, funciona
INSERT INTO book (title, pages, user_id)
VALUES ('Dom Casmurro', 208, 1);

-- pai com filhos: o user 1 tem um book
DELETE FROM user WHERE id = 1;
-- ERROR 1451: Cannot delete or update a parent row:
--   a foreign key constraint fails

-- limpe o book de teste: o CRUD da API começa do zero
DELETE FROM book;

Dois erros, uma regra: a referência nunca quebra. O 1452 recusa o órfão; o 1451 protege o pai. É o RESTRICT padrão da teoria — e ninguém escreveu um if sequer.

Checkpoint parcial: SHOW TABLES lista book e user; o SHOW CREATE TABLE book exibe a FOREIGN KEY (user_id) REFERENCES user (id); a turma viu o ERROR 1452 (órfão) e o 1451 (pai protegido); a tabela book terminou vazia (SELECT * FROM book; → Empty set) e existe pelo menos um User cadastrado.

10 min Teoria — o mapa REST se cumpre: rotas aninhadas

Pontos a explicar:

  • O mapa da aula 03 previu este dia: a linha GET /users/{user_id}/books — os Books de um User — aula 05 está no quadro desde então. Hoje ela sai do papel, junto com o restante do CRUD;
  • A URI conta a relação: o caminho de uma URI é hierárquico por definição (RFC 3986, seção 3.3) — /users/1/books lê-se "os books do user 1". A relação 1:N que acabou de virar chave estrangeira no banco aparece agora na própria URL: o mesmo desenho, em duas camadas do sistema;
  • Coleção aninhada, item plano: listar e criar acontecem na coleção do dono (GET/POST /users/{user_id}/books — criar um book sem dizer de quem ele é nem faria sentido); já GET/PUT/DELETE de um book específico usam /books/{book_id} — o id identifica o recurso sozinho, sem repetir o dono na URI. O ADR-0002 pede o mesmo nome de variável em rotas relacionadas: sempre book_id. (É nesse endereço plano que a aula 06 vai pendurar o POST /books/{book_id}/progress);
  • O prefixo /api se aposenta junto com a lista em memória: o mapa da aula 03 já registrava os endereços definitivos sem ele — /signup (aula 04) inaugurou o padrão;
  • A falha deliberada (ADR-0001): quem chama a rota escolhe o user_id. Sem autenticação, qualquer pessoa lê e escreve os livros de qualquer usuário — o aluno atento da aula 03 já tinha percebido. É deliberado: a aula 09 abre demonstrando esse ataque, e ele motiva o JWT. Anote no quadro, ao lado da senha em texto puro: "dívida: user_id na URL, sem autenticação".

O mapa de hoje — para o quadro:

Passo 6 — POST /users/{user_id}/books: o 500 anunciado

Por quê: o padrão da casa — provocar a falha antes de corrigi-la. Primeiro a versão ingênua, sem verificação nenhuma.

Depois de /health:

@app.post("/users/{user_id}/books", response_model=BookRead, status_code=201)
def create_book(user_id: int, book: BookCreate, session: Session = Depends(get_session)):
    new_book = models.Book(title=book.title, pages=book.pages, user_id=user_id)
    session.add(new_book)
    session.commit()
    session.refresh(new_book)
    return new_book

É o trio add/commit/refresh do signup, sem novidade — exceto o user_id, que vem do path e entra na FK. Teste no Swagger com o user 1:

POST /users/1/books
{"title": "Dom Casmurro", "pages": 208}

Resposta 201, com id gerado pelo banco e user_id: 1 — e o INSERT no echo. Agora o ataque combinado na teoria: POST /users/999/books. Resultado: 500 Internal Server Error — no terminal, IntegrityError com o ERROR 1452 do passo 3, agora atravessando a API. O banco segurou a integridade (nenhum órfão foi gravado), mas 5xx é o status errado: o problema está no pedido, não no servidor.

Qual 4xx? O recurso pai da URI — o user 999 — não existe: 404, pela tabela da aula 02. Adicione a verificação no início da função:

    user = session.get(models.User, user_id)
    if user is None:
        raise HTTPException(status_code=404, detail="User not found")

Novidade da aula: session.get(Model, pk) — busca por chave primária, o caminho curto quando se tem o id (o select().where() da aula 04 continua sendo o caminho para buscar por qualquer outra coluna). Reteste o 999: 404 "User not found". O banco continua de guarda (defesa em profundidade, como o UNIQUE vs o if do e-mail), mas a API agora responde com a verdade.

Passo 7 — GET /users/{user_id}/books: o relationship em ação

Por quê: a primeira leitura pela relação — nenhuma consulta escrita à mão.

@app.get("/users/{user_id}/books", response_model=list[BookRead])
def list_books(user_id: int, session: Session = Depends(get_session)):
    user = session.get(models.User, user_id)
    if user is None:
        raise HTTPException(status_code=404, detail="User not found")
    return user.books

user.books — o Relationship do passo 1 trabalhando: ao acessar o atributo, o ORM emite o SELECT dos books daquele dono (confira no echo: SELECT ... FROM book WHERE %s = book.user_id). O nome da técnica é lazy loading — a consulta só acontece quando (e se) a relação é usada.

Para a turma: "Sem o if user is None, o que GET /users/999/books devolveria?" (200 com [] — uma mentira: o cliente não distingue "user sem livros" de "user inexistente". O 404 aqui não trata erro do banco nenhum; trata a semântica)

Passo 9 — PUT /books/{book_id}: o UPDATE que ninguém escreve

Por quê: a última peça conceitual do ORM na aula — mutação rastreada.

@app.put("/books/{book_id}", response_model=BookRead)
def update_book(book_id: int, book: BookCreate, session: Session = Depends(get_session)):
    stored_book = session.get(models.Book, book_id)
    if stored_book is None:
        raise HTTPException(status_code=404, detail="Book not found")
    stored_book.title = book.title
    stored_book.pages = book.pages
    session.commit()
    session.refresh(stored_book)
    return stored_book

Repare no que não existe: nenhum session.update(). O objeto veio da sessão; basta mudar os atributos — o Unit of Work da aula 04 rastreia as mudanças e o commit emite o UPDATE sozinho (confira no echo). O corpo reaproveita BookCreate, como na aula 03: atualizar envia os mesmos campos que criar.

Passo 10 — DELETE /books/{book_id}

@app.delete("/books/{book_id}", status_code=204)
def delete_book(book_id: int, session: Session = Depends(get_session)):
    book = session.get(models.Book, book_id)
    if book is None:
        raise HTTPException(status_code=404, detail="Book not found")
    session.delete(book)
    session.commit()

session.delete anota a remoção; o commit a executa. Resposta 204 sem corpo, como na aula 03 — esse contrato não mudou; só a prateleira.

15 min Exercício em sala

Individual — a busca que ficou para trás. Na aula 02, GET /api/books?name=hobbit filtrava a lista em memória; a busca se perdeu na demolição. Reconstrua-a sobre o banco:

  1. Adicione à rota de listagem o query param opcional title: str = "" (o padrão da aula 02);
  2. Se vazio, devolva user.books como antes; senão, consulte com select(models.Book) filtrando pelo dono e pelo título — duas condições no mesmo where;
  3. Para "contém o trecho", use models.Book.title.contains(title); para executar e receber a lista, session.exec(...).all();
  4. Teste no Swagger (?title=dom) e confira no echo o SQL emitido — que operador SQL apareceu?

Gabarito (para o professor):

@app.get("/users/{user_id}/books", response_model=list[BookRead])
def list_books(user_id: int, title: str = "", session: Session = Depends(get_session)):
    user = session.get(models.User, user_id)
    if user is None:
        raise HTTPException(status_code=404, detail="User not found")
    if title == "":
        return user.books
    statement = select(models.Book).where(
        models.Book.user_id == user_id,
        models.Book.title.contains(title),
    )
    return session.exec(statement).all()

Pontos do gabarito: .all() é o irmão do .first() da aula 04 — devolve todos os objetos, não só o primeiro; nomear o statement antes de executar mantém a linha legível, como no signup; duas condições no where viram AND; contains vira LIKE '%dom%' no echo. Bônus de observação: ?title=dom acha "Dom Casmurro" — a collation padrão do MySQL não distingue maiúsculas, de graça (na aula 02, precisamos do .lower() à mão).

Circule pela sala: o erro clássico é esquecer a condição do user_id no where — a busca passa a vazar livros de todos os usuários. Vale apontar a ironia: é exatamente a dívida do quadro, só que por acidente.

  • Síntese: uma relação 1:N liga um pai a muitos filhos, e sua materialização é a chave estrangeira — que mora sempre no lado N (Chen, 1976; Date, 8ª ed.); a integridade referencial é o banco garantindo que a referência nunca quebra (órfão recusado, pai protegido — ERROR 1452 e 1451); no SQLModel, Field(foreign_key=...) declara a coluna e Relationship/back_populates dão à relação a forma de objetos navegáveis (user.books, com lazy loading); o CRUD de Books renasceu sobre o MySQL nas rotas do mapa da aula 03 — coleção aninhada no dono, item plano — com session.get para busca por chave primária e o Unit of Work emitindo o UPDATE sozinho; e o quadro ganhou a segunda dívida: user_id na URL, sem autenticação;
  • Gancho para a aula 06: "Um Book cadastrado ainda é uma foto parada — 208 páginas, e daí? A pergunta que o projeto existe para responder é 'em que página você está?'. Na próxima aula entra o Reading Update: a segunda relação 1:N do banco — desta vez o pai é o Book —, a rota POST /books/{book_id}/progress no endereço plano que deixamos pronto hoje, e a porcentagem de leitura calculada do update mais recente, sem nenhum campo de status gravado."
