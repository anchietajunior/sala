Aula 05 — Users e autenticação com JWT

Duração: ~2h (densa — administre o relógio nos checkpoints)  ·  Branch: aula-05-users-e-autenticacao-com-jwt

Temas teóricos: relação 1:N e chave estrangeira (aprofundamento do T-7); formas de autenticação e anatomia de um JWT [T-8]

Objetivos — ao final, o aluno consegue:

  • Declarar o model User e a relação 1:N com chave estrangeira obrigatória de books para users;
  • Implementar POST /signup guardando apenas o hash da senha (bcrypt) e explicar por que senha nunca se armazena em texto puro;
  • Comparar as formas de autenticação — cookies e sessions vs tokens — e justificar a escolha do JWT nesta aplicação;
  • Descrever a anatomia de um JWT (header, payload, assinatura) e os claims que ele carrega;
  • Implementar POST /login emitindo JWT e proteger o CRUD de books: cada usuário só enxerga e altera os próprios livros;
  • Organizar o backend por tipo de arquivo — schemas.py e routers/ por recurso — com o main.py como ponto de entrada.

5 min Ponto de partida

Abra o backend na tela e o Swagger ao lado. O CRUD de Books persiste no MySQL — restart não apaga nada, o banco gera os ids. Mas faça a demonstração incômoda: abra uma janela anônima do navegador, chame GET /api/books e apague um livro pelo Swagger. Funciona — para qualquer um.

O código tem dois buracos, e eles são o assunto de hoje:

  • Livro não tem dono. A tabela books não sabe de quem é cada linha — não existe sequer o conceito de usuário no sistema;
  • A API não sabe quem chama. Qualquer requisição lista, cria, altera e apaga qualquer livro.

São dois problemas distintos com nomes próprios: posse (de quem é o dado?) — resolvida no banco, com uma relação entre tabelas — e identidade (quem está pedindo?) — resolvida na API, com autenticação. A aula constrói os dois, nessa ordem.

15 min Teoria — a relação 1:N e a chave estrangeira

Pontos a explicar:

  • Origem: a modelagem por entidades e relacionamentos foi formalizada por Peter Chen no artigo "The Entity-Relationship Model — Toward a Unified View of Data" (ACM TODS, 1976): entidades (User, Book) se ligam por relacionamentos com cardinalidade — 1:1, 1:N, N:M;
  • Nosso caso é 1:N: um User possui vários Books; cada Book pertence a exatamente um User. É a regra do glossário do projeto: "Book pertence exclusivamente ao User que o cadastrou";
  • Como o modelo relacional expressa isso: com uma chave estrangeira (foreign key) — uma coluna na tabela do lado N (books.user_id) que guarda a chave primária do lado 1 (users.id). A relação não é um desenho: é uma coluna;
  • Integridade referencial (Date, An Introduction to Database Systems): a FK é uma constraint como o NOT NULL da aula do banco — o MySQL recusa um books.user_id que não exista em users.id. Livro órfão não entra;
  • Obrigatória por decisão de domínio: a coluna nasce NOT NULL — não existe livro sem dono neste sistema. Constraint é regra de negócio que o banco defende sozinho.
Para a turma: "Por que a coluna da relação fica em books e não em users?" (o lado N aponta para o lado 1: cada livro tem um dono — cabe numa coluna; um user tem vários livros — não caberia. A coluna mora onde a resposta é única)

25 min Live-coding 1 — User, a FK e o signup com hash

Passo 1 — instalar o bcrypt

Por quê: o signup vai guardar senha, e senha não se armazena — armazena-se o hash dela. O algoritmo da disciplina é o bcrypt (Provos & Mazières, USENIX 1999): uma função de mão única, com salt embutido e custo computacional ajustável — lenta de propósito, para inviabilizar força bruta.

Mac e Windows (venv ativo, dentro de projeto/backend) 
pip install bcrypt "pydantic[email]"
pip freeze > requirements.txt
  • Mão única: do hash não se recupera a senha — no login, calcula-se o hash do que o usuário digitou e comparam-se os hashes;
  • Salt embutido: duas senhas iguais geram hashes diferentes — tabelas pré-computadas de hash não funcionam;
  • Quem tiver acesso ao banco verá apenas o hash — e é assim que deve ser;
  • pydantic[email] — a sintaxe de extra do pip: instala o Pydantic com o validador de e-mail (email-validator), que o schema do cadastro vai usar.

Passo 2 — models.py: o User e a chave estrangeira

Por quê: a relação da teoria, agora em código — o lado 1 (User) e a coluna que o lado N aponta para ele.

Em backend/models.py, adicione o import do ForeignKey e o model User, e dê ao Book a coluna da relação:

from datetime import datetime

from sqlalchemy import ForeignKey, String, func
from sqlalchemy.orm import Mapped, mapped_column

from database import Base


class User(Base):
    __tablename__ = "users"

    id: Mapped[int] = mapped_column(primary_key=True)
    name: Mapped[str] = mapped_column(String(100))
    email: Mapped[str] = mapped_column(String(255), unique=True)
    password: Mapped[str] = mapped_column(String(255))
    created_at: Mapped[datetime] = mapped_column(server_default=func.now())


class Book(Base):
    __tablename__ = "books"

    id: Mapped[int] = mapped_column(primary_key=True)
    name: Mapped[str] = mapped_column(String(255))
    user_id: Mapped[int] = mapped_column(ForeignKey("users.id"))
    created_at: Mapped[datetime] = mapped_column(server_default=func.now())

Linha a linha do que é novo:

  • O User é um model como o Book: mesma Base, mesma anatomia. Dois campos pedem atenção: email com unique=True — o banco recusa dois cadastros com o mesmo e-mail (a constraint UNIQUE da teoria do banco, agora com papel de regra de negócio) — e password, que vai guardar o hash, nunca a senha (por isso String(255): hash de bcrypt é texto longo);
  • user_id: Mapped[int] = mapped_column(ForeignKey("users.id")) — a relação inteira numa linha: a coluna guarda um inteiro que precisa existir em users.id. Sem | None no tipo, é NOT NULL: não existe livro sem dono;
  • ForeignKey recebe "users.id" — tabela.coluna, os nomes do banco, não os da classe.

Passo 4 — os schemas do Book: validação na entrada, contrato na saída

Por quê: a tabela mudou e os schemas do Book precisam acompanhar — e ainda devem uma validação de verdade: o BookCreate de hoje aceita até nome vazio, e a regra que a coluna do banco impõe deveria valer também na porta da API.

No main.py, ajuste o import do Pydantic e os dois schemas do Book:

from pydantic import BaseModel, ConfigDict, Field
class BookCreate(BaseModel):
    name: str = Field(min_length=1, max_length=255)


class BookRead(BaseModel):
    model_config = ConfigDict(from_attributes=True)

    id: int
    name: str
    user_id: int

Três decisões para verbalizar:

  • Validação na criação: Field declara as regras do campo — min_length=1 recusa nome vazio e max_length=255 espelha o String(255) da coluna. A fronteira da API passa a exigir o que a coluna exige: quem erra recebe 422 com a explicação do campo, em vez de um erro cru do banco;
  • O PUT usa o mesmo BookCreate — a atualização ganha a mesma validação, sem escrever nada a mais;
  • O contrato de saída ganha o dono: user_id entra no BookRead — a relação criada no banco aparece na resposta da API. O created_at continua fora: o contrato publica o que o cliente precisa.

Teste no Swagger: POST /api/books com {"name": ""} → 422, apontando o min_length — a validação age antes de a função da rota executar. Agora tente um POST válido e deixe a falha acontecer: IntegrityError — a coluna user_id é NOT NULL e a rota não tem dono para dar ao livro. O banco acabou de exigir a segunda metade da aula: não existe livro sem dono, e ainda não sabemos quem chama a API.

Passo 5 — os schemas do User e o POST /signup

Por quê: para um livro ter dono, o dono precisa existir — o cadastro de usuários é o pré-requisito de tudo que vem depois.

No main.py, os schemas primeiro, junto aos de Book — com o import do Pydantic ganhando o EmailStr:

from pydantic import BaseModel, ConfigDict, EmailStr, Field
class UserCreate(BaseModel):
    name: str = Field(min_length=1, max_length=100)
    email: EmailStr = Field(max_length=255)
    password: str = Field(min_length=8, max_length=72)


class UserRead(BaseModel):
    model_config = ConfigDict(from_attributes=True)

    id: int
    name: str
    email: str

A entrada nasce validada, como a do Book:

  • name espelha o String(100) da coluna — não-vazio, até 100;
  • EmailStr valida o formato do e-mail (é o email-validator do passo 1 em ação): e-mail malformado responde 422 antes de a rota executar. O formato é problema do schema; a unicidade continua sendo do banco (UNIQUE);
  • password entre 8 e 72: o mínimo é política de senha; o máximo é um limite real do bcrypt — acima de 72 bytes a biblioteca levanta erro, e o schema barra antes, com 422 explicativo em vez de 500.

E o UserRead é o caso mais forte de response_model que o projeto já viu: a senha entra no UserCreate e nunca sai no UserRead — nem o hash. O contrato de saída é o filtro.

Agora a rota, com o hash na frente do banco. Import no topo do main.py: from security import hash_password — o arquivo security.py nasce no passo seguinte; escreva a rota primeiro para a turma sentir a falta dele:

@app.post("/signup", response_model=UserRead, status_code=201)
def signup(user: UserCreate, session: Session = Depends(get_session)):
    statement = select(models.User).where(models.User.email == user.email)
    existing_user = session.scalars(statement).first()
    if existing_user is not None:
        raise HTTPException(status_code=409, detail="Email already registered")
    new_user = models.User(name=user.name, email=user.email,
                           password=hash_password(user.password))
    session.add(new_user)
    session.commit()
    session.refresh(new_user)
    return new_user
  • A consulta preventiva devolve 409 Conflict para e-mail repetido: o pedido é válido, mas conflita com o estado atual do recurso — erro do cliente (4xx), não do servidor;
  • Se duas requisições com o mesmo e-mail chegarem ao mesmo tempo, ambas passam pelo if — a última defesa é o UNIQUE no banco. É para isso que a constraint existe mesmo com a verificação no Python;
  • hash_password(user.password) — a senha em texto puro existe só em trânsito, dentro desta função; o que desce para o banco é o hash.

Passo 6 — security.py, parte 1: o hash

Por quê: tudo que é segurança — hash, verificação, e daqui a pouco tokens — merece um arquivo próprio, como a conexão mereceu o database.py (estrutura por tipo de arquivo, ADR-0002).

Crie backend/security.py:

import bcrypt


def hash_password(password: str) -> str:
    return bcrypt.hashpw(password.encode(), bcrypt.gensalt()).decode()


def verify_password(password: str, hashed: str) -> bool:
    return bcrypt.checkpw(password.encode(), hashed.encode())
  • gensalt() gera o salt; hashpw devolve o hash com o salt embutido — por isso não guardamos o salt em coluna separada;
  • encode()/decode(): o bcrypt trabalha com bytes; o banco guarda texto;
  • checkpw refaz o hash da senha digitada usando o salt embutido e compara — é a verificação de mão única da teoria (o verify_password entra em cena no login).

Teste no Swagger: POST /signup com {"name": "Machado de Assis", "email": "machado@exemplo.com", "password": "segredo123"} → 201 com id, name e email — sem senha. Repita o mesmo corpo: 409. E a cena mais importante da parte 1, no cliente mysql:

SELECT id, email, password FROM users;

A coluna password mostra $2b$12$... — o hash, ilegível. Nem quem tem o banco inteiro nas mãos lê a senha de alguém. Cadastre um segundo usuário com a mesma senha e compare: os hashes são diferentes — o salt trabalhando.

Checkpoint parcial: tabelas users e books recriadas com a FK visível no SHOW CREATE TABLE books; signup respondendo 201 sem senha e 409 no e-mail repetido; hashes diferentes para senhas iguais no SELECT.

25 min Teoria [T-8] — identidade: de cookies a JWT

Pontos a explicar:

  • O problema: o HTTP é stateless — cada requisição chega sozinha, sem memória da anterior. O usuário fez login às 10h; às 10h01, o servidor já não sabe quem ele é. Toda autenticação web é uma resposta a essa amnésia;
  • Cookies + sessions — a resposta clássica: o cookie foi criado por Lou Montulli (Netscape, 1994; padronizado na RFC 6265, 2011). No login, o servidor cria um registro de sessão (em memória ou banco) e devolve ao navegador um cookie com o id dessa sessão; o navegador o reenvia sozinho a cada requisição. O estado mora no servidor: o cookie é só uma chave de armário;
  • Tokens — a resposta moderna para APIs: no login, o servidor emite um token autocontido, que o próprio cliente guarda e envia explicitamente no header Authorization. O estado mora no token: o servidor não guarda sessão nenhuma — ele verifica o token a cada requisição;
  • JWT — JSON Web Token (RFC 7519, IETF, 2015): "um meio compacto e seguro para URLs de representar claims a serem transferidos entre duas partes". São três partes separadas por ponto — header.payload.signature:
    • header: o algoritmo de assinatura ({"alg": "HS256", "typ": "JWT"});
    • payload: os claims — afirmações sobre o portador. Os registrados na RFC têm nome curto: sub (subject: quem é — nosso user.id), exp (expiration: até quando vale), iat (issued at: quando foi emitido);
    • signature: HMAC-SHA256 de header+payload com uma chave secreta que só o servidor conhece. Alterou um caractere do payload? A assinatura não bate e o token é recusado.
  • Base64url não é criptografia: header e payload são apenas codificados — qualquer um decodifica e lê (mostre em jwt.io). A assinatura garante integridade e origem, não sigilo. Consequência prática: nunca colocar senha ou dado sensível no payload;
  • Por que JWT nesta aplicação: o backend é uma API que servirá um frontend React — cliente e servidor conversam por requisições explícitas, e o token viaja no header Authorization: Bearer <token>. Sem sessão no servidor, qualquer instância da API valida o token apenas com a chave secreta — não há armário de sessões para consultar nem sincronizar;
  • Honestidade intelectual — o custo do stateless: um JWT emitido não pode ser "apagado" do lado do servidor: ele vale até o exp. Por isso tokens têm vida curta. Cookies+sessions continuam sendo uma escolha excelente para aplicações renderizadas no servidor — a escolha aqui é pela arquitetura do projeto, não porque JWT "é melhor".

Comparação para o quadro:

Para a turma: "O payload do JWT é legível por qualquer um. Por que ainda assim ele autentica?" (porque autenticar não é esconder — é provar origem: só o servidor tem a chave que produz aquela assinatura. Ler é permitido; forjar, não)
Para a turma: "Se o token diz quem você é, o que acontece se você alterar o sub para o id de outra pessoa?" (a assinatura deixa de bater — o servidor recalcula o HMAC e recusa. É o que o live-coding vai demonstrar)

Passo 8 — security.py, parte 2: emitir e verificar tokens

Por quê: as duas metades da autenticação — o login emite; toda rota protegida verifica.

Complete o backend/security.py:

from datetime import datetime, timedelta, timezone

import bcrypt
import jwt
from fastapi import Depends, HTTPException
from fastapi.security import HTTPAuthorizationCredentials, HTTPBearer
from sqlalchemy.orm import Session

import models
from database import get_session

SECRET_KEY = "change-me-in-production-32-bytes-min!"
ALGORITHM = "HS256"
TOKEN_LIFETIME = timedelta(hours=2)

bearer_scheme = HTTPBearer(auto_error=False)


def hash_password(password: str) -> str:
    return bcrypt.hashpw(password.encode(), bcrypt.gensalt()).decode()


def verify_password(password: str, hashed: str) -> bool:
    return bcrypt.checkpw(password.encode(), hashed.encode())


def create_access_token(user_id: int) -> str:
    payload = {
        "sub": str(user_id),
        "exp": datetime.now(timezone.utc) + TOKEN_LIFETIME,
    }
    return jwt.encode(payload, SECRET_KEY, algorithm=ALGORITHM)


def get_current_user(
    credentials: HTTPAuthorizationCredentials | None = Depends(bearer_scheme),
    session: Session = Depends(get_session),
) -> models.User:
    if credentials is None:
        raise HTTPException(status_code=401, detail="Not authenticated")
    try:
        payload = jwt.decode(credentials.credentials, SECRET_KEY,
                             algorithms=[ALGORITHM])
    except jwt.InvalidTokenError:
        raise HTTPException(status_code=401, detail="Invalid or expired token")
    user = session.get(models.User, int(payload["sub"]))
    if user is None:
        raise HTTPException(status_code=401, detail="Invalid or expired token")
    return user

Peça calma e leia de cima para baixo:

  • SECRET_KEY — a chave que assina tudo: quem a tem, emite tokens válidos. Em produção ela vem de variável de ambiente e nunca do código; aqui fica visível por didática — diga isso em voz alta. O HMAC-SHA256 exige chave de pelo menos 32 bytes (RFC 7518) — com menos, o PyJWT emite um aviso no terminal;
  • TOKEN_LIFETIME — o exp: a resposta ao problema da revogação. Token roubado vale, no pior caso, até expirar;
  • create_access_token — monta o payload com os claims da teoria (sub como texto, por exigência da RFC; exp em UTC) e assina. Uma linha do PyJWT: jwt.encode;
  • bearer_scheme — o HTTPBearer extrai o token do header Authorization: Bearer <token> e liga o botão Authorize do Swagger. Com auto_error=False, a ausência do header cai no nosso if — e respondemos 401, o código de "quem é você?" (403 é outro assunto: "sei quem é, e não pode" — fica para a aula de autorização);
  • get_current_user — a peça central da aula: uma dependency como o get_session. Verifica a assinatura e a validade (jwt.decode levanta InvalidTokenError para assinatura errada ou token vencido), busca o User do sub e o devolve. A rota que a declarar recebe o usuário logado, pronto — toda a mecânica de token fica fora dela.

Passo 9 — POST /login

Por quê: a porta de entrada — troca credenciais válidas por um token.

No main.py, ajuste o import da segurança e acrescente os schemas e a rota:

from security import (create_access_token, get_current_user, hash_password,
                      verify_password)
class LoginRequest(BaseModel):
    email: EmailStr
    password: str


class TokenResponse(BaseModel):
    access_token: str
    token_type: str = "bearer"
@app.post("/login", response_model=TokenResponse)
def login(credentials: LoginRequest, session: Session = Depends(get_session)):
    statement = select(models.User).where(models.User.email == credentials.email)
    user = session.scalars(statement).first()
    if user is None or not verify_password(credentials.password, user.password):
        raise HTTPException(status_code=401, detail="Invalid email or password")
    return TokenResponse(access_token=create_access_token(user.id))
  • O verify_password fecha o ciclo do bcrypt: hash do que foi digitado contra o hash guardado;
  • Uma única mensagem de erro para e-mail inexistente e senha errada — responder "e-mail não cadastrado" entregaria a um atacante a lista de quem tem conta;
  • token_type: "bearer" — vocabulário do header: bearer token, o token "ao portador": quem o carrega, é. Por isso ele não se compartilha.

Teste no Swagger: POST /login com as credenciais do Machado → 200 com o token. Copie o token, cole em jwt.io e mostre: header e payload legíveis (sub, exp), assinatura verificável só com a SECRET_KEY. Troque uma letra do payload no próprio site e aponte: Invalid Signature.

Passo 10 — o CRUD ganha dono

Por quê: o momento que junta as duas metades da aula — a FK (posse) e o token (identidade). Cada rota de books passa a declarar get_current_user e a operar só sobre os livros do usuário logado.

Substitua as cinco rotas de books no main.py:

@app.get("/api/books", response_model=list[BookRead])
def list_books(name: str = "", session: Session = Depends(get_session),
               current_user: models.User = Depends(get_current_user)):
    statement = select(models.Book).where(models.Book.user_id == current_user.id)
    if name != "":
        statement = statement.where(models.Book.name.contains(name))
    return session.scalars(statement).all()


@app.get("/api/books/{book_id}", response_model=BookRead)
def read_book(book_id: int, session: Session = Depends(get_session),
              current_user: models.User = Depends(get_current_user)):
    book = session.get(models.Book, book_id)
    if book is None or book.user_id != current_user.id:
        raise HTTPException(status_code=404, detail="Book not found")
    return book


@app.post("/api/books", response_model=BookRead, status_code=201)
def create_book(book: BookCreate, session: Session = Depends(get_session),
                current_user: models.User = Depends(get_current_user)):
    new_book = models.Book(name=book.name, user_id=current_user.id)
    session.add(new_book)
    session.commit()
    session.refresh(new_book)
    return new_book


@app.put("/api/books/{book_id}", response_model=BookRead)
def update_book(book_id: int, book: BookCreate,
                session: Session = Depends(get_session),
                current_user: models.User = Depends(get_current_user)):
    stored_book = session.get(models.Book, book_id)
    if stored_book is None or stored_book.user_id != current_user.id:
        raise HTTPException(status_code=404, detail="Book not found")
    stored_book.name = book.name
    session.commit()
    session.refresh(stored_book)
    return stored_book


@app.delete("/api/books/{book_id}", status_code=204)
def delete_book(book_id: int, session: Session = Depends(get_session),
                current_user: models.User = Depends(get_current_user)):
    book = session.get(models.Book, book_id)
    if book is None or book.user_id != current_user.id:
        raise HTTPException(status_code=404, detail="Book not found")
    session.delete(book)
    session.commit()

O IntegrityError do passo 4 morre aqui: o POST voltou a funcionar, agora com dono. As decisões para verbalizar:

  • A rota não mexe com token. Ela declara Depends(get_current_user) e recebe um models.User — a mesma inversão de controle do get_session, agora carregando identidade;
  • Na listagem, o filtro é pelo dono: where(models.Book.user_id == current_user.id) — a FK e o token se encontram nesta linha. O filtro por nome continua, encadeado;
  • No POST, o cliente não escolhe o dono: o corpo continua só com name; o user_id vem do token. Se viesse do corpo, qualquer um cadastraria livros em nome de qualquer um;
  • Livro dos outros responde 404, não 403: book.user_id != current_user.id cai na mesma resposta de "não existe" — a API não confirma a existência de um recurso que não é seu. Para quem pede, livro alheio e livro inexistente são indistinguíveis;
  • /health fica público de propósito: é rota de infraestrutura, não de dados.

Passo 11 — a prova com dois usuários

Por quê: autorização só se demonstra com dois atores.

  1. Sem token (clique em Logout no Authorize, se preciso): GET /api/books → 401 — a API agora exige identidade;
  2. POST /login com o Machado, copie o access_token, clique em Authorize no Swagger e cole-o. Crie dois livros e liste — eles vêm com user_id 1;
  3. Cadastre uma segunda usuária (clarice@exemplo.com), faça login com ela e troque o token no Authorize. GET /api/books → lista vazia: os livros do Machado existem, mas não para ela;
  4. Ainda como Clarice, tente GET /api/books/1 (livro do Machado) → 404. Idem PUT e DELETE;
  5. No mysql: SELECT id, name, user_id FROM books; — as linhas de cada dono, lado a lado, e o Swagger mostrando só as do token ativo.

Passo 12 — organizar o backend: schemas.py e routers/

Por quê: o main.py acumulou seis schemas e oito rotas de dois recursos diferentes — virou o arquivo onde tudo mora. A estrutura por tipo de arquivo (decisão do ADR-0002 para quando este momento chegasse) separa as responsabilidades: os schemas num módulo, as rotas de cada recurso num router próprio, e o main.py como puro ponto de entrada.

A estrutura final:

backend/
├── main.py          ← ponto de entrada: app, create_all, include_router
├── database.py      ← conexão, Base e sessão do ORM
├── models.py        ← as tabelas (User, Book)
├── schemas.py       ← todas as classes Pydantic
├── security.py      ← hash, token e get_current_user
└── routers/
    ├── __init__.py  ← vazio: torna a pasta um pacote
    └── users.py / books.py ← as rotas de cada recurso

Crie backend/schemas.py e mova para lá as seis classes Pydantic, com o import que as serve — nada muda nelas. Depois crie backend/routers/__init__.py (vazio) e backend/routers/books.py. A peça nova é o APIRouter: um "mini-app" que registra rotas fora do main.py, com um prefixo e uma tag declarados uma vez para o recurso inteiro:

from fastapi import APIRouter, Depends, HTTPException
from sqlalchemy import select
from sqlalchemy.orm import Session

import models
from database import get_session
from schemas import BookCreate, BookRead
from security import get_current_user

router = APIRouter(prefix="/api/books", tags=["books"])

Mova as cinco rotas de books, trocando @app por @router e removendo o prefixo de cada path — ele agora existe num lugar só:

@router.get("", response_model=list[BookRead])        # era @app.get("/api/books")
@router.get("/{book_id}", response_model=BookRead)    # era /api/books/{book_id}
@router.post("", response_model=BookRead, status_code=201)
@router.put("/{book_id}", response_model=BookRead)
@router.delete("/{book_id}", status_code=204)

Idem backend/routers/users.py com o signup e o login — sem prefixo, porque /signup e /login são ações de topo, mas com a tag do recurso:

router = APIRouter(tags=["users"])

E o main.py encolhe para o papel de ponto de entrada:

from fastapi import FastAPI

import models
from database import Base, engine
from routers import books, users

Base.metadata.create_all(engine)

app = FastAPI()

app.include_router(users.router)
app.include_router(books.router)


@app.get("/health")
def read_health():
    return {"status": "Ok"}
  • prefix — o nome padrão do recurso, declarado uma vez: toda rota do arquivo nasce sob /api/books;
  • tags — o Swagger se reorganiza em seções por recurso: users e books, em vez de uma lista única;
  • include_router — o main.py não conhece rota nenhuma: registra os recursos e sobe o app. O /health fica nele por ser rota de infraestrutura, não de recurso;
  • Abra o Swagger e compare: nenhuma URL mudou — a reorganização é interna. Refatorar é isto: mover sem mudar comportamento.

10 min Exercício em sala

Individual — uma rota nova usando a peça central da aula:

  1. Crie GET /api/users/me, que devolve o usuário logado no formato UserRead;
  2. Teste com o token de cada um dos dois usuários — a resposta muda com o token, sem nenhum parâmetro na URL;

Gabarito (para o professor): a rota mora em routers/users.py — é o router do recurso. O arquivo ainda não importa get_current_user; o aluno precisa acrescentá-lo ao import do security.

@router.get("/api/users/me", response_model=UserRead)
def read_current_user(current_user: models.User = Depends(get_current_user)):
    return current_user

O corpo tem uma linha: a dependency já fez todo o trabalho. É a demonstração de que identidade virou infraestrutura — as rotas apenas a declaram. Erro clássico a circular: esquecer o response_model e devolver o hash da senha na resposta — apontar que o UserRead é o que impede isso.

5 min Fechamento

  • Síntese: a relação 1:N (Chen, 1976) vira uma coluna com chave estrangeira — books.user_id — que o banco defende com integridade referencial: não existe livro sem dono; senha não se armazena — armazena-se o hash (bcrypt: mão única, salt, custo); o HTTP é stateless e a autenticação responde a isso — cookies+sessions guardam o estado no servidor, tokens o carregam consigo; o JWT (RFC 7519) é assinado, não cifrado: header.payload.signature, claims sub e exp, e a assinatura HMAC com a chave secreta é o que impede a falsificação; no código, o login emite o token e a dependency get_current_user o verifica — e o CRUD inteiro passou a operar sobre os livros do usuário logado, com o dono vindo do token e nunca do corpo da requisição; por fim, o backend se organizou por tipo de arquivo — schemas num módulo, cada recurso com seu router (prefixo e tag próprios) e o main.py como puro ponto de entrada.
