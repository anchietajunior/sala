10 min Teoria — por que a orientação a objetos existe

Origem. A POO nasce em Oslo, no Norwegian Computing Center, com a linguagem Simula 67, de Ole-Johan Dahl e Kristen Nygaard (1967). O problema deles era simulação: representar navios, filas e portos, em que cada entidade simulada tem estado próprio e comportamento próprio. Foi para isso que inventaram class, objeto e herança — e por esse trabalho receberam o Prêmio Turing de 2001.

O termo. Object-oriented programming foi cunhado por Alan Kay, no Xerox PARC, e materializado na linguagem Smalltalk (1972). Para Kay, o centro da ideia não são as classes, e sim as mensagens trocadas entre objetos que escondem seu estado interno.

Definição formal (Grady Booch, Object-Oriented Analysis and Design with Applications, 3ª ed., 2007):

"An object has state, behavior, and identity."

Estado (os dados que ele guarda), comportamento (o que ele sabe fazer) e identidade (ele é ele mesmo, distinto de outro objeto com os mesmos dados).

Propósito — o problema concreto que resolve. Sem POO, dados e comportamento andam separados:

book = {"title": "Clean Code", "pages": 464, "current_page": 120}


def progress_percentage(book):
    return book["current_page"] / book["pages"] * 100
  • Nada garante que o dicionário tenha as chaves certas — book["titulo"] só explode em produção;
  • A função que entende de livro mora longe do dado de livro; num arquivo com 40 funções, ninguém sabe quais servem para quê;
  • Qualquer parte do programa pode inventar um campo novo no dicionário.

A POO junta estado e comportamento numa única unidade e coloca uma fronteira em volta dela.

Em Python isso não é opcional nem exótico: a linguagem é orientada a objetos desde a origem (Guido van Rossum, 1991). int, str, list e até funções e módulos são objetos. Demonstre no interpretador: (5).__class__, "abc".upper(), type(print).
Para a turma: "Se todo dicionário aceita qualquer chave, quem garante que o livro que chega na sua função tem pages? (resposta honesta: ninguém — e é por isso que existe Pydantic, que veremos na aula 03)"

Passo 1 — a classe como molde

Por quê: a classe descreve o que todo livro tem e faz; o objeto é um livro concreto.

class Book:
    def __init__(self, title, pages):
        self.title = title
        self.pages = pages
        self.current_page = 0

    def progress_percentage(self):
        return self.current_page / self.pages * 100

Explique linha a linha, sem pressa:

  • class Book: — declara um novo tipo. Por convenção (PEP 8), nomes de classe em CapWords.
  • __init__ — o inicializador: roda automaticamente quando um objeto é criado, e sua função é dar o estado inicial ao objeto. Os nomes cercados por dois sublinhados são os dunder methods ("double underscore"), chamados pela linguagem, não por nós.
  • self — o próprio objeto, recebido como primeiro parâmetro. Não é palavra reservada; é convenção universal.
  • self.title = title — cria o atributo no objeto. Sem self., seria só uma variável local que morre no fim da função.
  • progress_percentage — um método: função que pertence à classe e recebe o objeto em self.

Passo 2 — instanciar e observar a independência dos objetos

clean_code = Book("Clean Code", 464)
pragmatic = Book("The Pragmatic Programmer", 352)

clean_code.current_page = 120

print(clean_code.progress_percentage())   # 25.86...
print(pragmatic.current_page)             # 0 — estado independente
print(type(clean_code))                   # <class '__main__.Book'>
print(isinstance(clean_code, Book))       # True
print(clean_code is pragmatic)            # False — identidade

Amarre com a definição de Booch, ponto a ponto: estado (title, pages, current_page), comportamento (progress_percentage), identidade (clean_code is pragmatic é falso mesmo que todos os campos fossem iguais).

Passo 3 — desmistificar o self

Por quê: é o ponto que mais confunde a turma, e a explicação cabe em duas linhas.

print(clean_code.progress_percentage())        # forma usual
print(Book.progress_percentage(clean_code))    # exatamente a mesma chamada

Diga a frase que resolve o assunto: objeto.metodo() é açúcar sintático para Classe.metodo(objeto). O self não é mágica — é o primeiro argumento, passado pelo interpretador.

Passo 4 — __repr__: como o objeto se apresenta

    def __repr__(self):
        return f"Book(title={self.title!r}, pages={self.pages})"

Antes: print(clean_code) mostra <__main__.Book object at 0x104f2b1d0>. Depois: Book(title='Clean Code', pages=464). Explique que a linguagem procura métodos com nomes convencionados — __repr__, __str__, __len__, __eq__ — e que implementá-los faz o objeto se comportar como um tipo nativo.

Passo 5 — atributo de classe × atributo de instância

class Book:
    genre = "unknown"          # atributo de classe: existe um só, compartilhado

    def __init__(self, title, pages):
        self.title = title     # atributo de instância: um por objeto
        ...

Agora a armadilha — vale digitar e rodar, porque ninguém acredita antes de ver. Um atributo de classe mutável (uma lista, um dicionário) é um objeto só, compartilhado por todas as instâncias:

class Book:
    tags = []                  # mutável e compartilhado — a armadilha

    def __init__(self, title):
        self.title = title


clean_code = Book("Clean Code")
pragmatic = Book("The Pragmatic Programmer")

clean_code.tags.append("favorito")

print(clean_code.tags)     # ['favorito']
print(pragmatic.tags)      # ['favorito'] — mudou junto!
print(clean_code.tags is pragmatic.tags)   # True — é a MESMA lista

A correção é criar a lista por objeto, dentro do __init__:

class Book:
    def __init__(self, title):
        self.title = title
        self.tags = []         # uma lista nova a cada objeto
A regra geral: valor padrão que precisa ser novo a cada objeto não pode morar no corpo da classe — tem de ser criado na inicialização. Guardem a armadilha; ela reaparece na aula 04, quando um campo precisar da data e hora do momento em que cada registro é criado. Não antecipe o código de lá: por ora, a lição é a lista compartilhada que vocês acabaram de ver.
Para a turma: "Se dois alunos cadastram livros diferentes, quantos objetos Book existem em memória? E quantas classes Book?"

Erro típico: esquecer o self no parâmetro do método (TypeError: ... takes 0 positional arguments but 1 was given) — aproveite o erro, ele confirma que o objeto é passado automaticamente.

15 min Encapsulamento e propriedades

Origem e propósito. A ideia é anterior à própria POO: David Parnas, em On the Criteria To Be Used in Decomposing Systems into Modules (Communications of the ACM, 1972), propõe o ocultamento de informação — cada módulo deve esconder uma decisão de projeto sujeita a mudar, expondo apenas uma interface estável. Encapsulamento é essa ideia aplicada ao objeto: quem usa o objeto conversa com a interface pública e ignora como o estado é guardado por dentro.

Como Python trata o assunto. Não existem private nem public. Existe convenção, sustentada pela cultura da linguagem:

  • nome — público, faz parte da interface;
  • _nome — uso interno, "não mexa" (PEP 8); o interpretador não impede nada;
  • __nome — sofre name mangling: vira _Classe__nome, o que evita colisão em herança. Não é segurança.

Fonte: PEP 8 — Style Guide for Python Code, seção "Designing for Inheritance".

Passo 6 — @property: dado derivado, não armazenado

Por quê: esta é a peça de POO mais importante para o nosso domínio. O Reading Progress do Reading Tracker é, por definição, derivado: a porcentagem é a página atual sobre o total, e "concluído" é 100% — não existe campo de status armazenado. Uma @property é exatamente isso: um cálculo que se lê como se fosse um atributo.

class Book:
    def __init__(self, title, pages):
        self.title = title
        self.pages = pages          # passa pelo setter e já é validado
        self.current_page = 0

    @property
    def pages(self):
        return self._pages

    @pages.setter
    def pages(self, value):
        if value <= 0:
            raise ValueError("pages must be greater than zero")
        self._pages = value

    @property
    def progress_percentage(self):
        return round(self.current_page / self.pages * 100, 1)

    @property
    def is_finished(self):
        return self.current_page >= self.pages

    def __repr__(self):
        return f"Book(title={self.title!r}, pages={self.pages})"
clean_code = Book("Clean Code", 464)
clean_code.current_page = 464

print(clean_code.progress_percentage)   # 100.0 — sem parênteses
print(clean_code.is_finished)           # True

Book("Broken", 0)                       # ValueError: pages must be greater than zero

Pontos a destacar:

  • progress_percentage é lido como atributo e calculado como método. Nunca fica desatualizado, porque não é guardado.
  • O setter centraliza a validação: um único lugar impede um livro com zero páginas, venha o valor de onde vier. É o mesmo raciocínio que a aula 15 aplicará às validações da API.
  • A propriedade permite trocar a implementação sem quebrar quem usa: hoje self._pages é um inteiro; amanhã poderia vir de outra fonte, e book.pages continuaria funcionando. É Parnas em três linhas.
Mencione de passagem, sem aprofundar: @staticmethod (função que vive na classe mas não usa o objeto) e @classmethod (recebe a classe em vez do objeto, útil para construtores alternativos). A turma vai encontrá-los em bibliotecas.
Para a turma: "Se guardássemos progress_percentage como um campo comum, o que aconteceria depois de o usuário registrar uma nova página? (resposta: o campo mentiria até alguém lembrar de atualizá-lo — o clássico dado derivado desatualizado)"

20 min Herança

Origem. A subclasse nasce no Simula 67 (Dahl e Nygaard) e serve a dois propósitos que convém não confundir: reutilizar implementação e declarar um subtipo ("todo EBook é um Book").

Definição formal do subtipo — o Princípio da Substituição, de Barbara Liskov (Data Abstraction and Hierarchy, OOPSLA, 1987):

"If for each object o1 of type S there is an object o2 of type T such that for all programs P defined in terms of T, the behavior of P is unchanged when o1 is substituted for o2, then S is a subtype of T."

Em português de sala de aula: onde o programa espera um Book, um EBook tem de funcionar sem surpresas. Se a subclasse quebra a expectativa da superclasse, a herança está errada — mesmo que o código compile.

Passo 7 — herdar e estender

class EBook(Book):
    def __init__(self, title, pages, file_format):
        super().__init__(title, pages)     # reaproveita a inicialização do Book
        self.file_format = file_format

    def __repr__(self):
        return f"EBook(title={self.title!r}, format={self.file_format!r})"
fluent = EBook("Fluent Python", 1012, "epub")
fluent.current_page = 506

print(fluent.progress_percentage)      # 50.0 — herdado, não reescrito
print(isinstance(fluent, EBook))       # True
print(isinstance(fluent, Book))        # True — "é-um"
print(fluent)                          # usa o __repr__ da subclasse
  • class EBook(Book) — a classe entre parênteses é a superclasse (ou classe-mãe).
  • super().__init__(...) — chama o inicializador da superclasse. Esquecê-lo é o erro mais comum: o objeto nasce sem title e sem pages.
  • Redefinir __repr__ é sobrescrita (override): a versão da subclasse tem precedência.
  • Python decide qual método usar percorrendo a MRO (Method Resolution Order) — visível em EBook.__mro__. Mostre a saída e siga adiante; herança múltipla não é assunto de hoje.

# aula 03 — Pydantic (Samuel Colvin, 2017)
class BookCreate(BaseModel):

# aula 04 — SQLModel, construído sobre Pydantic e SQLAlchemy
class User(SQLModel, table=True):

  • Herdar de BaseModel traz de graça: inicializador por palavras-chave, validação de tipos, conversão para JSON e mensagens de erro. Nós escrevemos duas linhas; a superclasse fornece centenas.

class BookRead(BookBase):
    id: int
    user_id: int
Deixe explícito: não vamos alterar o projeto agora — os schemas seguem escritos por extenso enquanto forem pequenos, porque a duplicação ainda é mais legível que a indireção. Guardem o padrão; ele reaparece quando os schemas crescerem.

10 min Polimorfismo e duck typing

Origem do termo. Polimorfismo entra na computação com Christopher Strachey (Fundamental Concepts in Programming Languages, 1967), que separa polimorfismo paramétrico de ad hoc; a taxonomia moderna vem de Cardelli e Wegner (On Understanding Types, Data Abstraction, and Polymorphism, ACM Computing Surveys, 1985).

Propósito: escrever um código que serve a vários tipos — quem chama não precisa saber com qual está falando.

library = [
    Book("Clean Code", 464),
    EBook("Fluent Python", 1012, "epub"),
]

for item in library:
    print(item)          # cada objeto se apresenta do seu jeito

Um único print, dois comportamentos: a linguagem escolhe o __repr__ do tipo concreto em tempo de execução.

Duck typing — a variante pythônica

"Se anda como um pato e grasna como um pato, é um pato": Python não exige parentesco, exige que o objeto tenha o método usado.

class Magazine:                 # não herda de Book
    def __init__(self, name, pages):
        self.name = name
        self.pages = pages
        self.current_page = 0

    @property
    def progress_percentage(self):
        return round(self.current_page / self.pages * 100, 1)


def print_progress(item):
    print(f"{item.progress_percentage}%")


print_progress(Book("Clean Code", 464))          # funciona
print_progress(Magazine("Superinteressante", 90))  # funciona também

print_progress não pede um Book: pede qualquer coisa que tenha progress_percentage. Vantagem: flexibilidade. Preço: o erro só aparece quando o método falta, em tempo de execução — motivo pelo qual anotações de tipo e validação (Pydantic, aula 03) ganharam tanto espaço no ecossistema.

Prepare a turma para o que vem na semana seguinte: na aula 02 vocês vão escrever raise HTTPException(status_code=404, ...). HTTPException herda de Exception — e é por ser um subtipo que o raise a aceita e que o FastAPI consegue capturá-la junto com qualquer outra exceção. Quando a linha aparecer, ela já estará explicada.

10 min Composição — "tem-um" em vez de "é-um"

Duas formas de um objeto usar outro:

  • Herança — relação "é-um": EBook é um Book;
  • Composição — relação "tem-um": User tem Books.

Recomendação clássica (Gamma, Helm, Johnson e Vlissides, Design Patterns, 1994):

"Favor object composition over class inheritance."

Motivo: a herança amarra a subclasse à implementação da superclasse — mudou a mãe, quebraram as filhas. A composição amarra apenas a uma interface, e pode ser trocada em tempo de execução.

class User:
    def __init__(self, name, email):
        self.name = name
        self.email = email
        self.books = []                      # tem-um (na verdade, tem-vários)

    def add_book(self, book):
        self.books.append(book)

    @property
    def finished_count(self):
        return sum(1 for book in self.books if book.is_finished)
user = User("Ana", "ana@example.com")
user.add_book(Book("Clean Code", 464))
user.add_book(EBook("Fluent Python", 1012, "epub"))

print(len(user.books))          # 2
print(user.finished_count)      # 0

Ligue diretamente ao projeto: esta é a relação 1:N que a aula 05 grava no banco. O que aqui é uma lista Python, lá é uma chave estrangeira mais uma relação do ORM — mas o desenho é o mesmo:

# projeto/backend/models.py — aula 05
class User(SQLModel, table=True):
    books: list["Book"] = Relationship(back_populates="user")

10 min POO declarativa — anotações e decorators

Falta explicar o estilo de classe que a turma mais vai escrever no projeto — e que não se parece com nada do que fizemos até aqui: sem __init__, sem self, sem métodos.

class BookCreate(SQLModel):
    title: str
    pages: int

Primeiro ponto: title: str não é atribuição, é anotação. Nada é atribuído a title; a linha apenas registra que o nome title tem o tipo str. As anotações ficam guardadas num dicionário da classe (PEP 526 — Syntax for Variable Annotations, Python 3.6, 2016). Demonstre no interpretador:

>>> class BookCreate(SQLModel):
...     title: str
...     pages: int
...
>>> BookCreate.__annotations__
{'title': <class 'str'>, 'pages': <class 'int'>}

A superclasse lê essas anotações e, a partir delas, gera o inicializador, a validação e a conversão para JSON. É por isso que BookCreate(title="Clean Code", pages=464) funciona sem que ninguém tenha escrito um __init__. As anotações de tipo em si vêm do PEP 484 (2014); o Pydantic, de Samuel Colvin (2017), foi quem transformou anotação em validação em tempo de execução.

Segundo ponto: table=True é um argumento nomeado passado na definição da classe (PEP 3115). Quem o recebe é a maquinaria que constrói a classe — a metaclasse — e é ela que decide criar também uma tabela no banco. Cite o nome e siga: metaclasses não são assunto de graduação inicial; o que importa é saber que table=True é um interruptor, não um atributo.

Terceiro ponto: o @. Um decorator é apenas uma função que recebe uma função e devolve algo no lugar dela (PEP 318, Python 2.4, 2004).

def log_call(function):
    def wrapper(*args, **kwargs):
        print(f"calling {function.__name__}")
        return function(*args, **kwargs)
    return wrapper


@log_call
def read_health():
    return {"status": "Ok"}


read_health()          # imprime "calling read_health" e devolve o dicionário

Com isso, @property e @app.get("/health") deixam de ser mágica: o primeiro transforma o método num atributo calculado; o segundo não altera a função — ele a registra na tabela de rotas do objeto app e a devolve intacta. Este é o mecanismo da inversão de controle discutida na aula 01: nós declaramos, o framework chama.

Checkpoint — feche o ciclo da abertura. Volte ao trecho projetado no início da aula e peça que a turma leia em voz alta, símbolo a símbolo: class Book(SQLModel, table=True) é uma classe que herda de SQLModel com um interruptor de tabela ligado; id: int | None é uma anotação de tipo; Field(...) configura a coluna; Relationship(...) é a composição 1:N do lado do ORM.

class Author:
    def __init__(self, name, country):
        self.name = name
        self.country = country

    def __repr__(self):
        return f"Author(name={self.name!r})"


class Book:
    def __init__(self, title, pages, author):
        self.title = title
        self.pages = pages
        self.author = author
        self.current_page = 0

    @property
    def progress_percentage(self):
        return round(self.current_page / self.pages * 100, 1)

    @property
    def is_finished(self):
        return self.current_page >= self.pages

    def __repr__(self):
        return f"Book(title={self.title!r}, author={self.author.name!r})"


class AudioBook(Book):
    def __init__(self, title, pages, author, duration_minutes):
        super().__init__(title, pages, author)
        self.duration_minutes = duration_minutes

    def __repr__(self):
        return f"AudioBook(title={self.title!r}, minutes={self.duration_minutes})"


class Library:
    def __init__(self):
        self.books = []

    def add(self, book):
        self.books.append(book)

    @property
    def average_progress(self):
        if not self.books:
            return 0.0
        total = sum(book.progress_percentage for book in self.books)
        return round(total / len(self.books), 1)

5 min Fechamento

  • Síntese: objeto é estado + comportamento + identidade; self é o próprio objeto passado como primeiro argumento; @property expõe dado derivado sem armazená-lo; herança é "é-um", composição é "tem-um" — e a recomendação é preferir a segunda; duck typing troca parentesco por presença do método; classes declarativas funcionam porque a superclasse lê as anotações de tipo.
  • Por que esta aula existe: a partir da aula 03, o projeto passa a ser escrito em classes o tempo todo — schemas Pydantic, modelos SQLModel, relações 1:N. Sem esta base, o aluno copia o código; com ela, o aluno o lê.

Na próxima, dissecamos a viagem entre uma coisa e outra — DNS, HTTP, o papel real do uvicorn — e criamos as primeiras rotas de books, ainda com dicionários crus. Guardem o incômodo: na aula 03, esses dicionários viram classes."
