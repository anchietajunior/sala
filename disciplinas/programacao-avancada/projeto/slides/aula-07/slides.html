Objetivos da aula

  • Distinguir autenticação de autorização e situar o RBAC a partir da matriz de acesso;
  • Modelar papéis com um enum do Python mapeado para um ENUM do MySQL, com o menor privilégio como padrão;
  • Concentrar a regra de acesso a Books em um método do model e aplicá-la em todas as rotas;
  • Proteger rotas por papel com a dependency require_admin e escolher entre 401, 403 e 404;
  • Construir o Admin Dashboard em /admin no React - e mostrar que quem protege os dados é a API.

Autenticação pergunta quem é; autorização, o que pode

Autenticação: o processo de verificar uma alegação de que uma entidade do sistema possui determinado valor de atributo.

Autorização: uma aprovação concedida a uma entidade do sistema para acessar um recurso do sistema.

  • Definições da Internet Security Glossary (RFC 4949, R. Shirey, IETF, 2007), em tradução livre;
  • No projeto, o JWT e o get_current_user respondem a primeira pergunta; a segunda ainda não tem resposta no código.

RBAC: a permissão é dada ao papel, não à pessoa

No RBAC, permissões são associadas a papéis, e usuários são designados aos papéis apropriados, adquirindo assim as permissões desses papéis.

  • Origem: David Ferraiolo e Richard Kuhn, Role-Based Access Controls (NIST, 1992) - uma alternativa para organizações civis e comerciais aos modelos do Orange Book (TCSEC, 1985), pensados para o meio militar;
  • A definição acima é de Sandhu, Coyne, Feinstein e Youman (IEEE Computer, 1996), em tradução livre; virou norma em 2004 (ANSI INCITS 359).

FERRAIOLO, D.; KUHN, R. - 1992 · SANDHU, R. et al. - Role-Based Access Control Models, 1996

O papel decide se a relação de dono importa

  • "O User acessa os próprios livros" não é RBAC: depende da relação entre quem pede e o recurso - book.user_id;
  • O OWASP recomenda combinar papéis com atributos e relações (Authorization Cheat Sheet);
  • O sistema é essa combinação: o papel admin dispensa a relação; o papel user a exige.
Entra um terceiro usuário com o papel user: nenhuma regra nova. A linha dele na matriz é gerada pelo papel e pela relação de dono.

O papel é um conjunto fechado de valores


import enum


class Role(enum.Enum):
    ADMIN = "admin"
    USER = "user"
  • enum.Enum - biblioteca padrão do Python (PEP 435, Barry Warsaw, Eli Bendersky e Ethan Furman; Python 3.4): só estes dois valores existem;
  • Cada membro tem nome (ADMIN, em maiúsculas por ser constante) e valor ("admin");
  • No código compara-se user.role == Role.ADMIN - nunca com uma string solta, que aceitaria "Admin" ou "adm".

PEP 435 - Adding an Enum type to the Python standard library, 2013

A coluna: ENUM no MySQL, menor privilégio como padrão


role: Mapped[Role] = mapped_column(
    Enum(Role, values_callable=lambda roles: [role.value for role in roles]),
    server_default=Role.USER.value,
)
  • Enum(Role, ...) é do SQLAlchemy - o tipo da coluna; o enum.Enum do Python define os valores;
  • values_callable: o banco guarda o valor ('admin'), não o nome do membro ('ADMIN');
  • server_default: o DEFAULT fica no banco - todo INSERT sem papel cria um usuário comum.

`role` enum('admin','user') NOT NULL DEFAULT 'user'
Antes: DROP TABLE books; DROP TABLE users; - o model ganhou coluna e o create_all não altera tabela existente. Depois: SHOW CREATE TABLE users;

Três princípios de proteção de Saltzer e Schroeder

  • Padrões à prova de falha (fail-safe defaults): "basear as decisões de acesso em permissão, e não em exclusão" - negar é o padrão; o acesso precisa ser provado;
  • Mediação completa (complete mediation): "todo acesso a todo objeto deve ser verificado quanto à autoridade" - toda rota que toca um livro, não só a listagem;
  • Menor privilégio (least privilege): "todo programa e todo usuário do sistema deve operar com o menor conjunto de privilégios necessário para completar o trabalho" - todo cadastro nasce user.

Jerome Saltzer e Michael Schroeder reuniram oito princípios em 1975 - ainda hoje a base dos guias de segurança. Tradução livre.

SALTZER, J.; SCHROEDER, M. - The Protection of Information in Computer Systems, Proceedings of the IEEE, 1975

401, 403 e 404: três situações diferentes

401: a requisição não foi aplicada porque não possui credenciais de autenticação válidas para o recurso. 403: o servidor entendeu a requisição, mas se recusa a atendê-la. Um servidor que deseje "esconder" a existência de um recurso proibido pode, em vez disso, responder 404.

SituaçãoRespostaPor quê
Sem token, ou token inválido401a API não sabe quem é
User pede livro de outro User404a existência do livro não se confirma
User chama rota administrativa403a rota é pública no Swagger: não há o que esconder

RFC 9110 - HTTP Semantics, IETF, 2022 (15.5.2 e 15.5.4), tradução livre

Recapitulando - princípios e falhas

  • Negar por padrão, verificar todo acesso, dar o menor privilégio (Saltzer e Schroeder, 1975);
  • BOLA, mass assignment e BFLA: objeto, propriedade e função (OWASP, 2023);
  • 401 = não sei quem é; 403 = sei e não permito; 404 = não confirmo que existe (RFC 9110).

A regra de acesso vive em um método do User


@property
def is_admin(self) -> bool:
    return self.role == Role.ADMIN

def can_access(self, book: "Book") -> bool:
    return self.is_admin or book.user_id == self.id
  • is_admin: property lida como atributo, calculada a partir do papel;
  • can_access: a matriz em uma linha - o Admin acessa qualquer livro (papel); os demais, os que têm o próprio id (relação). Só devolve True com permissão explícita;
  • "Book" entre aspas: a classe é definida mais abaixo no arquivo (forward reference, PEP 484).

O token diz quem é; o banco diz o que pode

  • Machado foi promovido depois do login - e o token dele passou a valer como Admin sem novo login;
  • O token carrega o sub (quem é), não o papel: o get_current_user busca o usuário no banco a cada requisição, e o papel vem junto;
  • Rebaixar alguém também vale na hora.

require_admin: autorização no nível da função


def require_admin(current_user: models.User = Depends(get_current_user)) -> models.User:
    if not current_user.is_admin:
        raise HTTPException(status_code=403, detail="Admin role required")
    return current_user
  • Uma dependency que depende de outra: sem token, o get_current_user responde 401 antes; com token, a decisão é sobre o papel;
  • 403, não 404: a API sabe quem é e recusa.

A interface esconde, a API proíbe

OWASP - Authorization Cheat Sheet

Por que o papel vai no login, e não dentro do token

  • A interface precisa do papel só para decidir o que desenhar - o link e a página /admin;
  • A API não confia nele: consulta o banco a cada requisição;
  • Se a API lesse o papel do token, um Admin rebaixado continuaria Admin até o exp;
  • Custo assumido: a interface conhece o papel do momento do login - a mudança aparece na tela depois de sair e entrar. Nas rotas, vale na hora.

O login entrega o token e o papel


export async function login(email, password) {
  const data = await request("/login", { method: "POST", body: { email, password } });
  return { token: data.access_token, role: data.role };
}
  

const { token, role } = await login(email, password);
onLogin(token, role);
  • O service continua escondendo o formato da resposta da API (access_token);
  • Desestruturação: extrai as duas propriedades do objeto em duas constantes. No App, o papel segue o caminho do token: localStorage no login, removido no logout.

Síntese da aula

  • Autenticação responde quem é; autorização, o que pode (RFC 4949). Toda decisão é uma célula da matriz de Lampson (1971), e o RBAC a gera a partir de papéis (Ferraiolo e Kuhn, 1992; Sandhu et al., 1996) - no projeto, combinado com a relação de dono;
  • O papel é um enum do Python mapeado para um ENUM do MySQL com DEFAULT 'user'; a API não oferece rota para concedê-lo, e o schema de entrada ignora o que não declara;
  • A regra de acesso a Books vive em User.can_access e toda rota de um livro a consulta - padrão à prova de falha, mediação completa e menor privilégio (Saltzer e Schroeder, 1975);
  • BOLA, mass assignment e BFLA são as falhas que o OWASP mais encontra; 401 = não sei quem é, 403 = sei e não permito, 404 = não confirmo que existe (RFC 9110);
  • require_admin, declarado no router, protege todas as rotas administrativas de uma vez;
  • O Admin Dashboard em /admin aparece só para o Admin - mas a tela é conveniência: quem protege os dados é a API, que consulta o papel no banco a cada requisição.
