O único cliente da API é o Swagger

Cadastro, login e o CRUD de Books autenticado estão prontos - e para usá-los uma pessoa precisaria escrever requisições HTTP à mão, copiar o token e montar o header.

  • Não existe interface - o User é uma pessoa; a API fala JSON. Falta o programa que roda no navegador e conversa com a API em nome dela;
  • Book só tem nome - o Reading Progress é a página atual sobre o total de páginas, e a tabela books não guarda nenhum dos dois números.

Primeiro o backend - páginas e progresso nos dados, e a permissão para um cliente de outra origem; depois a interface (React) que os exibe.

Objetivos da aula

  • Estender o Book com pages e current_page e expor o Reading Progress como dado derivado;
  • Explicar a política de mesma origem, configurar o CORSMiddleware e verificar o preflight com curl;
  • Criar um projeto React com Vite, configurar o Tailwind e situá-lo entre as bibliotecas de estilo e de componentes;
  • Explicar o modelo de componentes do React - interface como função do estado - e organizar o código em pages, components e services, com componentes estilizados reutilizáveis;
  • Consumir a API com fetch: cadastro, login e o CRUD de Books, com o token no localStorage e no header Authorization: Bearer.

Aplicação de página única: trocar dados, não páginas

O navegador carrega um único documento HTML e um programa que, de forma assíncrona, pede dados ao servidor e atualiza a tela - sem recarregar a página.

  • Origem: nomeada por Jesse James Garrett no ensaio Ajax: A New Approach to Web Applications (2005) - a comunicação assíncrona deixa de trocar páginas inteiras;
  • A API construída até aqui é o lado dos dados desse modelo; o que falta é o lado da tela.

GARRETT, J. J. - Ajax: A New Approach to Web Applications, 2005

React: a interface é uma função do estado

"The library for web and native user interfaces." - react.dev

  • Origem: criada por Jordan Walke no Facebook, em uso interno desde 2011 e publicada como código aberto na JSConf US de 2013;
  • Interface declarativa: o componente descreve como a tela deve ficar para um dado estado; o React calcula o que mudar no DOM quando o estado muda;
  • Em uma fórmula: UI = f(estado). O programador nunca toca o DOM.

Componente, props, estado e efeito

  • Componente: uma função JavaScript que devolve JSX - sintaxe parecida com HTML, compilada para chamadas JavaScript pelo Vite;
  • Props: os parâmetros do componente - o pai passa dados e funções para o filho;
  • Estado (useState): o valor cuja mudança redesenha o componente;
  • Efeito (useEffect): código que roda depois de desenhar - o lugar de buscar dados quando a tela aparece;
  • Os hooks existem desde o React 16.8 (2019) e são a forma atual de escrever componentes.

Reading Progress: dado derivado, nunca armazenado


class Book(Base):
    __tablename__ = "books"

    id: Mapped[int] = mapped_column(primary_key=True)
    name: Mapped[str] = mapped_column(String(255))
    pages: Mapped[int]
    current_page: Mapped[int]
    user_id: Mapped[int] = mapped_column(ForeignKey("users.id"))
    created_at: Mapped[datetime] = mapped_column(server_default=func.now())

    @property
    def progress(self) -> int:
        return round(self.current_page * 100 / self.pages)
  • Mapped[int] sem mapped_column: o tipo Python basta - vira INTEGER NOT NULL;
  • progress é property, não coluna: calculada a cada leitura, nunca desatualizada. Concluído = 100%, sem campo de status.

A entrada valida dois campos de uma vez


class BookCreate(BaseModel):
    name: str = Field(min_length=1, max_length=255)
    pages: int = Field(gt=0)
    current_page: int = Field(default=0, ge=0)

    @model_validator(mode="after")
    def check_current_page(self):
        if self.current_page > self.pages:
            raise ValueError("current_page must not exceed pages")
        return self
  • Field(gt=0) e Field(ge=0): regras de um campo só; default=0 - cadastrar um livro é começar a lê-lo;
  • @model_validator(mode="after"): regra entre dois campos, depois da validação individual; o ValueError vira 422 com a mensagem.

Origem = esquema + host + porta

Dois URLs têm a mesma origem quando esquema, host e porta coincidem - a tripla que identifica de onde um documento veio.

  • Origem: RFC 6454, The Web Origin Concept (Adam Barth, IETF, 2011);
  • http://localhost:5173 e http://127.0.0.1:8000 diferem duas vezes - host e porta. Bastaria uma.

RFC 6454 - The Web Origin Concept, IETF, 2011

A política de mesma origem protege o usuário

  • Origem: introduzida no Netscape Navigator 2.0 (1995), junto com o JavaScript;
  • A regra: um script só pode ler respostas da origem de onde veio;
  • O motivo: sem ela, qualquer página aberta em outra aba leria, com os cookies do usuário, as respostas do banco dele;
  • É uma regra do navegador, para o navegador - o curl, o Swagger e um script Python não a consultam.

MDN Web Docs - Same-origin policy

CORS: o servidor declara, o navegador aplica

Cross-Origin Resource Sharing: o mecanismo pelo qual o servidor declara, por headers de resposta, quais origens podem ler suas respostas.

  • Origem: especificado por Anne van Kesteren; Recomendação W3C em 2014, hoje parte do Fetch Standard da WHATWG;
  • A declaração: Access-Control-Allow-Origin: http://localhost:5173. Sem o header, ou com outra origem, o navegador descarta a resposta e o script recebe um erro de rede.

W3C - Cross-Origin Resource Sharing, 2014 · WHATWG - Fetch Standard

Recapitulando - mesma origem e CORS

  • Origem = esquema + host + porta (RFC 6454);
  • O navegador não deixa um script ler resposta de outra origem (Netscape, 1995);
  • CORS: o servidor libera origens por header; o navegador obedece (W3C 2014, Fetch Standard);
  • Preflight OPTIONS antes de métodos e headers não triviais;
  • Não vale fora do navegador - não substitui o token.

O curl envia a consulta que o navegador enviará

Mac


curl -i -X OPTIONS http://127.0.0.1:8000/signup \
  -H "Origin: http://localhost:5173" \
  -H "Access-Control-Request-Method: POST" \
  -H "Access-Control-Request-Headers: content-type"

Windows (PowerShell)


curl.exe -i -X OPTIONS http://127.0.0.1:8000/signup `
  -H "Origin: http://localhost:5173" `
  -H "Access-Control-Request-Method: POST" `
  -H "Access-Control-Request-Headers: content-type"
  • -i mostra os headers da resposta; cada -H é uma pergunta do preflight: quem pede, com que método, com que headers;
  • No PowerShell, curl.exe com a extensão - curl sozinho pode ser um apelido para outro comando.

Sem configuração, a API recusa o preflight


HTTP/1.1 405 Method Not Allowed
server: uvicorn
allow: POST
content-type: application/json

{"detail":"Method Not Allowed"}
  • 405 com allow: POST: a rota /signup só conhece POST;
  • Nenhum header Access-Control-Allow-*: para o navegador, a resposta é "não" - e o POST real nunca sairia;
  • No uvicorn: "OPTIONS /signup HTTP/1.1" 405 Method Not Allowed.

O CORSMiddleware envolve todas as rotas


from fastapi.middleware.cors import CORSMiddleware

app.add_middleware(
    CORSMiddleware,
    allow_origins=["http://localhost:5173"],
    allow_methods=["*"],
    allow_headers=["*"],
)
  • Toda requisição passa pelo middleware antes da rota, e toda resposta passa por ele na volta;
  • Responde o preflight sozinho e acrescenta os Access-Control-Allow-* em toda resposta a uma origem permitida;
  • "*" em métodos e headers libera o que o frontend envia: PUT, DELETE, Authorization - só para a origem listada.

Documentação oficial do FastAPI - fastapi.tiangolo.com (CORS)

Com o middleware, o preflight é respondido


HTTP/1.1 200 OK
vary: Origin
access-control-allow-methods: DELETE, GET, HEAD, OPTIONS, PATCH, POST, PUT
access-control-max-age: 600
access-control-allow-origin: http://localhost:5173
access-control-allow-headers: content-type
  • access-control-allow-origin repete a origem que perguntou - é a autorização que o navegador procura;
  • access-control-max-age: 600: o navegador guarda a resposta por 600 s e não repete o preflight nesse intervalo;
  • O curl recebe tudo, sempre: os headers são instruções para o navegador, que é quem descarta a resposta.
Com Origin: http://127.0.0.1:5173: 400, Disallowed CORS origin. localhost e 127.0.0.1 são a mesma máquina, mas origens diferentes - a lista é literal.

Separação de responsabilidades: um aspecto de cada vez

"It is what I sometimes have called 'the separation of concerns', which, even if not perfectly possible, is yet the only available technique for effective ordering of one's thoughts, that I know of."

  • O problema no frontend: cada tela desenha campos, guarda o que o usuário digitou e conversa com a API. No mesmo arquivo, uma rota nova na API obriga a abrir todas as telas.

  • Props descem, callbacks sobem; só os services chamam request.

Button.jsx: a variante escolhe a aparência


const baseClasses = "rounded-lg px-4 py-2 text-sm font-semibold focus-visible:outline-2 focus-visible:outline-offset-2 focus-visible:outline-indigo-600";

const variantClasses = {
  primary: "bg-indigo-600 text-white shadow-xs hover:bg-indigo-500",
  secondary: "bg-white text-slate-700 shadow-xs ring-1 ring-slate-300 ring-inset hover:bg-slate-50",
  danger: "bg-white text-red-600 shadow-xs ring-1 ring-red-200 ring-inset hover:bg-red-50",
};

export default function Button({ variant = "primary", children, ...props }) {
  return (
    <button className={`${baseClasses} ${variantClasses[variant]}`} {...props}>
      {children}
    </button>
  );
}
  • children: o texto entre <Button> e </Button>; ...props repassa onClick e type ao <button>;
  • hover: e focus-visible: são prefixos de estado: a classe vale com o mouse em cima ou com o foco do teclado.

services/api.js: uma função para toda conversa com a API


const API_URL = "http://127.0.0.1:8000";

export async function request(path, { method = "GET", body } = {}) {
  const headers = { "Content-Type": "application/json" };
  const token = localStorage.getItem("token");
  if (token) {
    headers["Authorization"] = `Bearer ${token}`;
  }
  const response = await fetch(API_URL + path, {
    method,
    headers,
    body: body ? JSON.stringify(body) : undefined,
  });
  • fetch: a função do navegador para HTTP; async/await como no Python - espera sem travar a tela;
  • O token é lido do localStorage a cada requisição e vai no header - o que o botão Authorize do Swagger montava.

Erro da API vira exceção com a mensagem


  if (response.status === 204) {
    return null;
  }
  const data = await response.json();
  if (!response.ok) {
    const error = new Error(
      Array.isArray(data.detail) ? data.detail[0].msg : data.detail,
    );
    error.status = response.status;
    throw error;
  }
  return data;
}
  • 204 não tem corpo - chamar json() nele quebraria;
  • detail é texto nas HTTPException e uma lista no 422 (o msg do campo inválido); error.status guarda o código HTTP.

authService.js: a página pede uma ação, não uma rota


import { request } from "./api";

export function signup(name, email, password) {
  return request("/signup", { method: "POST", body: { name, email, password } });
}

export async function login(email, password) {
  const data = await request("/login", { method: "POST", body: { email, password } });
  return data.access_token;
}
  • O nome é o da ação: quem chama signup(...) não sabe que existe um POST /signup;
  • login devolve só o token - o formato da resposta da API fica escondido aqui;
  • signup devolve a promessa do request direto; login precisa de async porque trabalha a resposta.

SignupPage.jsx: estado por campo, submit sem reload


import { signup } from "../services/authService";

export default function SignupPage({ onDone }) {

  const [email, setEmail] = useState("");
  const [password, setPassword] = useState("");

  async function handleSubmit(event) {

    }
  }
  • A página chama uma ação do service: nenhuma URL, nenhum verbo HTTP neste arquivo;
  • { onDone } é uma prop: o pai decide o que acontece depois do cadastro;
  • preventDefault() impede o formulário HTML de recarregar a página - o que destruiria a aplicação.

O input controlado: o estado é a fonte da verdade

               value={name} onChange={(e) => setName(e.target.value)} />
    ...

      I already have an account

  • A página monta a tela com os componentes estilizados: nenhuma classe de campo ou de botão se repete aqui;
  • Sem type, o botão é o submit; type="button" chega ao elemento pelo ...props e não submete.

Bearer: quem porta o token, é

"A security token with the property that any party in possession of the token (a 'bearer') can use the token in any way that any other party in possession of it can."

  • Origem: RFC 6750, The OAuth 2.0 Authorization Framework: Bearer Token Usage (IETF, 2012) - define o header Authorization: Bearer <token>;
  • A API é stateless: o cliente apresenta o token em toda requisição - logo o navegador precisa guardá-lo entre uma requisição e outra, e entre um F5 e outro.

RFC 6750 - Bearer Token Usage, IETF, 2012

localStorage: armazenamento por origem

  • Origem: a API Web Storage - especificação W3C de 2013, hoje no HTML Standard da WHATWG;
  • Chave-valor por origem, sobrevive ao fechamento do navegador: setItem, getItem, removeItem;
  • Ao contrário do cookie, o navegador não o envia sozinho: só o nosso JavaScript o lê e o coloca no header;
  • Consequência: outra página não consegue fazer o navegador anexar o token - o ataque de requisição forjada entre sites (CSRF) não se aplica.

O token entra no login e sai em toda requisição

Recapitulando - o token no navegador

  • Authorization: Bearer - quem porta, é (RFC 6750);
  • localStorage: por origem, sobrevive ao F5, enviado só pelo nosso código;
  • Sem CSRF; com risco de XSS - mitigado por escape, sem script alheio, vida curta;
  • Sair é esquecer o token: a API não tem sessão para encerrar.

App.jsx: o token decide a página


export default function App() {
  const [token, setToken] = useState(localStorage.getItem("token"));
  const [showSignup, setShowSignup] = useState(false);

  function handleLogin(newToken) {
    localStorage.setItem("token", newToken);
    setToken(newToken);
  }

  function handleLogout() {
    localStorage.removeItem("token");
    setToken(null);
  }

  if (token) {
    return <BooksPage onLogout={handleLogout} />;
  }
  if (showSignup) {
    return <SignupPage onDone={() => setShowSignup(false)} />;
  }
  return <LoginPage onLogin={handleLogin} onShowSignup={() => setShowSignup(true)} />;
}
  • Estado inicial vem do localStorage: o F5 mantém o login. handleLogin guarda e muda o estado - um sem o outro não bastaria;
  • Três return condicionais: UI = f(estado) na forma mais literal.

BooksPage.jsx: buscar dados quando a tela aparece


export default function BooksPage({ onLogout }) {
  const [books, setBooks] = useState([]);
  const [form, setForm] = useState(emptyForm);
  const [error, setError] = useState("");

  useEffect(() => {
    loadBooks();
  }, []);

  async function loadBooks() {
    try {
      setBooks(await listBooks());
    } catch (err) {
      setError(err.message);
    }
  }
  • useEffect(..., []): roda depois do primeiro desenho, uma vez. Buscar fora do efeito dispararia uma requisição a cada redesenho;
  • A página guarda o estado e chama o service; o desenho fica nos componentes.

  • map transforma a lista de dados em lista de componentes; o key - o id do banco - fica no elemento que o map devolve;

Síntese da aula

  • O Book ganhou pages e current_page; o Reading Progress é dado derivado - property no model, publicada pelo BookRead, nunca armazenada;
  • Aplicação de página única (Garrett, 2005), servida por outra origem: a política de mesma origem (RFC 6454) exigiu que a API declarasse por CORS quem pode ler suas respostas - o preflight OPTIONS verificado com o curl antes da primeira tela;
  • Componentes como funções de estado - useState para o que muda, useEffect para buscar dados, props e callbacks para conversar com o pai; Vite serve e empacota, Tailwind estiliza no JSX, npm gerencia como o pip;
  • Separação de responsabilidades (Dijkstra, 1974; Parnas, 1972): services escondem a API, pages guardam o estado de cada tela, components só desenham;
  • Do Bootstrap às bibliotecas sobre o Tailwind, o projeto copia e adapta: Button, TextInput, ErrorMessage e Card concentram a aparência, com rótulo, foco visível e erro anunciado;
  • O token vive no localStorage e viaja em Authorization: Bearer (RFC 6750) - custo assumido do XSS, defesa da vida curta;
  • O CRUD inteiro roda na tela; a garantia de que cada um só mexe nos próprios livros continua onde sempre esteve: na API.
