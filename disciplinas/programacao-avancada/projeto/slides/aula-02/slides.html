A rede não entende nomes

  • unirios.com.br é um nome — bom para humanos;
  • A rede localiza máquinas por números: endereços IP;
  • Antes de qualquer pedido, o navegador precisa traduzir nome → IP.

KUROSE; ROSS. Computer Networking: A Top-Down Approach, 2021

DNS é a agenda de contatos da internet

Como a agenda do celular: você toca no nome, o telefone descobre o número — só então liga.

RFC 1034 / RFC 1035 — Domain Names, IETF, 1987 · KUROSE; ROSS, 2021

127.0.0.1 nem sai da sua máquina

  • 127.0.0.1 já é um IP — nenhuma consulta DNS acontece;
  • É o endereço de loopback: "esta própria máquina" — funciona sem internet;
  • O :8000 é a porta: identifica qual programa dentro da máquina;
  • IP acha a máquina; porta acha o programa. Cada servidor escuta a sua.

Dois programas na porta 8000? O segundo falha: "address already in use".

Recapitulando — DNS

  • A rede entende números; o DNS traduz nome → IP;
  • A consulta sobe em etapas: cache → provedor → raiz → .br → domínio;
  • IP + porta = a máquina e o programa dentro dela;
  • 127.0.0.1 é loopback: a requisição fica em casa.

A requisição é texto com formato fixo


GET /health HTTP/1.1
Host: 127.0.0.1:8000
User-Agent: Mozilla/5.0 (Macintosh; ...)
Accept: */*
  • Linha de pedido: método (GET = "me dê") + caminho + versão;
  • Headers: metadados do pedido, em pares chave–valor;
  • Corpo: GET normalmente não tem — entra quando enviamos dados.

RFC 9110 — HTTP Semantics, IETF, 2022

A resposta também


HTTP/1.1 200 OK
server: uvicorn
content-type: application/json
content-length: 15

{"status":"Ok"}
  • Linha de status: versão + status code;
  • content-type avisa "o corpo é JSON" — por isso o navegador exibe formatado;
  • A "tela" é só o corpo; o resto viaja escondido.

RFC 9110 — HTTP Semantics, IETF, 2022

Recapitulando — HTTP

  • Requisição: linha de pedido + headers (+ corpo);
  • Resposta: linha de status + headers + corpo;
  • Status code: 2xx certo, 4xx culpa do cliente, 5xx culpa do servidor;
  • Tudo texto, com formato fixo — dá para ler a olho nu.

Servidor web: um programa escutando uma porta

  • Fica esperando bytes chegarem pela rede;
  • Interpreta o protocolo HTTP;
  • Devolve a resposta — e volta a esperar.

No nosso projeto, esse programa é o uvicorn.

Dois programas, um contrato: ASGI

  • O ASGI define como servidor e framework conversam — é padrão, não casamento: outro servidor ASGI rodaria a mesma app;
  • O server: uvicorn nos headers é ele se identificando;
  • O --reload é serviço do uvicorn: ele vigia os arquivos e reinicia a aplicação;
  • Em produção há mais camadas na frente (ex.: nginx) — fica a menção.

Quem está no comando quando rodamos uvicorn main:app? Eles. Nosso código só roda quando chega requisição — a inversão de controle da aula 01.

Especificação ASGI — asgi.readthedocs.io

Recapitulando — servidores web

  • uvicorn: escuta a porta, fala HTTP, traduz bytes ↔ Python;
  • FastAPI: decide qual função responde e monta o JSON;
  • O contrato entre eles se chama ASGI;
  • É o recepcionista bilíngue: a cozinha nunca fala com a rua.

A URL é a primeira entrada de dados

Nossas rotas respondem sempre a mesma coisa — sistemas reais recebem dados. Na URL, eles viajam em dois lugares:

  • Path parameters — pedaço variável do caminho: dizem qual coisa queremos;
  • Query parameters — chave=valor depois do ?, separados por &: ajustam o pedido.

Você usa os dois todo dia


github.com/torvalds/linux
        └─ path: identifica o usuário e o repositório

google.com/search?q=fastapi
        └─ query: q é o termo buscado

youtube.com/watch?v=9bZkp7q19f0&t=42
        └─ dois query params: o vídeo (v) e o segundo inicial (t)

Por que o termo buscado do Google vai na query, e não no caminho?

Um livro pelo id: path param em ação


from fastapi import FastAPI, HTTPException

@app.get("/api/books/{book_id}")
def read_book(book_id: int):
    for book in books:
        if book["id"] == book_id:
            return book
    raise HTTPException(status_code=404, detail="Book not found")
  • O {book_id} do caminho vira o argumento da função — mesmo nome, obrigatório, tipado (int);
  • /api/books/abc → 422: validação de graça, nossa função nem rodou;
  • Livro não existe? Nós escolhemos o status: /api/books/99 → 404 com mensagem nossa.

Documentação oficial do FastAPI — fastapi.tiangolo.com · DevSheets. FastAPI Cheat Sheet — devsheets.io/sheets/fastapi

Buscar pelo nome: query param em ação


@app.get("/api/books")
def list_books(name: str = ""):
    if name == "":
        return books
    return [book for book in books if name.lower() in book["name"].lower()]
  • name não está no caminho → query param: /api/books?name=hobbit;
  • Default "" → opcional: sem ele, lista tudo como antes;
  • Query ajusta: o mesmo endpoint, filtrado — o .lower() dos dois lados ignora maiúsculas.

POST /api/books — criar (por enquanto, na lista)


@app.post("/api/books", status_code=201)
def create_book(book: dict):
    new_book = {"id": len(books) + 1, "name": book["name"]}
    books.append(new_book)
    return new_book
  • Os dados viajam no corpo da requisição — e a barra do navegador só faz GET: teste pelo Swagger;
  • 201 Created — direto da tabela de status codes de hoje;
  • book: dict é cru, sem validação (POST sem name → 500!) — o Pydantic fecha esse buraco na aula 03;
  • Reinicie o servidor: o livro criado some — memória morre com o processo; banco de dados na aula 04.
