Ligar dados por valor, não por ponteiro

  • Antes do modelo relacional, os bancos navegacionais (hierárquicos, como o IMS da IBM; de rede, como os do padrão CODASYL) ligavam registros por ponteiros físicos — o programa navegava a estrutura;
  • A proposta de Edgar F. Codd (1970): relações se ligam por valores compartilhados — uma tabela referencia a outra guardando o valor da chave dela;
  • É essa ideia que hoje ganha nome e sintaxe no nosso projeto.

CODD, E. F. — A Relational Model of Data for Large Shared Data Banks, CACM, 1970

Modelar o mundo antes de criar tabelas

  • Origem: Peter Chen, The Entity-Relationship Model — Toward a Unified View of Data (ACM Transactions on Database Systems, vol. 1, n. 1, 1976);
  • Propósito: descrever o domínio antes do banco — entidades (as "coisas": User, Book), relacionamentos (as associações: "cadastrou", "pertence a") e cardinalidades;
  • Cardinalidades: 1:1, 1:N, N:M (esta exige tabela associativa — fica na menção);
  • O nosso caso: um User tem muitos Books; cada Book pertence a exatamente um User — 1:N;
  • Aula 06: a segunda 1:N do projeto — um Book tem muitos Reading Updates.

A chave estrangeira mora no lado N

Chave estrangeira: coluna (ou conjunto de colunas) cujos valores devem ser, obrigatoriamente, valores da chave primária da tabela referenciada.

  • No nosso caso: book.user_id só aceita valores que existam em user.id;
  • Cada Book aponta para o seu único dono — uma coluna escalar basta;
  • O contrário não funciona: o User teria que guardar uma lista de ids numa coluna só — e o lado N é ilimitado.

DATE, C. J. — An Introduction to Database Systems, 8ª ed., 2003

Integridade referencial: a referência nunca quebra

  • Garantia defendida pelo banco, não pelo programa — como o UNIQUE do e-mail na aula 04;
  • Recusa o filho órfão: INSERT de book com user_id inexistente falha;
  • Protege o pai com filhos: DELETE de user que ainda tem books falha;
  • Comportamento padrão do MySQL: RESTRICT (recusar);
  • Alternativas declaráveis: ON DELETE CASCADE (o pai leva os filhos), ON DELETE SET NULL — menção, não usaremos.

Recapitulando — relações 1:N

  • Relações se ligam por valores, não por ponteiros (Codd, 1970);
  • Cardinalidades — 1:1, 1:N, N:M — descrevem o domínio (Chen, 1976);
  • A chave estrangeira materializa a relação e mora sempre no lado N;
  • Integridade referencial: órfão recusado, pai protegido — o banco defende sozinho.

models.py — o model Book


class Book(Base):
    __tablename__ = "book"

    id: Mapped[int] = mapped_column(primary_key=True)
    title: Mapped[str] = mapped_column(String(200))
    pages: Mapped[int]
    user_id: Mapped[int] = mapped_column(ForeignKey("user.id"))
    created_at: Mapped[datetime] = mapped_column(server_default=func.now())

    user: Mapped["User"] = relationship(back_populates="books")
  • pages: Mapped[int] — sem mapped_column(): nada a configurar, a anotação basta;
  • ForeignKey("user.id") — a string é "tabela.coluna": a linha FOREIGN KEY ... REFERENCES do quadro;
  • Convenções (ADR-0002): tabela no singular, FK <tabela>_id, datetime com _at.

relationship — os dois lados da relação


class User(Base):
    # ...colunas da aula 04...
    books: Mapped[list["Book"]] = relationship(back_populates="user")


class Book(Base):
    # ...colunas...
    user: Mapped["User"] = relationship(back_populates="books")
  • relationship não vira coluna — existe só no mundo Python;
  • É a relação como objetos navegáveis: user.books é uma lista de Book; book.user é o dono;
  • back_populates: os dois atributos são a mesma relação, vista de cada lado;
  • A FK é a relação na língua do banco; o relationship, na língua dos objetos — o ORM traduz.

O mapa REST da aula 03 se cumpre

A URI conta a relação

  • O caminho de uma URI é hierárquico por definição (RFC 3986, seção 3.3): /users/1/books lê-se "os books do user 1";
  • A relação 1:N aparece em duas camadas do sistema: chave estrangeira no banco, hierarquia na URL;
  • Coleção aninhada: listar e criar acontecem na coleção do dono — criar um book sem dizer de quem ele é não faria sentido;
  • Item plano: /books/{book_id} — o id identifica sozinho; sempre book_id (ADR-0002). A aula 06 pendura aqui o /progress;
  • O prefixo /api se aposenta com a lista em memória — /signup (aula 04) inaugurou o padrão definitivo.

POST /users/{user_id}/books — o 500 anunciado


@app.post("/users/{user_id}/books", response_model=BookRead,
          status_code=201)
def create_book(user_id: int, book: BookCreate,
                db: Session = Depends(get_db)):
    new_book = models.Book(title=book.title, pages=book.pages,
                           user_id=user_id)
    db.add(new_book)
    db.commit()
    db.refresh(new_book)
    return new_book
  • O trio add/commit/refresh do signup — a novidade é o user_id vindo do path, direto para a FK;
  • POST /users/1/books → 201; POST /users/999/books → 500: o ERROR 1452, agora pela API.

GET — o relationship em ação


@app.get("/users/{user_id}/books", response_model=list[BookRead])
def list_books(user_id: int, db: Session = Depends(get_db)):
    user = db.get(models.User, user_id)
    if user is None:
        raise HTTPException(status_code=404, detail="User not found")
    return user.books
  • user.books — nenhuma consulta escrita à mão: ao acessar o atributo, o SQLAlchemy emite o SELECT (lazy loading — confira no echo);
  • Sem o if, /users/999/books devolveria 200 com [] — uma mentira: "user sem livros" e "user inexistente" ficariam indistinguíveis;
  • O 404 aqui não trata erro do banco: trata a semântica.

PUT — o UPDATE que ninguém escreve


@app.put("/books/{book_id}", response_model=BookRead)
def update_book(book_id: int, book: BookCreate,
                db: Session = Depends(get_db)):
    stored_book = db.get(models.Book, book_id)
    if stored_book is None:
        raise HTTPException(status_code=404, detail="Book not found")
    stored_book.title = book.title
    stored_book.pages = book.pages
    db.commit()
    db.refresh(stored_book)
    return stored_book
  • Não existe db.update(): o objeto veio da sessão — mudar os atributos basta;
  • O Unit of Work (aula 04) rastreia as mudanças; o commit emite o UPDATE sozinho — confira no echo.

@app.get("/books/{book_id}", response_model=BookRead)

@app.delete("/books/{book_id}", status_code=204)
def delete_book(book_id: int, db: Session = Depends(get_db)):
    book = db.get(models.Book, book_id)
    if book is None:
        raise HTTPException(status_code=404, detail="Book not found")
    db.delete(book)
    db.commit()
  • db.delete anota a remoção; o commit a executa;
  • 204 sem corpo, como na aula 03 — o contrato não mudou, só a prateleira.

Síntese da aula

  • Relação 1:N: um pai, muitos filhos — cardinalidades do modelo ER (Chen, 1976);
  • A chave estrangeira materializa a relação e mora no lado N (Date); a integridade referencial recusa órfãos e protege pais — ERROR 1452 e 1451;
  • No SQLAlchemy: ForeignKey declara a coluna; relationship/back_populates dão à relação a forma de objetos (user.books, lazy loading);
  • O CRUD de Books renasceu sobre o MySQL: coleção aninhada no dono, item plano, db.get por chave primária, UPDATE emitido pelo Unit of Work;
  • Segunda dívida no quadro: user_id na URL, sem autenticação (ADR-0001 → aula 09).
