Sem objetos, dados e comportamento andam separados


book = {"title": "Clean Code", "pages": 464, "current_page": 120}

A POO nasceu para simular o mundo

  • Simula 67 — Ole-Johan Dahl e Kristen Nygaard, Norwegian Computing Center, Oslo, 1967;
  • Problema real: simular navios, filas e portos — cada entidade com estado e comportamento próprios;
  • Para isso inventaram class, objeto e herança;
  • Prêmio Turing de 2001.

DAHL; NYGAARD. SIMULA 67 Common Base Language, 1968

O termo veio do Xerox PARC

  • Alan Kay cunhou object-oriented programming;
  • Materializado na linguagem Smalltalk (1972);
  • Para Kay, o centro não são as classes: são as mensagens trocadas entre objetos que escondem o próprio estado.

KAY, A. The Early History of Smalltalk. ACM HOPL-II, 1993

Um objeto tem estado, comportamento e identidade

"An object has state, behavior, and identity."
  • Estado — os dados que ele guarda;
  • Comportamento — o que ele sabe fazer;
  • Identidade — ele é ele mesmo, distinto de outro objeto com os mesmos dados.

BOOCH, G. Object-Oriented Analysis and Design with Applications, 3ª ed., 2007

Em Python, tudo já é objeto


>>> (5).__class__
<class 'int'>
>>> "abc".upper()
'ABC'
>>> type(print)
<class 'builtin_function_or_method'>

Números, textos, listas, funções e módulos: a linguagem é orientada a objetos desde a origem (Guido van Rossum, 1991).

Recapitulando — por que POO

  • Dicionários soltos não garantem nada e espalham o comportamento;
  • A POO junta estado e comportamento numa unidade com fronteira;
  • Origem: Simula 67; nome: Alan Kay, Smalltalk;
  • Objeto = estado + comportamento + identidade.

A classe é o molde; o objeto é a peça

Nossa primeira classe


class Book:
    def __init__(self, title, pages):
        self.title = title
        self.pages = pages
        self.current_page = 0

    def progress_percentage(self):
        return self.current_page / self.pages * 100

Anatomia da classe

  • class Book: — declara um novo tipo; nome em CapWords (PEP 8);
  • __init__ — o inicializador: roda ao criar o objeto e define seu estado inicial;
  • Nomes com dois sublinhados são dunder methods — chamados pela linguagem, não por nós;
  • self — o próprio objeto, primeiro parâmetro; não é palavra reservada, é convenção;
  • self.title = title — sem o self., seria variável local que morre no fim da função.

Cada objeto tem o seu próprio estado


clean_code = Book("Clean Code", 464)
pragmatic = Book("The Pragmatic Programmer", 352)

clean_code.current_page = 120

print(clean_code.progress_percentage())   # 25.86...
print(pragmatic.current_page)             # 0
print(isinstance(clean_code, Book))       # True
print(clean_code is pragmatic)            # False

Estado, comportamento e identidade — a definição de Booch, linha a linha.

O self não é mágica


clean_code.progress_percentage()        # forma usual
Book.progress_percentage(clean_code)    # exatamente a mesma chamada

objeto.metodo() é açúcar sintático para Classe.metodo(objeto).

O self é apenas o primeiro argumento, passado pelo interpretador.

O objeto decide como se apresenta


    def __repr__(self):
        return f"Book(title={self.title!r}, pages={self.pages})"

Sem __repr__

<__main__.Book object at 0x104f2b1d0>

Com __repr__

Book(title='Clean Code', pages=464)

Implementar __repr__, __str__, __len__, __eq__ faz o objeto se comportar como um tipo nativo.

RAMALHO, L. Fluent Python, 2ª ed., 2022 — o modelo de dados do Python

Atributo de classe × atributo de instância


class Book:
    genre = "unknown"          # um só, compartilhado por todos

    def __init__(self, title, pages):
        self.title = title     # um por objeto
Armadilha: atributo de classe mutável é compartilhado por todos os objetos. É por isso que, na aula 04, o modelo usa Field(default_factory=datetime.now) e não default=datetime.now() — a segunda forma daria a mesma data a todos os livros.

Recapitulando — classes e objetos

  • A classe descreve; o objeto existe;
  • __init__ dá o estado inicial; self é o próprio objeto;
  • objeto.metodo() = Classe.metodo(objeto);
  • Dunder methods integram o objeto à linguagem;
  • Atributo de classe é compartilhado — cuidado com os mutáveis.

Esconder decisões que podem mudar

Cada módulo deve ocultar uma decisão de projeto sujeita a mudar, expondo apenas uma interface estável.

A ideia é anterior à própria POO: ocultamento de informação. Encapsulamento é essa ideia aplicada ao objeto.

PARNAS, D. On the Criteria To Be Used in Decomposing Systems into Modules. CACM, 1972

Interface pública por fora, estado por dentro

Python confia na convenção, não na trava

  • nome — público, faz parte da interface;
  • _nome — uso interno, "não mexa"; o interpretador não impede nada;
  • __nome — sofre name mangling (vira _Classe__nome), o que evita colisão em herança.

Nenhum dos três é segurança — são acordos entre pessoas que leem o código.

PEP 8 — Style Guide for Python Code

Uma propriedade se lê como atributo
e roda como método


    @property
    def progress_percentage(self):
        return round(self.current_page / self.pages * 100, 1)

    @property
    def is_finished(self):
        return self.current_page >= self.pages
  

clean_code.current_page = 464
print(clean_code.progress_percentage)   # 100.0 — sem parênteses
print(clean_code.is_finished)           # True

O Reading Progress é derivado — nunca armazenado

  • A porcentagem é a página atual sobre o total de páginas;
  • Um Book está concluído quando atinge 100%;
  • Não existe campo de status no sistema.

Um valor calculado nunca fica desatualizado; um valor guardado mente até alguém lembrar de atualizá-lo.

O setter concentra a validação num lugar só


    @pages.setter
    def pages(self, value):
        if value <= 0:
            raise ValueError("pages must be greater than zero")
        self._pages = value
  • Venha o valor de onde vier, um livro com zero páginas é impossível;
  • Hoje self._pages é um inteiro; amanhã pode vir de outra fonte — e book.pages continua funcionando;
  • Trocar o interior sem quebrar quem usa: Parnas em três linhas.

Recapitulando — encapsulamento

  • Interface estável por fora, decisões mutáveis por dentro;
  • Python usa convenção (_nome), não trava;
  • @property expõe dado derivado sem armazená-lo;
  • O setter centraliza a validação.

Herdar é reaproveitar e declarar um subtipo


class EBook(Book):
    def __init__(self, title, pages, file_format):
        super().__init__(title, pages)
        self.file_format = file_format

    def __repr__(self):
        return f"EBook(title={self.title!r}, format={self.file_format!r})"
  • super().__init__(...) — esquecê-lo é o erro mais comum: o objeto nasce sem title;
  • Redefinir __repr__ é sobrescrita: a versão da subclasse tem precedência.

O que é herdado funciona sem ser reescrito


fluent = EBook("Fluent Python", 1012, "epub")
fluent.current_page = 506

print(fluent.progress_percentage)   # 50.0 — veio de Book
print(isinstance(fluent, Book))     # True — "é-um"

Python escolhe o método percorrendo a MRO (Method Resolution Order), visível em EBook.__mro__.

Onde se espera a mãe, a filha tem de servir

"If for each object o1 of type S there is an object o2 of type T such that for all programs P defined in terms of T, the behavior of P is unchanged when o1 is substituted for o2, then S is a subtype of T."

Se a subclasse quebra a expectativa da superclasse, a herança está errada — ainda que o código rode.

LISKOV, B. Data Abstraction and Hierarchy. OOPSLA, 1987

No projeto, herdamos de quem veio antes

Duas linhas nossas, centenas herdadas


class BookCreate(BaseModel):

Herdar de BaseModel traz de graça:

  • Inicializador por palavras-chave;
  • Validação de tipos e mensagens de erro;
  • Conversão para JSON.

A herança também organiza o nosso código


class BookBase(SQLModel):
    title: str
    pages: int


class BookCreate(BookBase):
    pass


class BookRead(BookBase):
    id: int
    user_id: int
Não vamos alterar o projeto agora: enquanto os schemas forem pequenos, a duplicação é mais legível que a indireção. O padrão volta quando eles crescerem.

Recapitulando — herança

  • Herança é relação "é-um" e reaproveitamento de implementação;
  • super() chama a superclasse; sobrescrever redefine comportamento;
  • Liskov: onde se espera a mãe, a filha deve funcionar;
  • No projeto: BaseModel → SQLModel → nossas classes.

Um mesmo comando, comportamentos diferentes


library = [
    Book("Clean Code", 464),
    EBook("Fluent Python", 1012, "epub"),
]

for item in library:
    print(item)     # cada objeto se apresenta do seu jeito

A linguagem escolhe o método do tipo concreto em tempo de execução.

STRACHEY, C. Fundamental Concepts in Programming Languages, 1967 · CARDELLI; WEGNER, 1985

Python não pede parentesco — pede o método


class Magazine:                 # não herda de Book
    def __init__(self, name, pages):
        self.name = name
        self.pages = pages
        self.current_page = 0

    @property
    def progress_percentage(self):
        return round(self.current_page / self.pages * 100, 1)

"Se anda como um pato e grasna como um pato, é um pato" — duck typing.

A função não pede um tipo: pede um comportamento


def print_progress(item):
    print(f"{item.progress_percentage}%")


print_progress(Book("Clean Code", 464))            # funciona
print_progress(Magazine("Superinteressante", 90))  # funciona também
  • Vantagem: flexibilidade sem hierarquia forçada;
  • Preço: o erro só aparece em execução, quando o método falta;
  • Daí a força das anotações de tipo e da validação — o Pydantic da aula 03.

O projeto já usa polimorfismo


raise HTTPException(status_code=404, detail="Book not found")

HTTPException é-uma Exception. É por ser subtipo que o raise funciona e que o FastAPI consegue capturá-la junto com qualquer outra exceção.

Recapitulando — polimorfismo

  • Um mesmo código serve a vários tipos;
  • O tipo concreto decide o comportamento, em execução;
  • Duck typing: importa ter o método, não ter a mãe;
  • O preço é o erro tardio — validação existe para isso.

"É-um" e "tem-um" são coisas diferentes

Um User tem Books


class User:
    def __init__(self, name, email):
        self.name = name
        self.email = email
        self.books = []              # tem-um (na verdade, tem-vários)

    def add_book(self, book):
        self.books.append(book)

    @property
    def finished_count(self):
        return sum(1 for book in self.books if book.is_finished)

Prefira composição a herança

"Favor object composition over class inheritance."
  • A herança amarra a subclasse à implementação da superclasse: mudou a mãe, quebraram as filhas;
  • A composição amarra apenas a uma interface — e pode ser trocada em execução.

GAMMA; HELM; JOHNSON; VLISSIDES. Design Patterns, 1994

No projeto, a composição vira relação 1:N


class User(SQLModel, table=True):
    books: list["Book"] = Relationship(back_populates="user")

O que no laboratório é uma lista Python, no projeto é uma chave estrangeira mais uma relação do ORM. O desenho é o mesmo.

CHEN, P. The Entity-Relationship Model, 1976 — aprofundado na aula 05

Recapitulando — composição

  • Herança: "é-um"; composição: "tem-um";
  • A recomendação clássica é preferir a composição;
  • No Reading Tracker, User tem Books — a relação 1:N da aula 05.

Falta a classe sem __init__ e sem self


class BookCreate(SQLModel):
    title: str
    pages: int

Nenhum inicializador, nenhum método — e ainda assim
BookCreate(title="Clean Code", pages=464) funciona.

title: str não é atribuição — é anotação


>>> class BookCreate(SQLModel):
...     title: str
...     pages: int
...
>>> BookCreate.__annotations__
{'title': <class 'str'>, 'pages': <class 'int'>}

Nada é atribuído: a linha apenas registra que title tem o tipo str. A superclasse lê essas anotações e gera o inicializador, a validação e a conversão para JSON.

PEP 526 — Syntax for Variable Annotations, 2016 · PEP 484 — Type Hints, 2014

table=True é um argumento da definição da classe


class Book(SQLModel, table=True):
    ...
  • Não é atributo: é um argumento nomeado passado ao construir a classe;
  • Quem o recebe é a metaclasse — a maquinaria que fabrica classes;
  • Efeito prático: além de schema, esta classe vira uma tabela no banco.

PEP 3115 — Metaclasses in Python 3000

Um decorator é apenas uma função


def log_call(function):
    def wrapper(*args, **kwargs):
        print(f"calling {function.__name__}")
        return function(*args, **kwargs)
    return wrapper


@log_call
def read_health():
    return {"status": "Ok"}

Recebe uma função e devolve algo no lugar dela.

PEP 318 — Decorators for Functions and Methods, 2004

@app.get não altera a função — ele a registra

  • @property transforma o método num atributo calculado;
  • @app.get("/health") devolve a função intacta e a anota na tabela de rotas do objeto app;
  • É o mecanismo da inversão de controle da aula 01: nós declaramos, o framework chama.

FOWLER, M. Inversion of Control Containers and the Dependency Injection pattern, 2004

Recapitulando — POO declarativa

  • Anotação de tipo no corpo da classe é dado, não atribuição;
  • A superclasse lê as anotações e gera o comportamento;
  • table=True é um interruptor lido pela metaclasse;
  • O @ é uma função que recebe outra função.

De volta ao alvo


class Book(SQLModel, table=True):
    id: int | None = Field(default=None, primary_key=True)
    title: str = Field(max_length=200)
    pages: int
    user_id: int = Field(foreign_key="user.id")

    user: User | None = Relationship(back_populates="books")
  • Classe que herda de SQLModel, com o interruptor de tabela ligado;
  • id: int | None — anotação de tipo lida pela superclasse;
  • Field(...) configura a coluna; Relationship(...) é a composição 1:N.
