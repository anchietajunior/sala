Bloco 1 — Fundamentos e primeiras rotas (backend)

Aula 01 — Início do projeto e frameworks roteiro pronto

branch: aula-01-inicio-do-projeto-e-frameworks · ~2h
Teoria
  • [T-2] Cliente-servidor: cliente pede, servidor responde, nunca o contrário; analogia do restaurante.
  • [T-1] Framework: biblioteca × framework, inversão de controle ("princípio de Hollywood") — quem controla o main() é o FastAPI.
  • [T-6] Dependências: PyPI, pip, ambiente virtual isolado por projeto, requirements.txt, semver de passagem.
Prática
  • Criar projeto/backend, python -m venv .venv e ativar (Mac e Windows), pip install fastapi uvicorn, pip freeze > requirements.txt.
  • Primeira rota: @app.get("/") devolvendo {"message": ...} — o dict vira JSON sozinho.
  • Subir com uvicorn main:app --reload e ver o reload agir ao editar a mensagem.
  • .gitignore (.venv/, __pycache__/) e README.md com a Tabela de Dependências.
  • Teaser de 30s no /docs — "o framework documentou a API sozinho".
Exercício
Rotas GET /status e GET /about, testadas no navegador. Erros clássicos: venv desativado e arquivo não salvo.

Gancho: "digitamos um endereço e apareceu um JSON — mas o que viajou pela rede entre uma coisa e outra?"

Aula 01.2 — Programação Orientada a Objetos com Python aula extra roteiro pronto

sem branch · ~2h · laboratório em oop_lab.py, fora do repositório do projeto
Teoria
  • Por que a POO existe: o dicionário cru não garante nada e espalha o comportamento. Origem em Simula 67 (Dahl & Nygaard) — inventada para simular entidades com estado próprio; o termo vem de Alan Kay e do Smalltalk. Definição de Booch: objeto = estado + comportamento + identidade.
  • Encapsulamento: ocultamento de informação (Parnas, 1972) — interface estável por fora, decisões mutáveis por dentro. Python usa convenção (_nome), não trava.
  • Herança: reaproveitar implementação e declarar um subtipo; princípio da substituição (Liskov, 1987) — onde se espera a mãe, a filha tem de servir.
  • Polimorfismo (Strachey, 1967) e duck typing: Python não pede parentesco, pede o método — e o preço é o erro tardio, que motiva a validação da aula 03.
  • Composição × herança: "tem-um" contra "é-um"; a recomendação clássica do GoF de preferir a composição.
Prática
  • Ponte: reler app = FastAPI() da aula 01 — classe, objeto e método já estavam lá.
  • Classe Book com __init__, atributos e método; instanciar dois objetos e provar que o estado é independente.
  • Desmistificar o self: objeto.metodo() é açúcar para Classe.metodo(objeto), digitado lado a lado.
  • __repr__ e os dunder methods; atributo de classe × de instância — e por que a aula 04 usa default_factory=datetime.now.
  • @property para dado derivado: progress_percentage e is_finished calculados, nunca armazenados — exatamente a definição de Reading Progress do CONTEXT.md. O setter centraliza a validação (pages > 0).
  • EBook(Book) com super() e sobrescrita; leitura da hierarquia real BaseModel → SQLModel → nossas classes.
  • Duck typing com uma Magazine que não herda de nada; HTTPException funcionando por ser-uma Exception.
  • Composição User → Books como lista Python — o mesmo desenho que a aula 05 grava no banco com Relationship.
  • POO declarativa: title: str é anotação e não atribuição (__annotations__ ao vivo no interpretador), table=True como argumento lido pela metaclasse, e um decorator escrito à mão para explicar o @app.get.
Exercício
Uma pequena biblioteca: Author, Book por composição, AudioBook(Book) com __repr__ sobrescrito e Library.average_progress (com o caso da lista vazia). Erros previsíveis: super().__init__() esquecido, parênteses ao ler uma @property e divisão por zero.
Aula complementar: não evolui o Reading Tracker e não gera branch — prepara a turma para lê-lo. Abre e fecha com o mesmo trecho de models.py da aula 05: "quantos símbolos vocês explicam agora?" no início, releitura símbolo a símbolo no fim.

Gancho: "voltamos ao projeto na aula 02, ainda com dicionários crus — guardem o incômodo: na aula 03 eles viram classes."

Aula 02 — Ciclo de vida de uma requisição roteiro pronto

branch: aula-02-ciclo-de-vida-de-uma-requisicao · ~2h
Teoria
  • [T-4] DNS: nome → IP, a consulta em etapas, IP + porta identificando máquina e programa, 127.0.0.1 como loopback (sem DNS nenhum).
  • [T-4] HTTP cru: linha de pedido, headers, corpo; a resposta com linha de status e content-type. Famílias de status: 2xx, 3xx, 4xx (culpa do cliente), 5xx (culpa do servidor).
  • [T-5] uvicorn × FastAPI: o servidor cuida da rede e dos bytes, o framework cuida da aplicação; o contrato entre eles é o ASGI; o --reload é serviço do uvicorn.
  • Parâmetros: path identifica o recurso, query ajusta o pedido (exemplos do GitHub, Google e YouTube).
Prática
  • Analisar a conversa: DevTools → aba Network na rota /health (status, request/response headers, server: uvicorn); curl -i e curl -v mostrando as duas direções; provocar um 404 em /nada.
  • Modelo Book como classe (__init__ + __repr__, Python puro) e a lista books de objetos em memória + prefixo /api — a POO da aula 01.2 entrando no projeto, no mesmo desenho que o ORM usa na aula 04.
  • GET /api/books (lista) e GET /api/books/{book_id} com book_id: int e HTTPException(404) — /abc devolve 422 antes da função rodar. Acesso por atributo (book.id), e o FastAPI serializa o objeto lendo seus atributos.
  • GET /api/books?name= — query param opcional com .lower() dos dois lados.
  • Explorar o Swagger (/docs): rotas documentadas de graça, "Try it out" como cliente HTTP.
  • POST /api/books com book: dict cru e status_code=201 — entra dicionário, sai Book: o dict só existe na fronteira.
  • PUT /api/books/{book_id} (path param e corpo juntos pela primeira vez; o objeto é mutado no lugar) e DELETE com 204 sem corpo.
  • Demonstração da falha: com o DELETE em mãos, len(books) + 1 produz dois livros com o mesmo id — o novo fica inalcançável e o DELETE apaga o errado. Fica sem conserto, como dívida da aula 03.
  • Tabela de Endpoints no README.
Exercício
"Quem decidiu esse status?" — o aluno interroga a própria API: provoca 200/404/422/500 e classifica cada um entre rejeitado na borda pelo framework, escolhido por nós ou consequência de um erro não tratado. Depois argumenta por escrito: por que o 422 e o 404 diferem para o cliente; por que o 500 do POST é a API mentindo sobre a culpa; por que name: str não impediu um livro chamado 42; e por que busca vazia é 200 e não 404. Em casa: fechar a fronteira na mão, escolhendo entre 400 e 422 com justificativa — e contar quantos if seriam necessários com dez campos.
Ganchos armados de propósito: POST sem name → 500 — e a classe não impede, porque ela protege o interior e não vigia a borda (o Pydantic fecha na aula 03); o Swagger documenta a entrada mas mostra a resposta como schema vazio (gancho do response_model); ao salvar qualquer arquivo o livro criado some (memória morre com o processo — banco na aula 04); "o que quebra no len(books) + 1 quando existir DELETE?"

Aula 03 — APIs REST e URIs roteiro pronto

branch: aula-03-apis-rest-e-uris · ~2h
Teoria
  • [T-3] Anatomia da URI (RFC 3986): esquema, host, porta, caminho, query, fragmento — e o fragmento que o navegador nunca envia. URI × URL.
  • [T-3] REST (Fielding, tese de 2000): estilo arquitetural, seis restrições, recurso × representação, interface uniforme, stateless (que motiva o token da aula 09). Honestidade: o mercado usa o núcleo recursos + verbos + status codes.
  • Verbos × CRUD na coleção e no item, com status típicos (201, 200, 204); métodos seguros e idempotentes (RFC 9110); PATCH mencionado, não usado.
  • Boas práticas de URI: substantivo e não verbo, plural na coleção, mesmo nome de path param em todas as rotas.
Prática
  • Desenhar o mapa de rotas do projeto no quadro — inclusive as que só nascem depois (/signup, /users/{user_id}/books, /books/{book_id}/progress).
  • Reproduzir o 500 do dict cru e trocá-lo por Pydantic: BookCreate → o erro vira 422 apontando o campo.
  • response_model nas rotas + schema Book (o que sai tem id, o que entra não).
  • PUT /api/books/{book_id} (idempotência ao vivo) e DELETE com 204 sem corpo.
  • Quebrar o len(books) + 1: apagar → criar → dois livros com id 3; corrigir com contador monotônico next_book_id e global.
  • Atualizar a tabela de Endpoints do README.
Exercício
Campo author (opcional, padrão "") nos dois schemas + create e update. Descartável: a branch segue sem ele.

Gancho: "o CRUD está completo, mas os dados continuam morrendo a cada restart — e o contador de id é artesanal."

Bloco 2 — Persistência (backend)

Aula 04 — Banco de dados e ORMs roteiro pronto

branch: aula-04-banco-de-dados-e-orms · ~2h · pedir o download do MySQL com antecedência
Teoria
  • [T-7] Modelo relacional (Codd, 1970): tabela, linha, coluna, chave primária, constraint, independência de dados; auto-increment aposentando o contador artesanal.
  • SQL (Chamberlin & Boyce, 1974; ANSI 1986): linguagem declarativa. MySQL (Widenius & Axmark, 1995) como banco do curso.
  • [T-7] ORM: descompasso objeto-relacional, padrões de Fowler (Active Record, Data Mapper, Unit of Work), SQLAlchemy como Data Mapper. Tabela comparativa SQL cru × ORM.
  • Honestidade: o ORM não elimina o SQL, ele o gera — por isso o echo=True fica ligado a aula inteira.
Prática
  • Instalar e subir o MySQL (brew / MySQL Installer), CREATE DATABASE reading_tracker.
  • SQL na mão: CREATE TABLE user, INSERT, SELECT, DESCRIBE; repetir o INSERT e ver o ERROR 1062: Duplicate entry; DROP TABLE ao final para o ORM recriá-la.
  • pip install sqlalchemy pymysql cryptography — uma dependência por camada da conversa.
  • database.py: DATABASE_URL dissecada como URI, engine com echo=True, SessionLocal, Base.
  • models.py: model User comparado coluna a coluna com o CREATE TABLE do quadro.
  • Base.metadata.create_all() — assistir ao ORM emitir o CREATE TABLE no terminal.
  • Schemas UserCreate/UserRead (from_attributes=True) e get_db com Depends — injeção de dependência, ensaio geral da autenticação da aula 10.
  • POST /signup: o trio add/commit/refresh como Unit of Work ao vivo.
  • Provar a persistência: reiniciar o uvicorn — o User fica, os Books voltam à lista de fábrica.
  • E-mail duplicado: 500 → 409 com select(...).where(...) + db.scalar, mantendo o UNIQUE como última defesa.
  • README ganha a seção Banco de dados e a Tabela de Dependências atualizada.
Exercício
Campo age no model — a pegadinha é o create_all não alterar tabela existente (Unknown column 'age'): resolve-se com DROP TABLE. É a dor que justifica migrations. Descartável.
Dívida deliberada (ADR-0001): a senha é gravada em texto puro e fica visível no SELECT * FROM user. Anotada no quadro; vira material da aula 09.

Aula 05 — Relações 1:N e o CRUD de Books roteiro pronto

branch: aula-05-relacoes-1-n-e-o-crud-de-books · ~2h
Teoria
  • Ligar dados por valor, não por ponteiro — o que o modelo relacional substituiu (bancos navegacionais, CODASYL).
  • Modelo entidade-relacionamento (Chen, 1976): entidades, relacionamentos, cardinalidades 1:1, 1:N, N:M.
  • Chave estrangeira (definição de C. J. Date) e por que ela mora sempre no lado N.
  • Integridade referencial: o banco recusa o filho órfão e protege o pai com filhos (RESTRICT padrão; CASCADE e SET NULL mencionados).
  • Rotas aninhadas: coleção no dono (/users/{user_id}/books), item plano (/books/{book_id}); o prefixo /api se aposenta.
Prática
  • models.Book com ForeignKey("user.id") e os dois lados de relationship(back_populates=...) — colunas × relação navegável.
  • create_all cria só a tabela book; SHOW CREATE TABLE book exibe a FK e o ENGINE=InnoDB.
  • Integridade ao vivo no cliente MySQL: ERROR 1452 (órfão) e ERROR 1451 (pai protegido) — sem um if sequer.
  • Demolição da lista em memória e dos schemas antigos; name vira title e pages entra no cadastro (a aula 06 depende dele).
  • CRUD sobre o banco: POST e GET /users/{user_id}/books (com db.get e 404 de User), GET/PUT/DELETE /books/{book_id}.
  • user.books e o lazy loading; o PUT sem nenhum db.update() — o Unit of Work emite o UPDATE sozinho.
  • Reiniciar o uvicorn: acabou a "lista de fábrica" — Users e Books moram no MySQL.
  • README com a tabela de Endpoints reescrita (sem dependências novas).
Exercício
Reconstruir a busca por título sobre o banco (select + contains + db.scalars().all()), observando o LIKE no echo. O erro clássico — esquecer o user_id no where — vaza livros de todos os usuários. Descartável.
Segunda dívida deliberada (ADR-0001): o user_id vem da URL, sem autenticação — trocar o número lê os livros de qualquer pessoa. É o ataque que abre a aula 09.

Fios que atravessam o semestre

  • Um projeto só: toda aula evolui o Reading Tracker; a teoria aparece quando a prática precisa dela.
  • Provocar a falha antes de corrigi-la: 500 do dict cru (03), 500 do e-mail duplicado (04), 500 do book órfão (05) — cada um vira o status 4xx correto na mesma aula.
  • Dívidas deliberadas (ADR-0001): senha em texto puro (04) e user_id na URL (05) ficam anotadas no quadro até a aula 09, quando abrem a discussão de autenticação.
  • Analogia do restaurante: recorrente das aulas 01 a 03 (cliente/servidor, status codes, interface uniforme).
  • Mac e Windows: todo comando de terminal aparece nas duas variantes.
  • Uma branch por aula em projeto/, e o README atualizado ao fim de cada uma (Endpoints + Tabela de Dependências) — exceto a aula extra 01.2, que não toca o projeto.
  • Exercícios descartáveis: das aulas 03, 04 e 05 são desfeitos ao final — a branch seguinte parte do código do roteiro.
